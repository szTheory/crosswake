### Phase 54: Sigra Session Authority Contract And Route-Gate Semantics

**Goal:** Expand v3.5's contract-only auth lane into a full backend-owned session authority projection and fail-closed route-gate evaluator.

**Requirements:** SESS-01, SESS-02, SESS-03, DIAG-01

**Plans:** 5 plans — completed 2026-06-02

Plans:
- [x] `54-01-PLAN.md` — Expand Sigra authority contracts and the canonical auth denial-code registry.
- [x] `54-02-PLAN.md` — Add explicit `auth_posture` validation and manifest-visible route truth.
- [x] `54-03-PLAN.md` — Implement `Sigra.Evaluator` and delegate RouteGate auth checks to it.
- [x] `54-04-PLAN.md` — Promote doctor, publish-readiness, support-matrix, and operator inspection to session-authority truth.
- [x] `54-05-PLAN.md` — Close guides, docs-contract, and merge-blocking proof for full Phase 54 auth posture.

**Success criteria:**
1. `SessionAuthorityLane` and `AuthContext` expose explicit state, assurance, freshness, expiry, remembered-session, and revocation/version fields with validators.
2. RouteGate denies missing, non-active, expired, revoked/version-mismatched, weak-assurance, and stale-recent-auth contexts before allowing sensitive routes.
3. Remembered or cached auth state cannot satisfy sensitive recent-auth predicates unless the route explicitly opts into the weaker posture.
4. Auth denial codes and shell-safe detail allowlists are canonical and do not leak tokens, provider payloads, passkey credential IDs, or PII.

### Phase 55: Session Handoff Tickets And Authority Projection

**Goal:** Add short-lived, single-use handoff tickets that upgrade session authority only through backend redemption.

**Requirements:** HAND-01, HAND-02, HAND-03

**Plans:** 3 plans

Plans:
- [ ] `55-01-PLAN.md` — Add pure Sigra handoff contracts plus the canonical `auth.handoff.*` denial registry and proof scaffold.
- [ ] `55-02-PLAN.md` — Prove example-host issue/redeem/revoke flow with Ecto-backed one-time records, audit events, and Phoenix session-renewal instructions.
- [ ] `55-03-PLAN.md` — Close diagnostics, support truth, guides, fixtures, and merge-blocking proof for shipped handoff machinery and explicit non-claims.

**Success criteria:**
1. Hosts can issue signed short-lived handoff envelopes backed by server-side one-time ticket records.
2. Redemption atomically consumes the ticket, renews the Phoenix session, and projects a refreshed backend `SessionAuthorityLane`.
3. Expired, replayed, revoked, binding-mismatched, intent-mismatched, and route-mismatched tickets deny with stable auth codes and sanitized shell-safe details.
4. Handoff lifecycle proof covers issue, redeem, revoke, expire, replay, and audit metadata without requiring provider/device services.

### Phase 56: Step-Up Intent And Plug/LiveView Ceremony

**Goal:** Provide a server-owned step-up intent and shared challenge/return flow for routes requiring stronger or fresher authentication.

**Requirements:** STEP-01, STEP-02, STEP-03

**Success criteria:**
1. Hosts can create bounded step-up intents with lifecycle state, required assurance/freshness, source, expiry, and manifest-known return target.
2. Plug/controller and LiveView `on_mount` paths call one evaluator and fail closed into the same intent/challenge flow.
3. Successful step-up consumes the intent, renews session/CSRF posture, refreshes backend authority, and returns only to a validated Crosswake route.
4. Invalid, expired, canceled, or consumed intents produce safe denial/fallback behavior without arbitrary `return_to` URL handling.

### Phase 57: OAuth, Passkey, And Native Return Boundaries

**Goal:** Ship typed adapter seams for OAuth, passkey, and native auth returns without provider-specific core templates or shell authority.

**Requirements:** RETN-01, RETN-02, RETN-03

**Success criteria:**
1. Route policy can declare auth-return boundaries as route-local seams with explicit return kind, callback/route binding, and validation requirements.
2. Return envelopes validate state, nonce, PKCE posture, redirect matching, link verification status, expiry, and replay posture before backend promotion.
3. OAuth callbacks, passkey assertions, native deep links, and shell bridge events remain evidence-only until backend validation updates session authority.
4. Public docs and support truth distinguish adapter seams from first-party provider templates, passkey SDK wrappers, refresh-token orchestration, and device proof claims.

### Phase 58: Auth Diagnostics, Proof, And Security Closeout

**Goal:** Make full Sigra machinery inspectable, documented, and proof-backed without overstating provider/device support.

**Requirements:** DIAG-02, DIAG-03, PROOF-01

**Success criteria:**
1. Stable `[:crosswake, :auth, ...]` telemetry events document low-cardinality metadata for session evaluation, denial, handoff, step-up, OAuth return, and passkey return flows.
2. Doctor, support matrix, operator inspection, guides, and docs-contract tests distinguish full Sigra machinery from v3.5 contract-only truth and advisory provider/device proof.
3. Merge-blocking hermetic proof covers contracts, route gates, replay/expiry/revocation, step-up returns, denial sanitization, telemetry/docs parity, and security-sensitive non-claims.
4. A dedicated security review checks token, handoff, step-up, OAuth/passkey return, telemetry, and denial surfaces before milestone closeout.
