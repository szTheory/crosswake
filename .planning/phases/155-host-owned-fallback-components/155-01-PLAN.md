**Decision: `no-change`.**

**Rationale (cites D-01, D-02, D-53, D-54).** The `pluralization` signal fired on "Fallback
Components", but D-01 locks that Phase 155 pushes nothing: there is no `menu` capability, no
menu wire command, and three shipped mechanisms actively forbid adding one this phase. So no
*second dispatch variant* exists to generalize over — promoting a new "control family" noun
today would mint an identity with exactly one inhabitant, which is abstraction-without-a-
second-case, the inverse of the error this checkpoint guards. D-02 further settles it: the
host-owned fallback is not a sibling delivery path selected at dispatch time; it is a pure
function of assigns that renders first, and a denial (from Phase 156 onward) *annotates* an
already-visible surface rather than triggering it. D-53 freezes the `actions` shape as the
155→156 seam and D-54 confirms 156 adds the native leg additively with zero breaking changes
to adopter-owned files — the promote moment, if it ever comes, is Phase 156's, with the
second variant actually in hand.

**Companion invariant (adopted, not deferred).** The generalized intent is encoded as a test:
*every declared control family resolves to exactly one of {native dispatch, host-owned
fallback, explicit denial} — never to silent success.* It lands as the A3 vocabulary
enumeration in 155-07 (`exercised ∪ explicitly-excluded == closed_vocabulary/0`) plus the
155-02 ExUnit assertions that the two undeclared moments raise distinct, named errors. It
goes red the instant a future phase reintroduces a silent-success path.
