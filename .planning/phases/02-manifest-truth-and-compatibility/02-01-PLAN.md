<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Phoenix-side typed contract -> generated manifest/runtime consumers | Incorrect contract modeling can let unsafe or dishonest compatibility claims propagate downstream |
| Support-matrix truth -> public claims | Drift or overbroad defaults can create support-claim dishonesty |
| Compatibility evaluation -> future shell activation | Ambiguous or permissive logic can enable silent compatibility downgrades |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-01 | T | `lib/crosswake/manifest/types.ex` | mitigate | Encode one canonical manifest shape with explicit top-level sections per D-04 so downstream consumers cannot reinterpret route truth through ad hoc JSON |
| T-02-02 | E | `lib/crosswake/compatibility/compatibility.ex` | mitigate | Separate manifest-schema, bridge, native-runtime, and capability checks so no single permissive result can elevate an incompatible route into an activatable one |
| T-02-03 | S | `lib/crosswake/compatibility/route_gate.ex` | mitigate | Surface origin/runtime/capability mismatches as explicit fail-closed route-gate reasons, preventing origin or route trust confusion |
| T-02-04 | R | `lib/crosswake/support_matrix/support_matrix.ex` | mitigate | Represent support claims as typed statuses with narrow presets so docs and tooling can prove whether a claim was supported, expected but unproven, or unsupported |
| T-02-05 | I | compatibility findings | accept | The findings expose version and support truth only; no secrets are introduced in this plan |
</threat_model>
