<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Compatibility module -> release docs | Runtime-compatibility semantics inform how release policy is explained publicly. |
| Canonical support truth -> doctor output | Generated support truth must stay aligned with operator-facing diagnostics. |
| Doctor output -> maintainers | Release decisions taken from diagnostics can under- or over-state compatibility if policy drifts. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-05 | Tampering | `guides/compatibility.md`, `guides/support_matrix.md` | mitigate | Render release/versioning policy from typed support truth and lock axis wording with ExUnit compatibility/renderer tests so policy drift cannot silently rewrite compatibility rules. |
| T-12-06 | Repudiation | `lib/crosswake/doctor/doctor.ex`, `guides/compatibility.md` | mitigate | Doctor and compatibility guides must both print the same compatibility axes and package-version caveat so maintainers cannot later claim the release contract was unclear. |
| T-12-07 | Spoofing | future companion release process | mitigate | Encode companion minimum-range requirements in canonical support truth so a companion cannot present itself as compatible without declaring core, axis, and capability-major ranges. |
| T-12-08 | Elevation of Privilege | `guides/compatibility.md` | mitigate | Keep package versions separate from runtime compatibility axes so a minor package bump cannot imply unsupported native/runtime authority is safe to activate. |
</threat_model>
