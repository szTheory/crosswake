<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HTTP client → Plug | Untrusted inbound `X-Crosswake-Thread-Id` header value crosses here |
| Plug → Logger.metadata / telemetry handlers | The id propagates into process metadata and emitted telemetry |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-92-01 | Tampering / Information Disclosure | Inbound `X-Crosswake-Thread-Id` carrying PII or oversized value | mitigate | All telemetry routed through `Threadline.Telemetry.execute/3`; `safe_value?/1` drops binaries > 128 chars before emission (Task 2). The id is stored opaquely in `Logger.metadata`; host owns log-sink hygiene (documented in Phase 96 guide). |
| T-92-02 | Spoofing | Client forging an inbound `thread_id` | accept | By design — `thread_id` is an opaque correlation hint, not an authority token. No security decision is made on its value. Documented gap closed by Phase 93 native injection. |
| T-92-03 | Information Disclosure | Forbidden/PII keys reaching telemetry handlers | mitigate | `meta` is restricted to `[:thread_id, :source]` and passed through `Telemetry.execute/3`; the Phase 91 forbidden-key denylist drops any forbidden key (Task 2 verifies). |
| T-92-04 | Denial of Service | Weak/predictable minted ids | mitigate | `Threadline.Id.generate/0` uses `:crypto.strong_rand_bytes/16` (CSPRNG), not `:rand` (Task 1). |
| T-92-SC | Tampering | npm/pip/cargo installs | n/a | Phase 92 introduces zero new packages (RESEARCH Package Legitimacy Audit: not applicable). |
</threat_model>
