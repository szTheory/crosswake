# Phase 152 - UI Design Contract

> Visual and interaction contract for the Phase 152 capability-map, collateral, and v20 handoff surfaces. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

---

## Phase Surface Contract

Phase 152 is a documentation and proof-surface phase, not a new application shell.
The primary surfaces are `guides/capability_map.md`, light entry-point links from
`README.md` and `examples/phoenix_host/README.md`, evidence/collateral labels, and
the planning-only `152-V20-HANDOFF.md`.

Required first-read order for the capability guide:

1. What works today.
2. What evidence exists.
3. What v20 will do.
4. Detailed capability rows, package ownership, proof posture, limitations, and named later packs.

Do not introduce a marketing hero, dashboard, generic plugin catalog, or broad native-support table that hides route ownership. The surface must read like a calm maintainer guide: route owner, proof posture, package owner, fallback behavior, and v20 implication must be visible in every capability row.

Sources: `152-CONTEXT.md` D-01 through D-29, `152-RESEARCH.md`, `brandbook/BRAND-SPEC.md`, `guides/capabilities.md`, `guides/support_matrix.md`.

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none; use deterministic Markdown renderer plus existing Phoenix host CSS patterns if a browser surface is touched |
| Icon library | none; use text labels instead of icon-only status indicators |
| Font | `--cw-font-body` Atkinson Hyperlegible Next for body/UI, `--cw-font-display` Space Grotesk for headings, `--cw-font-mono` JetBrains Mono for routes, code, and exact package values |

Contract details:

- Use semantic Crosswake tokens from `brandbook/tokens/tokens.css`; do not reference primitive tokens in new component CSS.
- Keep docs quieter than marketing: no oversized hero block, no gradient splash, no decorative orb/background treatment.
- Reuse existing showcase vocabulary: route cards, runtime badges, capability chips, diagnostics/details blocks, boundary warnings, and support-truth labels.
- Cards for any rendered browser collateral use 8px radius to match current showcase lane cards. Small badges use 6px radius.
- Every color-coded state must include visible text. Color alone is never sufficient.

shadcn gate: not applicable. No `components.json`, Tailwind config, React, Next.js, or Vite app was detected in this workspace.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Badge internal gaps, table cell micro-gaps, inline metadata separation |
| sm | 8px | Chip padding, compact row gaps, badge group gaps |
| md | 16px | Default block spacing, table cell padding, card inner rhythm |
| lg | 24px | Guide section padding, route-card padding, README entry block spacing |
| xl | 32px | Major guide section breaks, capability group breaks |
| 2xl | 48px | Top-level guide breaks between today/evidence/v20/detail sections |
| 3xl | 64px | Page-level spacing only; avoid inside dense capability tables |

Exceptions: interactive links or controls in any browser-rendered Phase 152 surface must have a 44px minimum touch target. Markdown tables may use native document flow, but any custom HTML wrapper must preserve the 16px body rhythm and must not introduce horizontal overflow at 375px width.

## Typography

Use exactly these four text sizes and exactly two weights for Phase 152 surfaces.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px | 400 | 1.5 |
| Label | 14px | 600 | 1.43 |
| Heading | 20px | 600 | 1.2 |
| Display | 28px | 600 | 1.29 |

Rules:

- Body copy uses Atkinson Hyperlegible Next.
- Headings use Space Grotesk.
- Routes, package names, proof classes, and exact enum values use JetBrains Mono at the Label size.
- Do not introduce 700 or 800 weight in new Phase 152 docs/collateral UI; use 600 for emphasis.
- Do not use negative letter spacing in Phase 152 docs surfaces.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `--cw-surface-default` / `#F7F1E6` | Guide background, README entry area, default docs surface |
| Secondary (30%) | `--cw-surface-raised` / `#EFE6D6` | Capability row group backgrounds, warning boxes, metadata bands |
| Accent (10%) | `--cw-action-bg` / `#2B756A` | Primary CTA, guide links, active route-line highlight, selected capability group border |
| Destructive | `--cw-status-error` / `#9A4D35` | Destructive or policy-risk states only |

Accent reserved for: `Read Capability Map` links/buttons, active in-page anchors, selected capability group border, and route-line highlights in optional collateral. Do not use the accent for every chip or status.

Semantic status colors:

| Semantic | Token | Required Label |
|----------|-------|----------------|
| LiveView route | `--cw-runtime-liveview` | `LiveView route` |
| Offline island or cached route | `--cw-runtime-offline` | `Offline island` or `Cached read-only` |
| Native screen | `--cw-runtime-native` | `Native screen` or `The host app owns this native screen` |
| Bridge contract | `--cw-runtime-bridge` | `Bounded bridge` |
| Sensitive, destructive, or policy risk | `--cw-runtime-sensitive` | Exact risk label, never color alone |
| Warning or advisory | `--cw-status-warning` | `Advisory evidence` or concrete warning text |

Accessibility rules:

- Normal text must meet WCAG AA contrast in light and dark modes.
- `--cw-text-muted` is allowed for normal secondary text; `--cw-text-subtle` is not allowed for normal-size text.
- Focus rings use `--cw-action-focus-ring`, 2px outline, 2px offset.
- Reduced motion must preserve meaning; no looping animation behind documentation text.

## Component And Interaction Contract

Capability guide row order:

| Position | Field |
|----------|-------|
| 1 | Capability or surface |
| 2 | Display label |
| 3 | Route or evidence source |
| 4 | Current category |
| 5 | Route runtime owner |
| 6 | Package owner |
| 7 | Proof posture |
| 8 | Denial/fallback behavior |
| 9 | v20 implication |

Required display labels:

- `Available today`
- `Proof-backed example`
- `Demo pressure`
- `Advisory evidence`
- `Future gap`
- `Next-pack candidate`

Required proof posture labels:

- `merge-blocking`
- `advisory`
- `not-yet-proven`
- `unsupported`

Required package-owner labels:

- `core`
- `native shell`
- `first-party companion`
- `example/docs-only`
- `deferred`

Required interaction behavior:

- README and example README add one short entry-point link each; they must not duplicate the full capability map.
- Optional browser-rendered collateral must remain single-purpose: show the product surface and link to proof labels. It must not become a dashboard.
- Any expandable detail block must open to limitations, fallback behavior, or proof source; do not hide the core label/category fields behind disclosure.
- Any screenshot metadata must state that screenshots are collateral after route-tour assertions. Screenshots cannot be labeled as proof posture.
- Any reset affordance must distinguish server fixture reset from browser-owned IndexedDB/local outbox reset.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Read Capability Map |
| Empty state heading | No capability rows defined |
| Empty state body | Add a typed `Crosswake.CapabilityMap` row before rendering the guide. |
| Error state | Capability map drift detected. Regenerate `guides/capability_map.md` from `Crosswake.CapabilityMap` and rerun support/capability parity tests. |
| Destructive confirmation | Reset showcase fixtures: Reset server fixtures only. Browser IndexedDB and local outboxes are not cleared. |

Preferred microcopy:

- `Demo pressure`
- `Future gap`
- `Backend projection required`
- `The host app owns this native screen`
- `Screenshots are collateral after route-tour assertions`
- `Cached read-only is not offline mutation`

Forbidden copy:

- `magic bridge`
- `everything works offline`
- `native mobile with no native work`
- `generic plugin support`
- `write once, run anywhere`
- `live StoreKit support`
- `Play Billing support shipped`
- `RevenueCat support`
- any purchase, subscriber, unlock, or entitlement copy that bypasses backend projection authority
