## Summary
Phase 46 should be planned as a pure contract-and-policy slice: add typed auth contracts, wire route predicate declarations into policy+manifest, and enforce fail-closed auth denials in `RouteGate` with `:step_up_required`. No runtime step-up machinery is built in this phase. [VERIFIED: codebase grep]

The existing project architecture already provides direct templates for each required change: contract modules (`Commerce`, `Rindle`), route predicate validation (`Policy.Schema` + `Policy.Route`), fail-closed denial wiring (`RouteGate` + `Shell.Denial`), and product-truth surfaces (`Doctor` + `SupportMatrix`). Planning should reuse these seams, not invent new ones. [VERIFIED: codebase grep]

**Primary recommendation:** Implement Phase 46 as one cohesive fail-closed path: `Policy DSL -> Route struct -> Manifest RouteEntry -> RouteGate auth check -> Shell denial -> Doctor/support truth`, with hermetic proofs for each boundary. [VERIFIED: codebase grep]

### Pattern 1: Contract-First Companion Surface
**What:** Use nested structs + closed vocabularies + `new_*` and `validate_*` API. [VERIFIED: codebase grep]  
**When to use:** New companion seam contract without external dependency runtime. [VERIFIED: codebase grep]  
**Example:** `Crosswake.Companions.Rindle.Contracts` and `Crosswake.Commerce.Contracts`. [VERIFIED: codebase grep]

### Pattern 2: Evidence-Authority Fence
**What:** Reject authority-like keys in evidence payload metadata. [VERIFIED: codebase grep]  
**When to use:** Any client-originated signal that must not directly grant authority. [VERIFIED: codebase grep]  
**Example:** `reject_trace_authority_lane/2` style in Rindle contracts tests. [VERIFIED: codebase grep]

### Pattern 3: Fail-Closed Gate Ordering
**What:** Prepend specialized denials before generic compatibility findings. [VERIFIED: codebase grep]  
**When to use:** Security-restrictive predicates (gates, kill switches, auth). [VERIFIED: codebase grep]  
**Example:** `RouteGate` kill-switch then gate currently; insert auth immediately after gate per D-16. [VERIFIED: codebase grep]

### Anti-Patterns to Avoid
- **Auth authority in client evidence:** Violates AUTH-01 and D-08/D-09. [VERIFIED: codebase grep]
- **Fail-open on missing auth context:** Violates AUTH-02 and D-10. [VERIFIED: codebase grep]
- **Using generic denial codes for auth:** Violates D-18/D-19. [VERIFIED: codebase grep]

## Common Pitfalls

### Pitfall 1: Predicate Drift Across Policy/Manifest/Gate
**What goes wrong:** Add DSL keys but forget RouteEntry serialization or gate evaluation. [VERIFIED: codebase grep]  
**Why it happens:** Multi-file route contract path (`Schema -> Route -> Builder -> Types -> RouteGate`). [VERIFIED: codebase grep]  
**How to avoid:** Plan one vertical slice test that asserts full path from route declaration to denial behavior. [VERIFIED: codebase grep]  
**Warning signs:** Predicates compile but no `:step_up_required` emitted. [VERIFIED: codebase grep]

### Pitfall 2: Evidence Field Creep Into Authority
**What goes wrong:** Evidence accepts `mfa_level`/authority-esque keys and bypasses backend projection. [VERIFIED: codebase grep]  
**Why it happens:** Convenience during struct ingestion. [ASSUMED]  
**How to avoid:** Explicit forbidden-key validator mirroring Rindle trace metadata checks. [VERIFIED: codebase grep]  
**Warning signs:** Tests only check happy-path evidence construction, not forbidden keys. [VERIFIED: codebase grep]

### Pitfall 3: Doctor/Support Truth Lagging Code
**What goes wrong:** Runtime behavior changes without support-matrix/doctor parity. [VERIFIED: codebase grep]  
**Why it happens:** Product-truth surfaces are separate modules/tests. [VERIFIED: codebase grep]  
**How to avoid:** Add auth finding tests in doctor human + JSON formatting and support matrix rendering parity tests. [VERIFIED: codebase grep]  
**Warning signs:** New denial exists but no auth row/finding in doctor/support outputs. [VERIFIED: codebase grep]

|---------------|---------|-----------------|

| V6 Cryptography | no (Phase 46) | Deferred; no token/passkey/OAuth ceremony implementation in this slice |

### Known Threat Patterns for Elixir/Phoenix Route-Policy Auth
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Client asserts stronger auth than backend | Spoofing/Elevation | Reject authority keys in evidence and require backend authority lane |
| Missing auth context silently allows access | Elevation | Fail-closed `:step_up_required` when predicates are declared and unmet |
| Over-disclosure in denial payload | Information Disclosure | Limit denial details to typed non-sensitive fields only |
