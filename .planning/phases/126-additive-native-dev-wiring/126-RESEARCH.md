## Summary

Phase 126 is a strictly additive codebase change: no new runtime dependencies, no library changes, no proof-fixture mutations. All decisions were locked at discuss-phase (D-01..D-16). This research grounds those decisions in the actual codebase state so the planner can write exact, executable tasks without ambiguity.

**Three areas of high implementation-execution risk:**

1. **D-10 blast radius (HIGHEST):** Introducing `prod`/`dev` product flavors renames every Gradle variant. The complete inventory (below) shows three distinct hit sites across `script/verify_generated_android_shell.sh` and `examples/QUICK_START.md`. All CI workflows that contain `gradlew` task names run against `packages/crosswake-shell-core-android` (not `examples/android_shell_host`), so they are EXEMPT from the blast radius. Only the script and QUICK_START need migration.

2. **QUICK_START drift scanner compatibility:** The existing `quick_start_adoption_drift_test.exs` `wrong_port_failures` function scans for `localhost:(\d+)` and `PORT=(\d+)` — NOT `10.0.2.2:(\d+)`. The Android dev URL `http://10.0.2.2:4700` will NOT trigger a wrong-port failure. However, any path like `examples/android_shell_host/app/src/dev/assets/route_activation.json` appearing in QUICK_START would be checked by `documented_path_failures` — that file will exist after generation, so no false failure.

3. **native_evidence_drift_test `required_terms` for build.gradle:** The test requires `"versionName \"0.1.2\""` to remain in `app/build.gradle`. Adding `versionNameSuffix "-dev"` to the `dev` flavor does NOT remove `versionName "0.1.2"` from `defaultConfig` — safe. The test also requires `"io.github.sztheory:crosswake-shell-core-android:0.1.2"` — the flavor addition does not change the dependency declaration — safe.

**Primary recommendation:** Execute in this wave order: (1) extend contract generator + commit dev fixtures, (2) iOS pbxproj + scheme + Info-Dev.plist, (3) Android build.gradle + dev source-set files, (4) migrate blast-radius hits in script + QUICK_START, (5) write + run the D-14 guard test.

**Recommended approach:** The script already forks on `PROJECT_ROOT_INPUT` (lines 218-224). Add the `prod`-flavored tasks only in the `PROJECT_ROOT_INPUT`-is-set branch, or unconditionally use `prod`-prefixed tasks (generated shells from the template have no flavor → `testProdDebugUnitTest` would fail on them). **Best: use a variable:**

## Common Pitfalls

### Pitfall 1: `NSExceptionDomains` key must be hostname `localhost` (not `127.0.0.1`)

**What goes wrong:** Using `127.0.0.1` as the `NSExceptionDomains` key silently fails — ATS requires the hostname `localhost`, not the IP.
**How to avoid:** `Info-Dev.plist` uses `<key>localhost</key>` as the exception domain key.

### Pitfall 2: `WKAppBoundDomains` must include `localhost` in dev plist

**What goes wrong:** If `limitsNavigationsToAppBoundDomains` is effectively on and `WKAppBoundDomains` does not include `localhost`, WebKit silently refuses navigation to `http://localhost:4700`.
**How to avoid:** `Info-Dev.plist` `WKAppBoundDomains` array = `["example.com", "localhost"]`.

### Pitfall 3: `autoVerify="true"` on the dev Android intent-filter

**What goes wrong:** Adding `android:autoVerify="true"` to the `http://10.0.2.2` intent-filter triggers install-time asset-link verification that always fails (10.0.2.2 has no Digital Asset Links file). On API ≤ 30 this can cascade and break the proof domain's verification too.
**How to avoid:** The dev intent-filter in `app/src/dev/AndroidManifest.xml` omits `autoVerify` entirely.

### Pitfall 4: `tools` namespace not declared on dev manifest root

**What goes wrong:** `tools:replace="android:networkSecurityConfig"` silently no-ops if `xmlns:tools` is not declared on `<manifest>`.
**How to avoid:** `app/src/dev/AndroidManifest.xml` must have `xmlns:tools="http://schemas.android.com/tools"` on `<manifest xmlns:android="...">`.

### Pitfall 5: `flavor named main` collision with source-set

**What goes wrong:** If the proof flavor were named `main`, it would collide with the `src/main` source set. [Already resolved: locked to `prod` by D-06.]

### Pitfall 6: Default `mix crosswake.contract.gen` run clobbers dev fixtures

**What goes wrong:** If the `if dev?` guard is absent or inverted, a plain `mix crosswake.contract.gen` call overwrites the dev fixtures with prod content.
**How to avoid:** The `--dev` branch is gated by `if dev? do ... end`. The prod branch runs the existing 6 `write_if_changed` calls, plus the informational shell output. The dev branch runs ONLY the 2 dev path writes.

### Pitfall 7: Adding dev paths to `@generated_json_paths` in contract_drift_test

**What goes wrong:** Adding dev fixture paths to `@generated_json_paths` causes the "seven committed surfaces" test to assert them as prod surfaces (the test name and count become wrong; the anti-vacuity regression may also false-trigger).
**How to avoid:** Add a SEPARATE `@dev_generated_json_paths` module attribute and a separate test, as specified in D-13.

### Pitfall 8: native_evidence_drift_test requires `build.gradle` terms

**What goes wrong:** Adding `productFlavors` to `build.gradle` is safe, but if `versionName "0.1.2"` were accidentally removed or moved, `native_evidence_drift_test.exs` fails on `:stale_android_coordinate`.
**How to avoid:** `versionName "0.1.2"` stays in `defaultConfig`; `versionNameSuffix "-dev"` is additive in the `dev` flavor block.

### Pitfall 9: `Run Script build phase` ordering in pbxproj

**What goes wrong:** If the Run Script phase is listed BEFORE the Resources phase in `buildPhases`, the copy overwrites a file that hasn't been copied yet — technically fine but non-standard. If listed first, it copies a file that doesn't exist in `$BUILT_PRODUCTS_DIR` yet.
**How to avoid:** Add the Run Script phase AFTER the Resources phase in the `buildPhases` array.
