# Phase 31: First Hex Publish — Strategic Recommendations

**Goal:** Execute the first authoritative Hex publish of `crosswake` securely and establish a durable, automated release pipeline using `release-please` and GitHub Actions, minimizing human error while maintaining operator trust.

---

## 1. Executive Summary & Core Stance

In alignment with the Crosswake Elixir OSS DNA ("Release truth matters" and "Install truth is product truth"), release automation must be designed early, not bolted on. The process of publishing a package should be hermetic, reproducible, and boring. 

We recommend **Fully Automated Publishing via `release-please`**. A human should review the generated changelog and version bump in a PR. Merging that PR should act as the authoritative gate that triggers the automated tag creation, GitHub Release generation, and Hex.pm publish. 

---

## 2. Approach Analysis: Orchestrating the Hex Publish

### Approach A: Fully Automated via `release-please` + CI Publish (Recommended)
This approach binds the source of truth (the git commit history) to the artifact (Hex package). `release-please` accumulates conventional commits into a Release PR. Merging the PR creates a tag, which in turn triggers a GitHub Action to run `mix hex.publish --yes`.
* **Pros:** 
  - Zero-touch publishing once the PR is merged.
  - Guarantees the git tag, GitHub Release, and Hex version are always perfectly aligned.
  - Enforces conventional commits, yielding high-quality, auto-generated changelogs.
  - Highly idiomatic in mature JS/Rust/Go ecosystems, and increasingly the gold standard for Elixir OSS.
* **Cons:** 
  - Requires giving GitHub Actions write access to the repository and a powerful Hex API key.
  - CI failures post-merge (e.g., a Hex network blip) require a manual "recovery lane".
* **Tradeoffs:** Prioritizes consistency and automation over absolute manual control. The human gate is shifted left (approving the PR) rather than right (typing `mix hex.publish`).

### Approach B: Manual Tagging & CI Publish
The maintainer manually creates and pushes a git tag (e.g., `v1.0.0`), which triggers CI to publish.
* **Pros:** Retains manual control over exactly when the tag is pushed. No need for `release-please` bot.
* **Cons:** Changelog maintenance becomes a manual, error-prone chore. Easy to forget to update `mix.exs` versions, leading to tag vs. code mismatches.
* **Tradeoffs:** Sacrifices DX and changelog accuracy for a perceived sense of control.

### Approach C: Manual Local Publish (Anti-pattern)
The maintainer runs `mix hex.publish` from their local machine.
* **Pros:** Requires no CI setup or secret management in GitHub.
* **Cons:** "Works on my machine" syndrome. Local dirty states, untracked files, or mismatched Elixir/Erlang versions can taint the published artifact. 
* **Tradeoffs:** Violates the "publish gates inside trusted environments" directive.

## 3. Lessons Learned from Ecosystems

### What to Emulate (The Good)
* **Phoenix / Ecto:** Excellent guide-driven documentation. Their Hex pages are pristine because they enforce strict `ex_doc` rules. Crosswake must ensure `guides/` are properly linked and that the README doesn't drift.
* **Rust (Cargo) / `release-plz`:** The Rust ecosystem excels at hermetic publishes. They verify the build and docs *before* publishing. We emulate this by ensuring our CI runs `mix docs` and `mix hex.build` on all PRs.
* **Developer Ergonomics:** The release PR generated by `release-please` serves as an excellent communication tool for the team. It is a highly ergonomic way to see *exactly* what is going out.

### What to Avoid (The Footguns)
* **JS (NPM) / Python (PyPI):** Accidental inclusion of sensitive files (e.g., `.env`) or massive `test/` directories. 
  * *Fix:* The `mix.exs` `:package` definition must use a strict whitelist for the `:files` option (e.g., `files: ~w(lib priv mix.exs README* LICENSE* CHANGELOG*)`).
* **Broken Internal Links in Docs:** `ex_doc` is strict. A broken markdown link might not fail a local build silently, but it looks terrible on HexDocs.
  * *Fix:* Ensure `docs` is run in a strict mode in CI (`MIX_ENV=docs mix docs --warnings-as-errors`).
* **OTP Name Collisions:** Attempting to publish and finding out `crosswake` is already taken, or worse, having internal modules that aren't properly namespaced (e.g., defining a generic `Config` module instead of `Crosswake.Config`), which causes compilation conflicts for adopters.
  * *Fix:* Ensure all modules are strictly under the `Crosswake.*` namespace.

## 4. First Publish Specific Footguns

The first publish is uniquely dangerous because the package does not yet exist on Hex.pm.

1. **API Key Scope:** To publish a brand-new package, your Hex API key must have permissions to create packages. A package-scoped key won't work yet because the package doesn't exist. 
   * *Mitigation:* Generate an account-scoped key with `api:write` permissions for the initial publish. After v0.1.0 is published, revoke it and issue a package-scoped key (`api:write:crosswake`) for maximum security.
2. **Missing Metadata:** A rejected publish due to missing `:description`, `:licenses`, or `:links` in `mix.exs`.
   * *Mitigation:* Visually verify the `package/0` and `project/0` functions in `mix.exs` before merging the release PR.
3. **Docs Rendering Failure:** HexDocs runs its own generation. If your `mix.exs` specifies an older version of `ex_doc` or has missing assets in `priv/`, HexDocs will fail to generate, leaving a dead link on Hex.pm.
   * *Mitigation:* Run `mix hex.build` locally and inspect the tarball contents before the final merge.

## 5. Foolproof Instructions for Human-Gated Steps

Follow these exact steps to execute the Phase 31 publish securely.

### Step 1: Flip `default_workflow_permissions = write`
`release-please` requires permission to push commits (updating `CHANGELOG.md` and `mix.exs`) and create tags.
1. Navigate to your repository on GitHub.
2. Go to **Settings** > **Actions** > **General**.
3. Scroll down to **Workflow permissions**.
4. Select **Read and write permissions**.
5. Ensure **"Allow GitHub Actions to create and approve pull requests"** is checked (if applicable for your org rules).
6. Click **Save**.

### Step 2: Generate and Install `HEX_API_KEY`
You need to provide GitHub Actions with a Hex API key to authenticate the publish.
1. Open your local terminal.
2. Run the following command to generate a key (requires you to be logged into Hex locally via `mix hex.user auth`):
   ```bash
   mix hex.user key generate crosswake-ci-key --permission "api:write"
   ```
3. Copy the generated API key (it will only be shown once).
4. Navigate to GitHub **Settings** > **Secrets and variables** > **Actions**.
5. Click **New repository secret**.
6. Name: `HEX_API_KEY`
7. Secret: Paste the key you copied.
8. Click **Add secret**.

*(Note: Once the package is created, it is a security best practice to revoke this key and generate a new one scoped strictly to the package: `mix hex.user key generate crosswake-ci-scoped --permission "api:write:crosswake"`, then update the GitHub secret).*

### Step 3: Merge the `release-please` PR
The `release-please` action should have already opened a pull request (e.g., `chore: release 0.1.0`).
1. Navigate to the **Pull Requests** tab in GitHub.
2. Open the `release-please` PR.
3. **Verify:** Check the "Files changed" tab. Ensure `CHANGELOG.md` looks correct and `mix.exs` shows the correct new version.
4. **Merge:** Click "Squash and merge" or "Merge pull request" (depending on repo settings).
5. **Monitor:** Navigate to the **Actions** tab. You should see a new workflow run triggered by the tag creation. Watch it execute the `mix hex.publish --yes` step.
6. **Verify Publish:** Visit `https://hex.pm/packages/crosswake` to confirm the package and docs are live.

## 6. Alignment with Crosswake Vision

By formalizing this automated release gate, we adhere strictly to the Crosswake Elixir OSS DNA:
* **"Proof lanes are part of the product"**: The release lane acts as the ultimate proof that the package is structurally sound.
* **"Release truth matters"**: Adopters will see a pristine, automated changelog and exact version matching between GitHub and Hex, building immediate trust. 
* **"Principle of Least Surprise"**: Adopters get a predictable, standard OSS experience, while the maintainer gets a frictionless, zero-touch deployment model after the PR is approved.

By following this document, Phase 31 will execute smoothly, securely, and idiomatically.
