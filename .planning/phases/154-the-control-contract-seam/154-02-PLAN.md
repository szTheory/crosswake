<objective>
Close CTRL-05 by making a control's rebuild cost and interaction class structurally undeniable
and then surfacing them everywhere an adopter looks: the doctor, the capability chooser guide,
the support matrix, and the changelog.

CTRL-05 is ~85% already wired (D-49). Exactly one leg is genuinely missing — doctor has no
capability-level rebuild finding at all — and two correctness holes need closing before the
enforcement can be tightened. This plan does the tightening in the order D-51 requires:
harden the tolerant construction path FIRST, then enforce, because enforcing first turns a
tolerant path into a crash.

`:interaction` lands here rather than in Phase 156 (D-55) so it shares one migration with the
`:rebuild` enforce-keys fix and the CTRL-05 surfacing pass. Deferring would mean two
`manifest_schema_version` bumps in one milestone, two fixture regenerations, two renderer
passes, and a PROOF-04 edit — in a project whose brand is compatibility honesty.

Purpose: CTRL-05 says every control declares its rebuild class. D-52 is the honest line —
`@enforce_keys` is the only part of this requirement that earns "structurally impossible";
everything else is CI-caught. This plan says which is which rather than overclaiming (D-45's
same discipline applied to CTRL-05).

Output: a `Capability` struct that cannot be built without a rebuild and interaction class, 15
catalog entries that declare both, a doctor rebuild finding, a rebuild column in the capability
map, and an additive `manifest_schema_version` bump with its fixtures regenerated.
</objective>

**Two open questions this plan closes explicitly, so execution does not re-open them:**

1. RESEARCH.md Open Question 1 — should the compatibility construction path default
   `:interaction` or raise? **Decision: default it to `:fire_and_forget`.** Rationale checked
   against D-54's honesty framing: `:fire_and_forget` is the LEAST-CLAIMING of the three values,
   so a default can never overclaim; and raising there would make an adopter's legacy or
   out-of-catalog capability id crash manifest generation instead of degrading. `:rebuild` takes
   the opposite default — fail-closed `:native_required` per D-51's stated intent — because for
   rebuild, the conservative value is the *most* demanding one.

2. RESEARCH.md Assumptions Log A1 — D-51's literal claim that `compatibility_capability_attrs(nil, id)`
   builds `rebuild: nil` does NOT reproduce. A live `mix run` probe shows it yields `:none` today,
   because `new_capability/1` tolerantly defaults it. **Frame the work as hardening a tolerant
   default, not fixing an observed crash.** The `CaseClauseError` in `RebuildPolicy.classify/2` is
   real but unreachable via this path today; the fix is cheap, correct, and prevents it from ever
   becoming reachable.

**Verified blast radius this plan must be sized for (RESEARCH.md §2, Pitfall 5):** adding
`:rebuild` to `@enforce_keys` is a no-op because Elixir's `@enforce_keys` checks key *presence*,
not value, and `new_capability/1` always supplies the key. Adding `:interaction` WILL raise
`ArgumentError` at all ~17 `new_capability/1` call sites — 15 catalog entries plus both
`compatibility_capability_attrs/2` branches — unless they are all updated in the same change.
Task 1 is therefore one atomic task, not a struct edit plus follow-on fixes.
