## Task 2 — Make the registration checker assert uniqueness

`script/check_required_checks_registered.sh` currently verifies that each discovered
`merge-blocking` job is present in branch protection. It never verifies that a name maps to exactly
one job — which is why three collisions survived.

Add a uniqueness assertion that fails loudly, naming both colliding files and the shared name. Match
the existing `[crosswake] FAIL: <id> - <detail>` microcopy shape used elsewhere in the repo.

Add a **negative control** to `test/crosswake/proof/phase153_1_gate_integrity_test.exs` proving the
assertion is not vacuous: construct a fixture with two jobs sharing a name and assert the script
exits non-zero. A uniqueness check that cannot fail is not a check.

### Also fix the racy green-check in `register_required_checks.sh`

Observed live on 2026-07-28 while registering `merge-blocking-ios-mirror-parity`: the script
reported

```
[crosswake] SKIP (no green run on main yet — register after it passes once): merge-blocking commerce support proof (hermetic)
```

for four lanes that **are** green on `main` and **are** already registered.

Root cause: `script/register_required_checks.sh:73` queries
`repos/<repo>/commits/main/check-runs` — the **tip commit only** — and keeps names whose conclusion
is `success`. At that moment the tip was `b26225d4` with its runs still in progress, so every lane
that had not yet finished on that one commit looked ungreen.

It was harmless this time because all four were already-registered contexts that carried through
unchanged. It is **not** harmless in the general case: a genuinely new lane that happens to be
discovered during this window is silently skipped and stays advisory, with no failure and no
retry — the same failure shape as the three holes this plan already closes (something looks fine
while a gate is not actually in force).

Fix: look back over the last N commits on the branch rather than the tip alone, and treat a lane as
green if it has succeeded on any of them. Keep the SKIP message, but make it distinguish
*never seen green* from *still running on the tip* — those warrant different operator responses.

## Task 3 — Give `:requires_example_host` a real CI lane

Today: 8 workflows pass `--exclude requires_example_host`; **no** lane passes `--only`;
`test/test_helper.exs` does not exclude it locally. Net effect — 20 test files run on laptops only.

Create `.github/workflows/requires-example-host-gate.yml`:
- builds `examples/phoenix_host` deps first (these tests need the example host compiled),
- runs `mix test --only requires_example_host`,
- runs **serially** (`--max-cases 1`). These tests are known order-dependent; the seed documents
  leaked `Application.put_env(:crosswake, :companions, …)` and `example_host.ex` replacing rather
  than merging repo config. Fixing that leakage is `FLAKE-*` and out of scope here — running
  serially is the correct scoping compromise, and it must be **commented in the workflow** as a
  deliberate stopgap with a pointer to SEED-007 `FLAKE-*`, not left to look like a preference.
- carries `timeout-minutes`,
- job name contains `merge-blocking` so it is auto-discovered.

Then add `:requires_example_host` to the default exclude in `test/test_helper.exs` so a bare
`mix test` means the same thing locally as in CI.

**Expect this lane to be red on first run.** That is the point — it is currently the only thing
that would have caught #89. If it is red, capture exactly what fails. Fix only what is a genuine
product defect; anything that is test-environment leakage gets captured against SEED-007 `FLAKE-*`
and the specific test tagged, with the tag justified in the summary. Do **not** make the lane green
by weakening what it asserts.
