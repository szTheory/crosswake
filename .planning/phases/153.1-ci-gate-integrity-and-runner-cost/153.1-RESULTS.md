### Read this before quoting the wall-clock number

**The 34.9 → 7.1 min figure measured on #93 is real but confounded.** macOS mean
queue fell 1,071 s → 31 s per job between the two samples, and nothing in this
phase makes a macOS runner start faster — that is ambient GitHub availability.
The baseline landed in a bad macOS window; the after run landed in a good one.

What is genuinely attributable, by lever:

| Lever | Attributable effect | Confounded? |
|---|---|---|
| RUNNER | billable-equivalent min 550 → 259 (**−53 %**) | No — exec × multiplier, independent of queue |
| RUNNER | 13 jobs permanently off the macOS queue | No — structural |
| RUNNER | the specific 7.1 min wall-clock | **Yes** — treat as best case |
| CACHE | see measurement run below | — |

The durable claim for RUNNER is not "the pipeline got 5× faster." It is that
wall-clock became **robust to macOS queue spikes**. Under baseline-grade
contention the 7 remaining macOS jobs would contribute ~7,500 s of queue rather
than the previous 20 jobs' ~21,400 s.

**Also note:** `main` pushes run ~25 jobs where a PR runs ~65 (most proof
workflows are `push: branches: [main]` only). Numbers from a `main` push are NOT
comparable to the PR-derived baseline — quoting them as a win would be a category
error.

## Cache measurement (CACHE Task 4)

Caches are **branch-scoped**: only `main` writes entries other refs can read, so
hit rate is meaningless until the first post-merge `main` run has populated them.
That run is `cfc25005`.

**Repo cache inventory after population:** 129 entries, **1.90 GiB of the 10 GiB
cap (19.0 %)**. No eviction pressure — the per-workflow+job scoping decision
(below) is affordable.

Entries readable by PRs (`refs/heads/main`, Elixir): **33**.
Typical sizes: `build-*` 4.1 MiB, `deps-*` 1.6 MiB per lane.

**Largest consumer is not Elixir.** The SPM cache is ~1,000 MiB — **54 % of all
cache usage** — held as ten near-identical copies of the same 100 MiB `.build`
directory across ten refs. Branch-scoped caches duplicate per ref by design, so
this is not a defect, but it is where the 10 GiB cap will bite first. Recorded
for SEED-007; not acted on here.

entry. Both lanes install a companion package (chimeway / sigra) mid-job. Cause
not yet established — recorded rather than guessed at.

## Why cache keys are scoped per workflow+job

The plan specified `os|arch|otp|elixir|MIX_ENV|hash(mix.lock)`. That is necessary
but **not sufficient**, and the missing dimension is a correctness hazard the plan
did not anticipate.

Several lanes are hermetic **absence** proofs — `phase43` proves rulestead is not
loaded, `phase45` the same for rindle — while other lanes install exactly those
optional deps. Under a repo-wide shared key, a dep-*present* lane could populate a
`_build` that a dep-*absent* lane then restores, so a fail-closed proof would be
evaluating a tree containing the very thing it claims is missing. The proof would
still report green.

Keys therefore carry a scope segment (`workflow-job`). The cost is entry count
against the 10 GiB cap, measured above at 19 % — affordable.

## GATE (153.1-01)

Three gate-integrity holes closed; branch protection went 23 → **27 required
contexts**, 26 of them auto-discovered merge-blocking lanes.

- **Duplicate check names.** Three names were each emitted by two different jobs.
  Branch protection matches by *string*, so GitHub could not tell them apart and a
  red run could be masked by a green one — the gate failed open while reporting as
  fully registered. Renamed the later-phase emitter in each pair (never the
  registered one), so protection stayed continuously valid: three contexts added,
  zero de-registered, no unprotected window.
- **Uniqueness is now asserted**, not just presence, via
  `list_merge_blocking_checks.py --emitters` consumed by
  `check_required_checks_registered.sh`. The assertion runs *before* the
  branch-protection read so it stays meaningful in CI, where no repo-admin token
  exists and the registration half exits `3 UNVERIFIED`.
- **`:requires_example_host` got a real CI lane.** These tests were excluded by
  every CI lane but included by a bare local `mix test`, so a red gate could sit on
  `main` unnoticed.

### The bug the new test caught on its first CI run

Both gate scripts used `mapfile`, which is bash 4.0+. macOS ships bash 3.2.57
(frozen at the last GPLv2 release), so on all four macOS lanes the scripts died
with `mapfile: command not found` and **exit 127 — before checking anything**.

A gate script that cannot run is indistinguishable from a gate that passes.

It went unnoticed because the audit workflow runs on ubuntu, and a maintainer's
PATH resolves `bash` to Homebrew 5.x — only `/bin/bash` is 3.2. Fixed with
portable read loops in both scripts plus a regression guard, verified under real
`/bin/bash` 3.2.57.

## RUNNER (153.1-02)

22 macOS jobs audited per-job, following every `run:` into its scripts
transitively. **9 need a macOS host, 13 do not.** All 13 moved.

`phase68`'s emulator lane was booting an `arch: x86_64` AVD on an arm64 macos-15
runner — full CPU emulation. On ubuntu it gets KVM. Verified by reading the log,
not the checkmark (the lane is `continue-on-error: true`, so green proves nothing):
`Boot completed in 39477 ms` / `Emulator booted.`, whole job ~75 s.

47 jobs across 16 workflows also gained a `timeout-minutes`; they had been
inheriting GitHub's 360-minute default.

### Two false positives from the audit tool

Both would have turned a working merge-blocking proof red. Both were caught by
hand-verifying tool output against the workflow files — which is precisely why
the plan forbids verdict-by-grep.

1. **`phase79`** — the script-reference regex missed the leading `./` in
   `run: ./script/verify_generated_ios_shell.sh`. That script hard-requires
   `xcodebuild`.
2. **`android-generated-shell-unit`** — a different failure mode entirely: no
   Apple *toolchain*, but a macOS *host* assumption. The verify script downloads a
   JDK from adoptium `.../ga/mac/$(arch)/...` and falls back to Homebrew. The
   pre-existing `# REVIEW FIX finding 2` comment on that line was correct.

**Generalisation for SEED-007:** "needs macOS" has at least two independent
causes. An audit that greps only for `xcodebuild`/`swift` finds the first and
silently misses the second.

## CACHE (153.1-03)

Five `_build` caches were keyed on nothing but a lock hash — no os, arch, OTP or
Elixir dimension. The toolchain comes from `.tool-versions`, so an OTP bump would
silently restore BEAM files built by a different compiler. **A green CI run is not
evidence a cache is safe**, which is why this survived.

Two further findings not in the plan:

- `offline-sync-e2e-gate` guard-02 cached `_build/prod` and then opened its only
  run step with `rm -rf _build/prod`. It downloaded a cache and deleted it.
  Removed rather than re-keyed — the guard is only meaningful against a clean prod
  compile, so the correct cache here is none.
- The SPM cache was keyed on a `Package.swift` hash with no platform dimension, on
  a directory of compiled object files. Found by the new guard test on its first
  run.

The Gradle cache pointed at the *project-local* `.gradle` (build state) rather
than `~/.gradle/caches` (downloaded deps), so it stored almost nothing. Replaced
with `gradle/actions/setup-gradle`.

`actions/cache@v3` appears nowhere — dependabot #51 (`b26225d4`) had already
handled it, so that plan bullet was stale.

## Left on the table — deliberately

### 1. The double compile (largest remaining single win)

Every adopted lane compiles **twice**: `mix compile --warnings-as-errors` in dev,
then `mix test` in test. Caching covers `test` (the larger half); the dev compile
stays cold.

Pinning `MIX_ENV=test` on the compile step would remove a full redundant compile
per lane across ~19 lanes. Not done here: it changes which `Mix.env()` the
warnings-as-errors check runs under, across 11 merge-blocking gates, in a codebase
that generates code conditionally. That earns its own change with its own
verification rather than being smuggled into a caching commit.

### 2. Release-path cache keys

`release-please.yml` and `hex-publish.yml` keys carry no OTP/Elixir dimension, so
an OTP bump can restore a stale `_build` into a **publish** job. Scoped out by the
plan as security-sensitive. Recorded in the guard test's exemption comment, which
asserts the exemption list exactly so it cannot quietly grow.

### 3. `CONSOL-*` is untouched

SEED-007's aspiration of ~25,500 → ~2,000–3,000 runner-seconds per push assumes
workflow consolidation, which was explicitly out of scope. 39 workflow files are
still 39 workflow files, and ~40 copies of the setup block became 19 uses of one
composite action — a start, not the consolidation.

### 4. Minor

- `phase10-proof` still runs `actions/setup-java` although none of its three
  scripts invoke Java or Gradle.
- `phase71` / `phase73` missing `build-*` cache entries (above).
- SPM cache duplication across refs (above).
