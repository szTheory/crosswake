  <context>
`PhysicalIphoneContract` is a closed, ordered, versioned vocabulary: `validate_report/1` rejects any
assertion id outside it, and `join_reports/3` requires the supplied report to equal the full expected
set exactly. Adding `PI-BRIDGE-HAPTIC-IMPACT` therefore changes what every conforming report must
contain — it is an intentional breaking addition, which is why SEED-014 asks for a `@schema_version`
bump alongside it (2 to 3, per the seed's own staleness note; re-derive the current value before
acting).

Why this is a decision and not an implementation detail: the vocabulary ships in the `crosswake`
package, and Phase 175 publishes `0.2.2`. Once published, an adopter whose report producer emits the
old set gets a hard `PI-ASSERTIONS-COMPLETE` rejection. That makes the change effectively **one-way**
at the point of publish, which is why this checkpoint sits in front of it rather than after it.

The adopter already built a host-owned three-layer haptics evidence gate outside the vocabulary, so
the gap currently costs them two gates and two records for one device session — it is a real cost,
not a hypothetical one. FID-01 is explicit that either outcome satisfies the requirement, provided
the chosen one is recorded.
  </context>

    - A failure where no validated report was produced — a missing or unreadable device report, a missing backend report, a bad envelope, a command-options error, a preflight block, a host-callback or cleanup failure — exits 2.
    - A blocked readiness result continues to exit 2, because readiness reports a precondition, not a refuted assertion.
    - A fully passing run continues to exit 0.
    - A rule id that the classifier does not recognise exits 2, the conservative status, and does so through an explicit catch-all rather than by falling off the end of a case.

  <action>
Introduce an explicit, named classifier in the task module — `exit_status_for/1` — that maps a rule
id to a process exit status, and route every `System.halt` call in `run/1` through it. The
classification rule is: the `join_reports/3` outcome rule (the one that fires when a validated,
complete, correctly-owned, correctly-ordered report contains a non-passing outcome) maps to **1**;
every other rule id maps to **2**; an unrecognised rule id maps to **2** through an explicit
catch-all clause.

Write the classifier as a `case` over the known rule ids with a catch-all, not as a negative filter:
the reason the catch-all is conservative rather than permissive is that a rule added later without a
classification decision must degrade to "could not run", never to "found a defect" — a false
"ran and found a defect" is the more expensive of the two mistakes for an operator triaging a red
run.

Make the emitted JSON carry the classification too, so a consumer reading stdout does not have to
infer it from the process status. Name the field explicitly and record its name in the SUMMARY.

Write the tests first, one per behavior above, driving `run_with/2` and the classifier directly
rather than spawning a process where possible; where the exit status itself must be observed, use
the pattern the existing test file already uses for `System.halt`. Five behaviors, five separately
named tests — one shared "it failed" assertion would leave the distinction CW-REQ-B is about
unproven, which is the whole defect.

Update the documented exit-status contract wherever this task's statuses are written down, and add
the CW-REQ-B section to `174-FID-01-DISPOSITION.md` plus a dated disposition line in SEED-014's
