version and would silently report a stale coordinate for any other release.

and a clean-room validator scoped to structural completeness only.
</objective>

<architectural_decision>
## D-171-B: `linked-release-status.json` gains a `version` key; `schema_version` becomes `"1.1.0"`

171-RESEARCH.md left this open. Resolving it explicitly, because deferring it is not actually
available:

`Workflow.validate!/1` re-derives its result by calling `rollup!/1` with fields taken from `result`,
then requires `rebuilt == result` exactly. If `rollup!/1` gains a required `:version` input but the
persisted result carries no version, `validate!/1` has nothing to pass and the round-trip cannot be
reconstructed. Likewise `validate!/1`'s `exact_map?` key list is exact — adding `version` to the
output map without adding it to that list makes every validation raise.

**Decision:** `rollup!/1` accepts `:version` AND emits `version` in its output map; `validate!/1`'s
exact-key list gains `version` and threads `result.version` into the rebuild; `schema_version` moves
from `"1.0.0"` to `"1.1.0"` because a consumer-visible key was added.

**Rating: `costly`.** The persisted artifact `linked-release-status.json` is uploaded as a CI
artifact and read by downstream tooling; widening its schema is additive but consumer-visible.
Additive-only (no key removed, no type changed), so an older reader that ignores unknown keys is
unaffected. The alternative — deriving the version by parsing it back out of `successful_coordinates`
— was rejected: it produces no version at all in the `BLOCKED` state, where `successful_coordinates`
is `[]`, so the fact would vanish exactly when a human most needs it.
</architectural_decision>
