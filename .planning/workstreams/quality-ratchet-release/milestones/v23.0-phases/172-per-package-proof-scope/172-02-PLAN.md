  <behavior>
    - Baseline (observed ref equals approved ref, digests equal): reason is `nil`, exactly as today.
    - Drifted, digests equal: reason is `"reachable_and_compatible"`.
    - Drifted, digests differ: reason is `"unproven"`.
    - Not drifted, digests differ: reason is the existing digest-mismatch diagnostic, unchanged. This is the SC#3 regression anchor.
    - A package absent from the registry still reports the registry-missing reason, even though its observed ref is nil — the missing branch still precedes every drift branch.
    - A package with a failing status, a non-registry source, a non-zero path-lock count or a source root outside the public root still reports its existing reason, never a drift reason — drift is never allowed to mask a harder failure.
    - An observed ref that is present but malformed (wrong length, uppercase, or non-hex) on a package that has otherwise passed the status and source predicates raises `ArgumentError`.
  </behavior>
  <action>
**1a. Validate the observed ref late, not early (XPUB-03).** At the top of the drift region of
`public_artifact_reason/3` — that is, after the registry-missing, status, source, path-lock and
source-root clauses have all failed to match, so the artifact is known to be a real, well-formed
registry artifact — resolve the observed ref through the `ref!/1` validator added by 172-01. Doing
this inside the classifier rather than in `validate_public_artifacts!/3` is what keeps the
registry-missing branch reachable for a package with a nil ref (172-01 task 1c).

**1b. Split the existing digest clause, preserving its strength verbatim (SC#3, XPUB-02).** The
current clause tests metadata-digest inequality OR payload-digest inequality. Rewrite the region so
that clause survives with its two comparisons textually identical, guarded by the additional
conjunct that the observed ref equals the approved ref. Do NOT change either comparison operator, do
not introduce any tolerance, normalization, case-folding or prefix comparison, and do not reorder
the two digest fields. The only permitted change to that clause is the added ref-equality conjunct.

**1c. Add the two drift branches, before the fallthrough.** `cond` short-circuits and today's final
fallthrough is what means "fully proven", so both new branches must intercept before it:
  - observed ref differs from approved ref AND both digests are equal -> `"reachable_and_compatible"`;
  - observed ref differs from approved ref -> `"unproven"`.
Order matters: the compatible branch must precede the unproven branch, so a drifted package whose
bytes still match is not swept into the weaker label. Each branch must name its concrete condition
explicitly; neither may be written as a catch-all `true ->` clause, which would make it fire for
reasons nobody enumerated.

**1d. Do not touch the fallthrough.** The final clause returning `nil` stays exactly as it is. After
this task `nil` means: real registry artifact, correct source root, no path locks, digests
byte-identical to the approved digests, AND the observed ref equals the ref those digests were
approved at. That is strictly stronger than what `nil` meant before, which is the correct direction
for a phase that must not loosen rigor.

**1e. Tests.** Write these before the implementation and watch each fail. Build every case from the
baseline `public_fixture/0` with a single targeted mutation via `update_approved_artifact/3` or
`update_public_artifact/3`, so exactly one variable moves per test:
  - drift-only (change one named package's observed ref, leave both digests untouched) -> assert that
    package's reason is `"reachable_and_compatible"` AND, in the same assertion block, that its
    metadata and payload digests are still equal to the approved ones, so the test proves the branch
    fired for the right reason rather than merely firing;
  - drift plus digest change -> `"unproven"`;
  - digest change with no drift -> the existing digest-mismatch reason (the SC#3 regression anchor —
    name it in the test description so a future reader cannot mistake it for an ordinary case).
    Write this as TWO cases, one per digest field: a `payload_digest` change and a `metadata_digest`
    change, each on its own with the other field left equal to the approved value. The OR-clause has
    two halves and the existing suite only ever exercises the payload half
    (`cleanroom_test.exs:195-199`), so a single combined case would leave the metadata half
    unproven while appearing to cover the clause;
  - registry-missing package, unchanged -> the existing registry-missing reason;
  - each of the harder pre-drift failures (bad status, non-registry source, path lock, bad source
    root) combined WITH a drifted ref -> still reports its own existing reason, never a drift reason;
  - malformed observed ref on an otherwise-healthy package -> raises `ArgumentError`.
  </action>

    - A run where all six packages are fully proven returns the existing completion state and an empty attested list, with every pre-existing assertion in the suite unchanged.
    - A run where one package is `reachable_and_compatible` and the other five are fully proven returns the new attested state, names that one package in `attested_packages`, and does not name it in `succeeded_packages`.
    - A run with one blocked package and one attested package returns the blocked state — a real defect outranks an attestation.
    - A run with a registry-missing package returns the existing partial state regardless of any attestation, preserving that branch's empty-installs invariant.
    - `package_claims` always has exactly six entries, one per package, in the canonical package order, each with a non-empty claim string.
    - Every entry of `package_claims` whose claim is the fully-proven claim corresponds to a package present in `succeeded_packages`, and vice versa — the two surfaces cannot disagree.
  </behavior>
  <action>
**2a. Add the bucket (D-172-A).** In `evaluate_public!/1`, add an `attested` filter beside the
existing blocked / missing / succeeded filters, selecting children whose reason is the
reachable-and-compatible string. Then narrow the `blocked` filter so it excludes that reason as well
as the two it already excludes — otherwise an attested package would be counted twice and would
force the blocked state, silently discarding the distinction this phase exists to create.

**2b. Add the state (D-172-A).** Insert a new clause into the state `cond` AFTER the blocked, missing
and live-status clauses and BEFORE the final fully-proven clause, producing the attested state and
calling the same complete-proof validation the fully-proven clause calls. This ordering is
load-bearing: a real defect, a missing package or a failing live status must each still outrank an
attestation, so an attested state is only ever reported for a run that is otherwise completely clean.

**2c. Add the claim vocabulary (D-172-C).** Add a private `public_artifact_claim/1` that maps a
reason to a claim: the nil reason to the fully-proven claim string, the reachable-and-compatible
reason to itself, and every other reason to the unproven claim string. Write it as a `case` with an
explicit clause per known input plus a final catch-all, so a reason string added later cannot slip
through unnamed. Call it in `validate_public_artifacts!/3` and carry `claim` on each normalized
child alongside `reason`.

**2d. Surface the six outcomes without averaging (SC#4).** Add two keys to the result map:
`attested_packages`, the package names from the attested bucket in canonical order; and
`package_claims`, one entry per child in canonical order carrying the package and its claim. Do NOT
remove or redefine any existing result key. In particular `succeeded_packages` keeps meaning
fully-proven-only and `package_count` keeps counting that same set — an attested package is not
counted as a proven one.

**2e. Tests.** Write them first. Cover each behavior above, building each case from the baseline
fixture with the single targeted mutation from Task 1. Add one test asserting the
`package_claims` / `succeeded_packages` cross-consistency property stated in the behavior list, and
one asserting `package_claims` has six entries with no empty claim string — a length-and-content
assertion, never a bare truthiness check on the list.
  </action>

    - `package_claims` has exactly six entries in canonical package order in every exact-public result the suite produces, including the blocked, partial and attested cases.

| Boundary | Description |
|----------|-------------|
| Published tarball digests -> `public_artifact_reason/3` | The only place byte-exactness is decided; any weakening here is a supply-chain integrity failure, not a test failure |

| `Cleanroom` result document -> `verify_companion_cleanroom.sh` terminal assertion | The last gate before the lane reports success |
