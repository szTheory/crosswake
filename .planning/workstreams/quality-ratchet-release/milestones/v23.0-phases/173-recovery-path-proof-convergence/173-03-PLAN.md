**2a. `script/append_release_ledger.sh`.** Take the package, version, approved head, published ref,
lane name, run id and the proof outcome, validate them with the same strict patterns the emitter
uses, and append exactly one line of JSON to `docs/release-ledger/RELEASE-LEDGER.jsonl`. Append-only:
the script never rewrites or reorders existing lines, so the file's history is the record. Make it
idempotent on the triple plus run id — a rerun of the same run must not add a second line — and say
so in a comment, because a rerun is the normal recovery motion in this pipeline.

The outcome field records failure as faithfully as success. A ledger that only records passes cannot
distinguish "the proof failed" from "the proof never ran", and the whole point of this milestone is
that those two must never look the same on disk.

**2b. Write the ledger from the proof workflow, and land it through a pull request.** Add a closing
step to the reusable proof workflow that always runs, captures the proof outcome, invokes the ledger
script, and opens a pull request carrying the new line — following `release-as-cleanup` step for
step, including the bot identity, the run-scoped branch name and the already-open-pull-request guard
that exists because duplicate cleanup pull requests once accumulated. The default branch is
protected; a direct push is not available and must not be attempted.

The ledger step must not be able to fail the proof. Its own failure must still be visible — record
that outcome in the step summary rather than swallowing it, so a ledger that quietly stops being
written is noticed.

**2c. Seed the ledger with a real run.** Backfill at least one entry for a release that actually
happened, with its real package, version, approved head, published ref and run id taken from the
recorded run, not invented. Note in the file's header comment that entries before a stated run id
were backfilled and from what source, so a reader can tell a backfilled line from a live-written one.
An undistinguishable backfill would let the ledger claim coverage it does not have.

**2d. Do not raise retention as the mechanism.** This repository is public, so the artifact retention
ceiling is far below this project's horizon and no retention value satisfies the criterion. The
existing retention setting on the proof artifact stays as it is — it remains a useful fast-path
signal and is not the durable copy of record. No task in this phase tunes it.
  </action>
