## Tests

### 1. Exact-public clean-room proof against the live-published 0.2.1 family

expected: All five companion profiles install twice from exact registry sources
(zero path locks), pass non-vacuous registration/Doctor checks, match the
approved normalized digests, and end in a live-status COMPLETE.

result: [blocked] — see TODO-012

**How to run.** Per `docs/COMPANION-PUBLISH-RUNBOOK.md` step 4, but in
`exact-public` mode rather than `candidate-local`:

```
bash script/verify_companion_cleanroom.sh \
  --source-mode exact-public \
  --approved-manifest <approved artifacts.json> \
  --result <new-result.json>
```

The approved manifest is the `artifacts.json` from the candidate receipt run.
`exact-public` fetches the approved six package digests from the public
sources; cached, repository-local, or merely configured coordinates cannot
satisfy it.

**Why this is human.** Real-network, stateful, long-running: it resolves live
Hex/SwiftPM/Maven and generates real Phoenix hosts. The repository carries only
fixture-backed unit coverage for this mode
(`test/crosswake/release_candidate/cleanroom_test.exs --only post_publication`),
not a captured live run.

**Why it has never run, which is the part worth understanding.** The
`exact-public-proof` job exists and is wired (`release-please.yml:718`), and the
rollup is fail-closed — `Workflow.rollup!/1` treats `skipped` as not-success, so
a proof that does not run yields `PARTIAL`, never `COMPLETE`. But the job
`needs:` the ordinary `publish-*` jobs, and 0.2.1 published through exact-ref
**recovery**. Those jobs never ran, so the proof was skipped. The release that
took the unusual path is precisely the one that went unproven.

This is recorded as the second half of `SEED-017`: ordinary and recovery
publication should converge on the same post-publication proof. Running this
test by hand closes the item for 0.2.1; SEED-017 closes it for every release
after.

**STILL BLOCKED — new reason as of 2026-09-16T00:10Z. See TODO-012.**

they are. That contradiction is the blocker, and it needs a design decision
recorded in `TODO-012` — not another publish.

## Disposition (2026-09-16)

**This item is handed off, not abandoned.** It stays `blocked` and is carried
into the next milestone rather than being run, waived, or marked passed.

The reason is that the test as specified cannot be made to pass by running it.
`TODO-012` establishes that `verify_companion_cleanroom.sh:206` requires a single
`candidate_ref` covering all six packages while `docs/COMPANION-PUBLISH-RUNBOOK.md:16-18`
and D-15/D-16 require companions to be independently versioned. Those two
requirements are mutually exclusive. No amount of execution resolves that; a
recorded design decision does.

Phase 168's own goal — 0.2.1 release candidate readiness — is met: `crosswake 0.2.1`
is live on Hex, SwiftPM and Maven, and all six Hex packages resolve. What remains
unproven is the *post-publication proof lane*, which three findings now show has
never executed at any release:

| Finding | What it establishes |
|---|---|
| `TODO-009` / `SEED-017` | The release graph is welded to `0.2.1`; any other version tags and publishes nothing. Interim CI tripwire landed. |
| `TODO-011` | The companion clean-room lane has failed at every release inspected (three releases, three distinct causes). |
| `TODO-012` | The exact-public proof is structurally unsatisfiable under the documented companion design. |

Those are one coherent body of work, not three checkboxes, and they belong in a
scoped phase with a discuss step — not in an improvised closeout.

**This item is not evidence that 0.2.1 is unsound.** It is evidence that the
repository cannot currently *demonstrate* soundness after publication. Do not
promote it to a supported claim in either direction.
