## Anchor slug rule

The link counter uses the GitHub heading-slug rule: lowercase, drop every character that is not a
letter, digit, space, hyphen or underscore, turn spaces into hyphens, suffix duplicates `-1`,
`-2` in document order, strip backticks and emphasis markers first.

ExDoc ids differ in places. Compared against `doc/*.html` generated by ExDoc 0.40.3:

| Heading | GitHub rule | ExDoc id | Same |
|---|---|---|---|
| `Journey 1: a route becomes shared runtime truth` | `journey-1-a-route-becomes-shared-runtime-truth` | `journey-1-a-route-becomes-shared-runtime-truth` | yes |
| `Capabilities (Parity-Locked)` | `capabilities-parity-locked` | `capabilities-parity-locked` | yes |
| `` `push/3` — the only entry point `` | `push3--the-only-entry-point` | `push-3-the-only-entry-point` | no |
| `5. Reconcile in Phoenix/Ecto` | `5-reconcile-in-phoenixecto` | `5-reconcile-in-phoenix-ecto` | no |

ExDoc turns punctuation such as `/` and the em dash into a hyphen and collapses runs, where the
GitHub rule deletes them. A heading with such punctuation therefore has two different anchors
depending on whether a reader is on GitHub or on HexDocs. The counter checks the GitHub rule
(the README and guides are read on GitHub); the baseline has `broken=0` under that rule.
Observed at baseline: existing links such as `#attach-first--push3-raises-on-a-socket-that-never-did`
and `#boundary-warnings--rough-edges` use the GitHub form with a doubled hyphen, so they resolve
on GitHub but not against the ExDoc ids on HexDocs. The counter does not flag this; it is
recorded here, not fixed (counted only this cycle). Prefer headings without such punctuation
when a link must work on both surfaces.
