## D-171-C: `Crosswake.ReleaseCandidate.Coordinate` is parameterized, not deleted

**Finding (verified, 171-RESEARCH.md Orchestrator Addendum):** `grep -rn "Coordinate" lib script test`
across the whole tracked tree returns, outside the module's own file, only
`test/crosswake/release_candidate/coordinate_test.exs`. The other hits are unrelated English prose in
`lib/crosswake/doctor/publish_readiness.ex` and a differently-named concept in
`test/fixtures/proof/phase52_publish_readiness.json`. The module exposes exactly one public function,
`validate!/1`. **No production caller exists.**

**Three dispositions were available:** delete the module; parameterize its five comparisons; leave it
with a recorded note.

**Decision: parameterize.** Rationale:
- Leaving it welded is the exact hazard 171-RESEARCH.md's Pitfall 3 names — a dormant validator that
  reactivates the defect the moment a future phase wires it back in, inside a module everyone believes
  was already fixed by this phase.
- Deleting it is a defensible change but it is NOT what WELD-01..08 asked for, and bundling a
  dead-code deletion inside a repair PR hides the deletion from review. Deletion stays available as
  its own future change, argued on its own merits.

**Inventory consequence:** in the WELD-01 inventory (plan 171-05), `coordinate.ex`'s five occurrences
are recorded under their own row type — `orphaned validator (no production caller; test-only)` — NOT
flattened into `live gate`. Recording them as live gates would misstate what the grep found.

**Rating: `reversible`.** Parameterizing a module nothing calls changes no production behavior.
</architectural_decision>
