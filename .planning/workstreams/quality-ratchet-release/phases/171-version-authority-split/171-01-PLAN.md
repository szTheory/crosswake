<architectural_decision>
## D-171-A: `approved_version` is a peer field of the identity receipt — and here is why that is safe

**Question raised by an assumption-delta scan:** `approved_head` / `approved_tree` / `merge_tree` are
content-addressed identity facts about a commit. A version is a *declared* fact read out of a file. If
`approved_version` becomes a fifth peer output on the same job, every downstream consumer that treats
`needs.approved-release-guard.outputs.*` as interchangeable identity evidence now treats a declared
string as though it were content-addressed.

**Decision: model it as a peer output.** Rating: `costly` (reversible, but four `if:` clauses, one
Elixir env-var contract and one persisted schema would have to be unwound together).

**Why it is defensible here, and only here:** `approved_version` is derived strictly from
`.release-please-manifest.json` content **at the approved head**, inside the same guard step that
already verifies tree-identity for that exact commit. The guard has already established, before the
derivation runs, that the checked-out tree IS the approved tree. A declared fact read out of a tree
whose identity is already content-addressed inherits that binding — it is not a free-floating string.

**What this decision forbids (carry into every later plan):**
1. `approved_version` is computed in exactly ONE place: the guard step. No consumer re-derives it.
   No job re-greps `mix.exs`. Any `lib/` module needing the approved version receives it as an
   explicit input or env var.
2. `approved_version` must never be derived from an attacker-influenceable surface — not a PR title,
   not a branch name, not a `workflow_dispatch` input, not a commit message.
3. The head/tree/base identity gate stays EXACT (WELD-08). This plan changes only the
   version-consistency pre-check at the top of the guard step. Every predicate below it is untouched.
</architectural_decision>
