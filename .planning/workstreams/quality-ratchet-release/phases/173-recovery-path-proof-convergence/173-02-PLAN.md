  <action>
**1a. Add one more path override.** Give the checker an `EXACT_PUBLIC_PROOF_WORKFLOW_PATH` override
with the real file as its default, through the existing `path_from_env/2` helper, alongside the
overrides the checker already exposes. Read it, strip full-line comments from it, and pass it to the
new predicates. This is what lets a fixture stand in for the reusable workflow without a live run.

**1b. Declare the lane roster as a constant.** Add a module attribute listing the two lane job
identities this phase converges: the ordinary caller in the release workflow and the recovery caller
in the recovery workflow. Every new predicate iterates that attribute.

The roster must NOT be computed by scanning the workflow files for jobs that happen to reference the
emitter or the reusable workflow. A roster derived from the artifact it polices silently drops a
non-compliant lane out of scope and reports green — that is the defect recorded as SEED-019, and it
is exactly the shape a "which lanes emit a record" scan would take. Write a short comment at the
attribute saying so, so a later reader does not helpfully replace the constant with a scan.

**1c. `release.recovery.publication_record_identical`.** For every lane in the roster, require that
the lane's publish job invokes the shared emitter script, that both invocations pass the same flag
names in the same order, and that both upload under the same artifact-name template with the
error-on-missing setting. Then require that both proof callers reference the same reusable workflow
path, compared as equal strings rather than each matched against a pattern — two callers that each
match a permissive pattern can still name different files.

Require, for every lane in the roster, that the caller job declares a job-level `permissions:` block
granting `actions: read`. Both workflow files declare a top-level `permissions:` key, so every scope
they do not list is none, and a called workflow's own permissions narrow the caller's token rather
than widening it — a caller that drops the grant makes the shared body's artifact reads fail with a
forbidden response at release time, and no linter decides it. This is the one property in the
identity check that is about authorization rather than shape, so state that in the check's detail
string.

Assert on the flag names, on the reusable workflow path, and on the permission grant, not merely on
the presence of the script name somewhere in the block. An assertion that the right script is mentioned, while the argument it
is called with goes unread, is the column-scope defect recorded as SEED-020: a real non-empty subject
examined in the wrong place.

**1d. `release.recovery.proof_record_fails_closed`.** Over the reusable proof workflow: require the
job's own condition to be the always-runs form; require the record-assertion step to be present and
to carry no failure-swallowing construct; require that the values compared against the record come
from the workflow's declared inputs. Also require the file declares no secrets-inheritance key —
the privilege constraint 173-01 established should be held by a check, not by memory.

**1e. Keep the roster honest.** Add both new IDs to `@roster_ids`. The existing roster-exactness
check compares the emitted ID set against that attribute in both directions, so a check that stops
being emitted is caught; adding the IDs is what puts the new checks under that protection.
  </action>

**2a. Extend the harness, do not duplicate it.** Add a fixture key for the reusable proof workflow
mapping to the `EXACT_PUBLIC_PROOF_WORKFLOW_PATH` name introduced in Task 1, and reuse the existing
temp-file-plus-env pattern so a fixture set can override the release workflow, the recovery workflow
and the reusable proof workflow together. Seven of these overrides are already exercised by the
phase-142 module; this is the eighth, in the same shape.

**2b. Build each fixture by mutating the real file, never by hand-writing a minimal one.** Start
from the real workflow text and apply one targeted removal or substitution, using a helper that
raises when the pattern it means to remove is absent. A hand-written minimal fixture drifts away
from the real graph silently and then proves nothing about it; a mutation that no-ops because the
workflow moved on must fail loudly at the mutation site, which is precisely what the existing
raise-on-no-op guard is for. Reuse that guard rather than writing a looser one.

**2c. The paired-fixture test that carries the criterion.** Write one test that runs BOTH fixture
sets in the same test body: the recovery-lane removal and an unmutated control. Assert the mutated
set fails with the named check ID AND that the control set passes. A red-only assertion cannot tell
a check that is genuinely sensitive from one that fails on every input; the pairing is what makes the
distinction between the two graphs a measured fact.

**2d. Cover the ordinary half symmetrically.** Repeat for the ordinary lane. Both halves must have
their own removal fixture — a single fixture covering "some lane" would let one lane regress while
the check stayed green, which is the whole failure mode this phase exists to close.

**2e. The different-paths fixture.** Include the case where both lanes still write records and both
still call a reusable workflow, but the two callers name different files. This is the case a
presence-only check passes and an identity check catches, and it is the most likely real-world drift.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Workflow YAML text -> checker predicates | The checker reads job blocks as text; a predicate can pass while the behavior it names is absent from the real runtime graph |
| Declared lane roster -> per-lane assertions | If the roster empties or shrinks, every per-lane assertion silently stops running |
| Fixture text -> mutation helper | A mutation that no-ops leaves the checker running against an unmutated input, so the negative control proves nothing |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-173-06 | Tampering | The lane roster silently shrinking to exclude a non-compliant lane | high | mitigate | Task 1b declares the roster as a constant with a comment forbidding a derived scan, and Task 2's second recorded mutation replaces it with a scan and observes the recovery test go red. |
| T-173-07 | Tampering | A presence-only assertion passing while the two callers name different files | high | mitigate | Task 1c compares the two `uses:` values as equal strings and Task 2e carries a fixture where both lanes emit records but call different files. |
| T-173-08 | Repudiation | A negative control that is red on every input, proving nothing | medium | mitigate | Task 2c requires a mutated-red and control-green pair asserted in the same test body. |
| T-173-09 | Denial of Service | A fixture mutation that no-ops after the real workflow drifts | medium | mitigate | Task 2b mandates reuse of the existing raise-on-no-op mutation helper, which fails at the mutation site rather than downstream. |
| T-173-16 | Denial of Service | A caller silently losing its `actions: read` grant, surfacing only during a real release | high | mitigate | Task 1c requires the grant per lane in the roster, and Task 2's behavior block carries a fixture that removes it from one caller and expects the check red. |
| T-173-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable to this plan — it adds no package-manager install step. |
