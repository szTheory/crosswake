**1b. `script/assert_publication_record.sh` — the record-presence decision.**

and what was found, and what the operator should do next, following the two-line
`FAIL:` plus `What to do next:` convention already used in the recovery ref validation step.

recorded as SEED-020 — the assertion would run against a real non-empty subject and prove nothing

fails rather than falling through to the absent branch: "we could not read it" and "it was not
there" must not produce the same result token, because they call for different operator actions.

This script must contain no fallback that converts a failure into success — no `|| true`, no
default-on-error branch, no exit code swallowed by a pipeline.

**2b. Order the steps so the record decision cannot be skipped.** The job's own `if:` is
`always()`. The applicability question and the record question are two different steps, in this
order:

- First, an applicability step using the two-tier pattern `approved-release-guard` already uses: a
  legitimate not-applicable outcome writes a marker and exits zero; every other condition is a bare
  assertion under `set -euo pipefail`. Only the genuinely-not-a-linked-release case may take the
  zero-exit branch.
- Second, download the publication record with the same `gh run download --name` plus artifact-count

  expected values from the artifact being verified is the scope-selector defect recorded as
  SEED-019, and it would make a record with the wrong version verify itself.

Then the existing proof body, moved verbatim: the checkout at the merge oid, the BEAM setup, the
approved-candidate manifest download, `bash script/verify_companion_cleanroom.sh --source-mode

a move, not an upgrade.

**2c. Replace the job in `release-please.yml` with a call.** The `exact-public-proof` job keeps its

steps used to read from `needs.*`. It drops only `runs-on`, `timeout-minutes` and `steps`, which move

Keeping `permissions:` on the caller is load-bearing, not cosmetic. `release-please.yml` declares a
top-level `permissions:` key, so every scope it does not list — `actions` among them — is none at
workflow level; `actions: read` exists today only as a job-level grant on this job and on
`approved-release-guard`. A called workflow's own `permissions:` can only narrow the token the caller
hands it, never widen it, so declaring `actions: read` inside the reusable workflow does not grant
it. Drop the caller's block and both the candidate-receipt download and the new
publication-record download fail with a forbidden response — at release time, on a real release,
which is the failure class this phase exists to eliminate. `actionlint` does not catch it.

`linked-release-rollup` keeps
reading `needs.exact-public-proof.result`; a caller job reports an aggregate result exactly like any
other job, so that edge is unchanged and must be left alone.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Publish job -> publication-record artifact | The record is produced by the job whose success it attests; nothing outside the run vouches for it |
| Publication-record artifact -> proof workflow | The proof decides pass/fail partly on a field set it downloads; a forged or stale record crosses here |
| `workflow_dispatch` inputs -> recovery proof caller | Recovery inputs are operator-supplied and reach the shared proof body as call inputs |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-173-01 | Spoofing | A replayed or forged publication record used to pass the proof without a real publish | high | mitigate | Task 2b binds the assertion's expected triple to the calling job's own trusted inputs — the approved head, version and merge oid already authenticated by `approved-release-guard` or by the recovery ref validation step — and never to values read out of the record. |
| T-173-02 | Elevation of Privilege | The new reusable workflow inheriting secrets it does not need | high | mitigate | Task 2a declares no `secrets:` key at all and keeps `actions: read` / `contents: read`. The proof body reads only the ambient job token. |
| T-173-03 | Tampering | Two drifting copies of the proof body, one per lane | high | mitigate | Task 3c requires a character-identical `uses:` value from both callers and Task 3's acceptance measures the occurrence count of the proof invocation across both workflow files. |
| T-173-04 | Repudiation | A record-assertion failure silently downgraded by a fallback | high | mitigate | Task 1b forbids any failure-swallowing construct in the assertion script and Task 1c proves the missing-record branch exits non-zero by a recorded mutation of that branch. |
| T-173-05 | Information Disclosure | Widening the recovery surface to native lanes while framing the change as Hex-only | medium | mitigate | Task 3c leaves `recover-android-core` byte-unchanged and records the reason in a comment; acceptance asserts the diff does not touch it. |
| T-173-15 | Denial of Service | A caller job dropping its `actions: read` grant, so the shared body's artifact reads are forbidden at release time | high | mitigate | Tasks 2c and 3c require an explicit job-level `permissions:` block on both callers, and Task 2's acceptance adds an assertion that every caller declares `actions: read`. Both workflow files declare a top-level `permissions:` key, so the scope is none unless granted per job, and the linter cannot decide this. |
| T-173-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable to this plan — it adds no package-manager install step. If any task later requires one, a package-legitimacy gate plus a blocking human checkpoint is required first. |
</threat_model>
