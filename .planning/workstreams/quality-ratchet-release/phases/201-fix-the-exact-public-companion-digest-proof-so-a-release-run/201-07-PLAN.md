## Standing approvals (who acts, how it is recorded)

The user's standing release approvals (user decisions 2026-11-05 and 2026-11-09) cover merging the green release PR,
the release-tags step, and the Hex, Maven and iOS mirror publishes. They are committed on `main` in AGENTS.md and
BEARINGS invariant 4 by PR 284, which Plan 02 merged. Task 1's first action re-checks this. If PR 284 is not merged,
or the text on `main` does not authorize these steps, the plan writes `201-07-BLOCKED.md` and stops before any
irreversible step. The Maven fire-drill dispatch (Plan 05) and remote-branch deletion keep their own one-use `allow`.

The plan agent performs each step itself, with no checkpoint raised. Each step still requires a PASS `precheck:` line
written at most 600 s before it, then exactly one record line, in `gates-201.txt`:

`standing: <id> at=<YYYY-MM-DDTHH:MM:SSZ> basis=standing-release-approvals-2026-11-09 scope="<what this one step does>" result=<merged|tags_created|published|failed> [merge_commit=<40hex>] <binding>`

The ids are `core-merge` (binding `head=<40hex>`), `core-tags`, `core-hex`, `core-maven` and `core-ios` (binding
`run=<release run id>`). Precheck lines use the field lists of 200-06, 200-07 and 200-08, with 0.2.14 values. The
`core-merge` and `core-hex` prechecks also carry `hex_latest=<version>` (W4), placed immediately before the
closing binding field (`head=` or `run=`). Environment approvals use
`gh api -X POST repos/szTheory/crosswake/actions/runs/<run>/pending_deployments` with one `environment_ids[]`,
`state=approved` and comment `201 <id> standing`. A failed or uncertain step is read and reconciled first, then
recorded, and the plan stops with 201-07-BLOCKED.md; nothing is re-run or re-approved. Tell the user in chat, in one
line each, what was approved and when; the standing approval does not make the step silent.
