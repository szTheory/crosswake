### 1. Exact-public clean-room proof against the live-published 0.2.1 family

expected: All five companion profiles install twice from exact registry sources
(zero path locks), pass non-vacuous registration/Doctor checks, match the
approved normalized digests, and end in a live-status COMPLETE.

result: [blocked] — see TODO-010

**How to run.** Per `docs/COMPANION-PUBLISH-RUNBOOK.md` step 4, but in
`exact-public` mode rather than `candidate-local`:

```
bash script/verify_companion_cleanroom.sh \
  --source-mode exact-public \
  --approved-manifest <approved artifacts.json> \
  --result <new-result.json>
```

The approved manifest is the `artifacts.json` from the candidate receipt run.
`exact-public` fetches the approved six package digests from the public
sources; cached, repository-local, or merely configured coordinates cannot
satisfy it.

**Why this is human.** Real-network, stateful, long-running: it resolves live
Hex/SwiftPM/Maven and generates real Phoenix hosts. The repository carries only
fixture-backed unit coverage for this mode
(`test/crosswake/release_candidate/cleanroom_test.exs --only post_publication`),
not a captured live run.

**Why it has never run, which is the part worth understanding.** The
`exact-public-proof` job exists and is wired (`release-please.yml:718`), and the
rollup is fail-closed — `Workflow.rollup!/1` treats `skipped` as not-success, so
a proof that does not run yields `PARTIAL`, never `COMPLETE`. But the job
`needs:` the ordinary `publish-*` jobs, and 0.2.1 published through exact-ref
**recovery**. Those jobs never ran, so the proof was skipped. The release that
took the unusual path is precisely the one that went unproven.

This is recorded as the second half of `SEED-017`: ordinary and recovery
publication should converge on the same post-publication proof. Running this
test by hand closes the item for 0.2.1; SEED-017 closes it for every release
after.

**BLOCKED as of 2026-09-15 — do not attempt this run yet.**

This test cannot pass today, and the reason is definite rather than flaky.
`verify_companion_cleanroom.sh:209` fetches a hardcoded family of six packages
and fails closed if any one is missing (`:248-263`, `state: PARTIAL`, `exit 1`)
*before* running a single profile. `crosswake_rindle` returns **404** from
hex.pm — it has never been published at any version.

Every other member matches its declared version exactly (crosswake 0.2.1,
rulestead 0.1.0, sigra 0.1.3, chimeway 0.1.0, threadline 0.1.0), so this is one
missing package, not broad drift.

Unblocking it requires a decision recorded in `TODO-010`: either publish
`crosswake_rindle 0.1.0` (a one-way door under D-19), or correct the expected
family to five if rindle is not actually a shipped companion. Do not unblock it
by making the harness tolerate a missing package — failing closed on partial
registry availability is what surfaced this.

**Superseded caveat.** `mix crosswake.release.status --live` currently
reports a WARNING that `crosswake_rindle@0.1.0` is absent from Hex (a bootstrap
pin still set). That is out of scope per D-15/D-16 and is expected — do not read
it as a failure of this test.
