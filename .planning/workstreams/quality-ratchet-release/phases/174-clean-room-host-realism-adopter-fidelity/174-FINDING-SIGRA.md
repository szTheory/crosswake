**Line 21 is exactly the failing test's definition line**, and line 22 is its body:
`refute Sigra.enabled?(%{})`. At `d3e914da`, `crosswake_sigra` was NOT yet routed into the
`crosswake_chimeway`-only branch that asserts `enabled?(%{})` defaults to `true` — it fell through
to the generic "default companion" branch, which assumes every no-engine companion defaults
`enabled?(%{})` to `false` and asserts that with `refute`. `crosswake_sigra`'s actual behavior is
`enabled?(%{}) == true` by default (a notification/auth-adjacent companion, same default-enabled
posture as chimeway) — so the generated `refute Sigra.enabled?(%{})` assertion fails against the
real package every time, independent of which sigra version is under test.

## Named root cause

**Harness-side, and it is a *different* defect from threadline's.** The harness's own no-engine
smoke-test template hard-coded a package-unaware default (`refute enabled?(%{})`) for every
companion except the one it had special-cased (`crosswake_chimeway`), and `crosswake_sigra` was
never added to that special case at the time it needed to be. This is a template-selection bug in
`verify_companion_cleanroom.sh`, not a `manifest_contract`/routing failure — the two companions'
failures share no code path: threadline's ran through Step 4/Step 7 (the router-then-doctor
sequence); sigra's ran through Step 5 (the no-engine smoke-test branch selection), entirely before
Step 4's router is even exercised meaningfully for this purpose.

**The fix, found and dated in git history, not assumed:** commit `d16e475a` ("fix(doctor): load
freshly compiled host routers (#120)", 2026-08-09 20:27:34 EDT — the same calendar day as the
failing run) changed the branch condition from:

```diff
-elif [ "$PACKAGE" = "crosswake_chimeway" ]; then
+elif [ "$PACKAGE" = "crosswake_chimeway" ] || [ "$PACKAGE" = "crosswake_sigra" ]; then
```

and updated the branch's own header comment from `"all other no-engine companions (e.g. sigra):
refute enabled?(%{})"` to `"crosswake_chimeway and crosswake_sigra: assert enabled?(%{}) — both
default enabled"`. That is the exact mechanism: sigra was moved out of the default-refute branch
and into the assert-true branch, matching Sigra's real behavior. This phase's own run is the
confirming evidence that the fix holds against the live published package today — Step 5's
`enabled?/1 defaults to true when no :enabled key is supplied` assertion (now at line 22 of the
current template, shown passing at 4/4 in `evidence/174-sigra-run.log`) is the direct descendant
of the line-21 test this diff repaired.

## Harness-side vs. package-side

**Harness-side.** `crosswake_sigra 0.1.3` resolved from Hex, compiled clean, and its real
`enabled?/1` behavior was correct throughout — the harness's assumption about that behavior was
wrong, not the package.

## Independence from the threadline finding

This root cause (a package-unaware boolean-default template branch, fixed in `d16e475a` months
before this phase began) shares no code, no commit, and no mechanism with threadline's
manifest_contract/routeless-router root cause (fixed in this phase's own plan 174-01, commit
`d04397a4`). The two findings are not restatements of one defect under two names.
