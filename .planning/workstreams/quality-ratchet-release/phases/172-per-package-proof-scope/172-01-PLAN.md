<architectural_decisions>
## D-172-A: a package reporting the weaker claim gets a DISTINCT third aggregate bucket, not the `blocked` bucket

**Question (left open by the pattern map):** when `public_artifact_reason/3` reports the new weaker
claim, does that package fold into `evaluate_public!/1`'s existing `blocked` bucket — the safe
default under `Enum.filter(children, &(&1.reason not in [nil, "registry_missing"]))` — or get a
distinct third top-level bucket?

**Decision: a distinct third bucket.** `evaluate_public!/1` gains an `attested` bucket and the
aggregate `state` gains a fourth value, `"ATTESTED"`. Implemented in 172-02; recorded here because
172-01's schema shape is chosen to serve it.

**Rationale.**

1. *Folding into `blocked` re-creates `TODO-012`.* `blocked` means "a defect was found." A package
   whose bytes match its approved digests but whose provenance ref has moved is not a defect — it is
   a true, weaker fact. Labelling it a defect makes the exact-public lane report BLOCKED with no way
   to distinguish "the published tarball does not match" from "the repository has moved on," which
   is the structurally-unsatisfiable-proof problem this milestone exists to remove.
2. *It does not weaken the gate.* `script/verify_companion_cleanroom.sh`'s terminal assertion
   compares the result state against the string `COMPLETE` and is NOT modified by this phase. An
   `ATTESTED` run therefore still fails the lane exactly as a `BLOCKED` run does. Rigor is
   identical; only legibility changes. This is the SC#3 discipline applied to the aggregate.
3. *It is the only shape that satisfies SC#4's "never silently averaged."* A fourth state value plus
   the `attested_packages` and `package_claims` result keys mean six distinct package outcomes
   survive into the result document instead of being reduced to one verdict.

**Rejected alternative:** reuse `"PARTIAL"`. Rejected because `"PARTIAL"` already has a precise,
different meaning in this module (`registry_missing` — packages not present in the registry at all,
with installs and profile results required to be empty). Overloading it would make two unlike
conditions indistinguishable to the shell.

Reversibility: `costly` — recorded as `<reversibility>` on the 172-02 task that implements it.

## D-172-B: drift is `observed ref != that package's own approved ref`; no `acceptable_refs` set is introduced

The pattern map sketched the drift predicate as `artifact.candidate_ref not in
expected.acceptable_refs`. A plural set is NOT adopted. The approved manifest carries exactly one
ref per package and nothing in the tree produces a set of acceptable refs, so an `acceptable_refs`
field would be a collection with a single element forever — an aggregate whose non-emptiness
nothing asserts.

**Decision:** the comparison is scalar and per package:
`public_artifacts[i].candidate_ref` (the ref OBSERVED by the exact-public lane) vs
`approved_artifacts[i].candidate_ref` (the ref that package was approved at).

**Where the observed ref comes from, and why it is not circular.** The exact-public lane must not
stamp the re-fetched artifacts with the approved ref it is about to compare them against — that
would make the comparison true by construction, a Shape-A vacuity. Task 2 therefore resolves the
observed ref independently, once, from the repository the proof is running against
(`git -C "$MATRIX_REPO_ROOT" rev-parse HEAD`), and passes THAT per package. In an ordinary release
run the exact-public proof executes at the approved head, so observed == approved for every package
and all six are fully proven. Drift appears exactly when the proof re-runs after the repository has
moved past a package's own publish-time ref — which is XPUB-03's condition, stated literally.

Reversibility: `reversible` — one shell variable and one scalar predicate.

## D-172-C: `claim` is a derived, total, positively-named field; `reason` keeps the precise cause

`nil`-means-proven is an absence. This milestone's governing rule is that absence must never be
scored as success. 172-02 therefore adds a per-package `claim` string derived totally from `reason`
(`nil` -> `"byte_exact"`, `"reachable_and_compatible"` -> `"reachable_and_compatible"`, every other
reason -> `"unproven"`) and surfaces `package_claims` in the result. `reason` is unchanged in
meaning and keeps the specific diagnostic (`"digest_mismatch"`, `"path_lock_present"`, and the
rest).

Reversibility: `reversible` — an added derived field with no upstream producer.

## D-172-D (scope boundary, recorded so absence is not read as success)

`hex_artifacts.sh` still takes a single `--ref` for a whole candidate run and stamps it onto all six
artifacts. That is correct: one candidate-local build IS one ref. What changes is that the ref now
travels as a per-artifact field rather than a run-level scalar, so an approved manifest assembled
from two different candidate runs (independently-versioned companions, D-15/D-16) is now
representable and accepted. **This phase does not add a multi-run approved-manifest assembler.**
The six-independent-refs capability is proven at the schema and evaluator layer by test (SC#1/SC#2),
not by a production producer that emits six different refs today. Do not record "the shell emits one
ref" as a gap; record it as this boundary.
</architectural_decisions>
