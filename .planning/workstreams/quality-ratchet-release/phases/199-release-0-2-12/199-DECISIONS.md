1. Gate ids: nine release gates, `core-maven-drill` (the Maven fire-drill dispatch, D-08 A), `core-merge`, `core-tags`, `core-hex`, `core-maven`, `core-ios`, `companion-merge`, `companion-tags`, `companion-hex`; and one housekeeping gate, `pr258` (D-06: the user's merge, close or leave-open choice for PR 258 in 199-19 Task 3; not a release step). `pr258` follows steps 2, 3, 6, 7 and 8 with two recorded differences: its `precheck:`, `gate:` and `decision:` lines go to `199-EVIDENCE/closeout-199.txt` (beside the `pr258_read:` line its audit reads), not gates-199.txt; its choices are `merge`, `close` or `leave_open` rather than allow or hold, and its applied outcome is recorded as one `pr258: <state> action=<..>` line rather than `applied:`.
2. Before displaying, re-read the live facts the gate depends on (PR head and CI for a merge; run id, job name, pending environment id and target-coordinate absence for a deployment; for the `core-maven-drill` dispatch: PR 236 head still equal to the captured head, the 0.2.12 POM still 404, and no fire-drill run already exists for that head). A drifted fact stops the gate; nothing is displayed on stale facts. Every re-read appends `precheck: <id> at=<UTC> result=<PASS|STALE|...> <facts read>` (the drill line also ends ` head=<40hex>`), and an attempt is displayed only when the most recent precheck line for its id is PASS and less than 10 minutes old.
3. Display in plain language: what this one step does, that it cannot be undone and what undo exists (Hex `mix hex.retire` advisory only; Maven none; the fire drill drops its own Central Portal deployment in the same run, and a missed drop is an incident; mirror tag correctable only for new resolutions; a merge cannot be unmerged), what is already verified, what is unknown, and the run link. No hash for the user to copy.
4. For the nine release gates, append to `199-EVIDENCE/gates-199.txt` (for `pr258`, to closeout-199.txt as step 1 says): `gate: <id> attempt=<n> displayed=<UTC> scope="<one line: version, coordinate, run id, environment>"`, then after the reply `decision: <id> attempt=<n> <allow|hold> at=<UTC>`. For `core-maven-drill`, the gate, decision and applied lines each end with ` head=<40hex>`, the captured candidate head the attempt is bound to. Every gate task's audit checks, in file order for its id: a PASS precheck, then `gate:` for attempt n, then `decision:` for the same attempt n, then exactly one `applied:` for that same attempt n, with exactly one `allow` overall (for the drill: among the lines bound to the current captured head).
5. Only `allow` acts, exactly once, for exactly the displayed scope. A deployment approval passes exactly one environment id with a comment `199 <id> attempt <n>`. A dispatch gate runs exactly one `gh workflow run` with the displayed ref and inputs. After acting append `applied: <id> attempt=<n> at=<UTC> result=<observed>`.
6. `hold` makes no API call and dispatches nothing. A later approval is a new attempt with a new display. Reject a pending deployment only if the user says reject or cancel.
7. An uncertain result (timeout, transport error) is read and reconciled before anything else (for a dispatch: list runs above the recorded prior run id); if the step happened, record it; if it verifiably did not, stop and display a new attempt; never re-issue under a used `allow`. A failed publisher job or fire-drill run is never re-run; recovery needs a new plan.
8. An approval is never standing and never transfers to another gate, attempt, run or head. No decision in this file authorizes any merge, tag, publish or Central Portal write; each happens only after its own displayed gate. Each Central Portal write, the Maven fire drill included, needs its own displayed gate. A new captured head (for example after a stale restart of 199-08) needs a new `core-maven-drill` display and a new `allow`.
