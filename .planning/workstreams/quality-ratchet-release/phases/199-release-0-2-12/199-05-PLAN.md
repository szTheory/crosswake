## Behavior the workflow must have (the executor implements it; no code is prescribed here)

| Job | New key or change | Behavior |
|---|---|---|
| `release-tag-gate` (new) | `environment: release-tags`; `needs: approved-release-guard`; `if` is `needs.approved-release-guard.outputs.rel17_context != ''` with no status-check function (so it also requires the guard's success) | one step that writes the displayed scope (operation `rel17_operation`, package `rel17_package`, version, merge OID, the tags Release Please will create) to the job summary; no `secrets.` reference, no checkout |
| `release-please` | `needs: [approved-release-guard, release-tag-gate]` | `if` begins with `!cancelled()`, then requires `github.event_name == 'push'` and `needs.approved-release-guard.result == 'success'`, and then either (`rel17_context == ''` and `needs.release-tag-gate.result == 'skipped'`) or (`rel17_context != ''` and `needs.release-tag-gate.result == 'success'`); any other combination skips it. The `skip-github-release` expression and every step are unchanged |

Downstream effect, stated so nobody "fixes" it later: GitHub evaluates a job's implicit `success()` over its
whole upstream graph. In a linked or companion run the gate succeeded, so publishers and proofs behave as today.
On a proposal run the gate is skipped, so every downstream job without a status-check function is skipped,
which is the intended proposal outcome (they are skipped by their own conditions anyway); jobs that already use
`always()` or `failure()` (`release-as-cleanup`, both rollups, `release-failure-alert`) are unaffected. 199-07
observes this on a real proposal run.
