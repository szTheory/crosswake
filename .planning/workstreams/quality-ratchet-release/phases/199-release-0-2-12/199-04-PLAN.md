## Behavior the workflow must have (the executor implements it; no code is prescribed here)

| Job | New key or change | Behavior |
|---|---|---|
| `release-tag-gate` (new) | `environment: release-tags`; `needs: approved-release-guard`; runs only when `needs.approved-release-guard.outputs.rel17_context != ''` | one step that writes the displayed scope (operation, package, version, merge OID, tags Release Please will create) to the job summary; no credentials, no checkout needed |
| `release-please` | `needs: [approved-release-guard, release-tag-gate]` | runs on push when the guard succeeded and either the REL-17 context is empty and the gate was skipped, or the context is non-empty and the gate succeeded; any other combination skips it. The `skip-github-release` expression is unchanged |
| `publish-hex` | `environment: publish-hex` | unchanged `if`, steps and needs |
| `publish-android-core` | `environment: publish-maven`; add `publish-hex` to `needs` | its `if` keeps every existing condition and additionally requires `needs.publish-hex.result == 'success'` |
| `publish-ios-core` | `environment: publish-ios-mirror`; add `publish-android-core` to `needs` | its `if` keeps every existing condition and additionally requires `needs.publish-android-core.result == 'success'` |
| `publish-hex-rulestead`, `-rindle`, `-sigra`, `-chimeway`, `-threadline` | `environment: publish-hex` | unchanged otherwise |

Downstream jobs (`clean-room-proof-*`, `exact-public-proof`, both rollups, `release-failure-alert`) keep their
`needs` lists; the scanner checks that already pin them (for example `clean-room-proof-ios` must not need
`publish-android-core` directly) must still pass. A held gate leaves later jobs skipped and the rollups record
the partial state, which is the honest outcome.
