## Where the gate lives (Claude's Discretion, settled at planning time)

A step in the existing macOS job `phase79-ios-proof` of `.github/workflows/crosswake-ci.yml`. The job already
runs on every full-proof run, ran on the 0.2.12 release PR head (PR 236, run 42388086844, 104 s, success) and
already generates the default `--local` project, but only runs `xcodebuild -list`
(`CROSSWAKE_IOS_BUILD_FOR_TESTING=0` makes `script/verify_generated_ios_shell.sh` exit before building), which
is why 0.2.12 passed it. A step, not a job: no new runner start, no duplicated `mix deps.get`, leaf count and
pins unchanged. The CI step uses local mode (the candidate's own Swift package), because on a release PR the
candidate's iOS core is not public yet. The step is blocking through the `Crosswake CI` aggregator once merged;
on main its findings are exactly one, the defect the same PR fixes, so it blocks nothing else.

The no-flag remote form (the clean-room job's form) is rehearsed, not run in CI: its pbxproj pins
`XCRemoteSwiftPackageReference` with `upToNextMajorVersion` and `minimumVersion` equal to the `mix.exs` version
(0.2.12 on origin/main, 0.2.13 on the release PR, measured 2026-11-08), so on the release PR it can only
resolve once the mirror tag exists. Remote mode rewrites only the scratch copy's `minimumVersion` to a version
already on the mirror and builds against that public core. Planning-time measurement on this machine: the
0.2.12 generator's no-flag output with `minimumVersion` set to 0.2.12 failed in 4 s with exit 65 (missing
settings file); the same project with the default settings file resolved `CrosswakeShellCore ... @ 0.2.12` and
built (`BUILD SUCCEEDED`, 8 s). This proves the generated remote form compiles against a public core; it does
not prove the 0.2.13 core, which the post-publish clean-room still proves.

## Script contract

`script/verify_default_ios_generation_build.sh [--source-root DIR | --project-root DIR] [--remote-version X.Y.Z]`,
bash 3.2, `set -euo pipefail`, no pipeline whose status decides a verdict. Work root: `mktemp -d` under
`${RUNNER_TEMP:-${TMPDIR:-/tmp}}`, mode 700, removed by an EXIT trap that touches only it.

- Generate mode (no `--project-root`): run the generator from the source root (default: the script's own repo root; `--source-root DIR` names another crosswake checkout, which must contain a `mix.exs` for app `:crosswake`, else ERROR `bad_source`) with `cd <source> && MIX_ENV=dev mix crosswake.gen.shell ios --target <work>/target`, adding `--local` unless `--remote-version` is given; the project is `<work>/target/native/ios/crosswake_shell` (`project=generated`). Because the generator runs in the source root, a `--local` project's relative `XCLocalSwiftPackageReference` path points at that root's `packages/` and stays valid. Record `generator=<git -C <source> rev-parse HEAD>` and `generator_dirty=<yes|no>` from `git -C <source> status --porcelain -- lib priv` (empty is `no`).
- `--project-root DIR`: only for the no-flag remote form. Copy DIR to `<work>/project` and build the copy (`project=given`, `generator=- generator_dirty=-`); DIR is never modified. A project carrying an `XCLocalSwiftPackageReference` is refused with ERROR `local_copy_unsupported` (copying it would break its relative package path); `--project-root` without `--remote-version` is ERROR `bad_usage`; `--source-root` with `--project-root` is ERROR `bad_usage`.
- Both refuse with ERROR `not_default_path` when `.crosswake/ios_host_generation.json` exists in the project.
- Local mode requires an `XCLocalSwiftPackageReference` (else ERROR `not_local_form`). Remote mode requires exactly one `minimumVersion = <v>;` inside the `XCRemoteSwiftPackageReference` (else ERROR `not_remote_form`), records `<v>` as `remote_from` and rewrites it to X.Y.Z in the work-root copy only.
- Build with `${CROSSWAKE_IOS_XCODEBUILD_BIN:-xcodebuild}` and exactly the clean-room arguments (`-project`, `-scheme CrosswakeShell`, `-sdk iphonesimulator`, `-destination 'generic/platform=iOS Simulator'`, `-derivedDataPath` and `-clonedSourcePackagesDirPath` inside the work root, `CODE_SIGNING_ALLOWED=NO ONLY_ACTIVE_ARCH=YES ARCHS="$(uname -m)" build`), timed in whole seconds. `Could not resolve package dependencies` in the log is ERROR `package_resolution_failed`. A non-zero build is FAIL `build_failed` (control `skipped`).
- Remote mode, after a zero build: read `CrosswakeShellCore: https://github.com/szTheory/crosswake-shell-core-ios.git @ <version>` from the build log as `resolved`. No readable line is ERROR `resolved_unreadable`; a version other than X.Y.Z is FAIL `resolved_version_mismatch`. PASS is never printed in remote mode unless `resolved` was parsed and equals X.Y.Z. In local mode `resolved=-`.
- Negative control, only after the build passed (and, in remote mode, `resolved` matched): copy the project to `<work>/control`, delete `CrosswakeHostSettings.xcconfig` there, build again with its own derived data and the same package dir: non-zero with `Unable to open base configuration reference file` is `detected`; zero is `not_detected` (FAIL `negative_control_passed`); non-zero without that text is `unexpected_error` (FAIL `negative_control_unexpected_error`). PASS needs `control=detected`.
- On FAIL print the last 40 lines of the relevant log to stderr. `first_error` is the first `error:` line with the work root, the project root and the source root replaced by `<work>`, `<project>` and `<source>`, in both the given and the `cd -P` resolved form (macOS shows /tmp and /private/tmp); `none` when there is no error.
- Exactly one verdict line, last on stdout, then exit 0 PASS, 1 FAIL, 2 ERROR:
  `default-ios-build: mode=<local|remote> project=<generated|given> generator=<40hex|-> generator_dirty=<yes|no|-> remote_from=<v|-> remote_min=<X.Y.Z|-> resolved=<version|-> build_rc=<n|-> build_seconds=<n|-> control_rc=<n|-> control=<detected|not_detected|unexpected_error|skipped> verdict=<PASS|FAIL reason=<r>|ERROR reason=<r>> first_error=<text|none>`
