## Gate protocol (Phase 200)

Every Phase 200 gate (`core-maven-drill` here; `core-merge`, `core-tags` in 200-06; `core-hex`, `core-maven` in
200-07; `core-ios` in 200-08) follows 199-DECISIONS.md `## Gate protocol` steps 2, 3, 5, 6, 7 and 8 by reference,
with these Phase 200 rules:

1. Records go to `200-EVIDENCE/gates-200.txt` only, never `gates-199.txt`; attempts number from 1 in this file;
   the deployment approval comment is `200 <id> attempt <n>`. No line names the 0.2.12 candidate head
   `efbc79124e99f5e60f8b85cbad1a507d4763e476`. No Phase 199 `allow`, and nothing in CONTEXT ("Go for it"
   authorizes work up to each gate, not the gates), authorizes any step here.
2. Who acts: a plan agent cannot see the user's replies. The plan agent re-reads the facts, appends the
   display-time `precheck:` line, returns `## CHECKPOINT REACHED` with the display text (the task's `<context>`
   filled with live values, including the run link `https://github.com/szTheory/crosswake/actions/runs/<run id>`
   from the precheck, or "no release run yet" for the merge gate), and stops. The orchestrator displays only on
   that PASS precheck, appends the `gate:` line at display time, waits for the reply, re-reads the same facts and
   appends a reply-time `precheck:` line, appends `decision:`, on `allow` performs exactly the one action once and
   appends `applied:`; on `hold` nothing is called. A continuation of the plan then verifies and writes evidence.
3. Line order per attempt, in this order and no other: display-time PASS precheck, `gate:`, reply-time PASS
   precheck, `decision:`, `applied:` (after the single allow only). The reply-time recheck line is written AFTER
   the `gate:` line; Phase 199's record wrote some rechecks before the gate line, and the Phase 200 checker
   rejects that shape. After `hold`, that attempt number is closed: a later approval needs a new `gate:` line
   with the next attempt number, preceded by a fresh display-time PASS precheck (or the latest PASS precheck
   if it is under 600 s old) and followed by its own reply-time recheck; re-displaying a held attempt number
   or allowing it without a new display fails the checker.
4. Timestamps are `YYYY-MM-DDTHH:MM:SSZ` (UTC, with seconds, valid calendar date and time) on every `at=` and
   `displayed=`. The checker computes: the display is at most 600 s after its display-time precheck and not
   before it; the reply-time recheck's `at=` is no earlier than the gate's `displayed=`, no later than the
   decision's `at=`, and at most 600 s before it. The orchestrator therefore writes the reply-time recheck
   immediately before recording the decision, never at display time.
5. Binding field: `head=<40hex>` for `core-maven-drill` and `core-merge`; `run=<release run id>` for `core-tags`,
   `core-hex`, `core-maven` and `core-ios`. It is the LAST field of every `gate:`, `decision:` and `applied:`
   line (after the quoted `scope="..."` on gate lines) and a field of every `precheck:` line (the plans write it
   last there too). Binding-shaped text inside `scope="..."` is ignored by the checker; keep scope text free of
   `run=`/`head=` tokens anyway. The `core-merge` applied line also carries `merge_commit=<40hex>` before the
   binding.
6. Every gate's order check is `awk -v g=<id> -v k=<binding> [-v m=merge_commit=<40hex>] -f .planning/workstreams/quality-ratchet-release/phases/200-forward-fix-and-release-0-2-13-default-ios-generation-builds/scripts/gate-order-200.awk <gates-200.txt>`
   (exit 0 only for exactly one allow and one applied for that binding, in the order and time windows above).
   Its 53 fixture controls (`scripts/gate-order-controls-200.sh`, planner run 2026-11-08 under /bin/bash 3.2 and
   macOS awk: 53 of 53 as expected) embed the plan checker's 18 iteration-2 fixtures verbatim (among them
   hold then allow without a new display, reply recheck long before the reply, garbage timestamps, scope
   spoofing, comment-prefixed lines, a 2028 leap boundary) plus the planner's cases (over-600 s display,
   minute-only timestamp, other run, empty binding, binding not last, recheck before the gate line, missing,
   STALE, 601 s-old or after-decision recheck, two allows, applied before decision, decision before gate, wrong
   merge commit, invalid calendar dates and times, year boundary, hold then a new attempt, hold then a
   re-displayed held attempt). They run in Task 2 before the first gate.
7. A failed or uncertain step is read and reconciled, never re-run or re-approved under a used `allow`. A
   non-passing post-action verify halts the phase: write `200-NN-BLOCKED.md`, not a SUMMARY.
