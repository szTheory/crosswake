Facts the tests rely on (read at planning time from BridgeChannel.kt `evaluate` and the corpus): order of
gates is protocol and versions (`compatibility_mismatch`), route scope (`inactive_route`), envelope origin
(`origin_denied`), command lookup (`undeclared_capability`), capability string equality
(`undeclared_capability`), route packs from the SESSION (`pack_incompatible`), then per-command capability
and delegate checks (`unavailable_capability`). Corpus `bridge_protocol_version` is `1.1.0`, so request
versions `1` and `1.0` (demand 1.0.0) are satisfied. `correlation_id` is echoed in replies by design; a
privacy sentinel therefore goes in `payload` and `capabilities`, never in `correlation_id`.
