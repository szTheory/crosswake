- D-39: git's stderr is a failure signal (amends D-07 and the D-05/D-23 builder; closes GAP3-CR-01).
  (a) Every git call keeps stderr in a shell variable and fails when it is not empty. The plain form's script is exactly: exec 2>/dev/null 3>&1; err=$("$@" 2>&1 1>&3 3>&-); rc=$?; [ -z "$err" ] || exit 125; exit $rc. The stdin form's script is exactly: in=$1; shift; exec 2>/dev/null 3>&1; err=$("$@" <"$in" 2>&1 1>&3 3>&-); rc=$?; [ -z "$err" ] || exit 125; exit $rc. Inside the substitution git's stderr goes to the variable and its stdout to fd 3, which is the port. The shell's own stderr stays /dev/null. Status 125 matches no accepted status (0 everywhere, 0 or 1 for check-ignore), so the call is :unavailable and clean_tree is {:blocked, :prerequisite_missing}. This is D-07's existing "unavailable" cause. The preflight's existing next action ("make the candidate a readable git work tree") fits, so there is no new cause, clause or wording (D-07, D-14). The text is only tested for emptiness. It is never read, returned, logged or written to a file, because it can carry a path. The candidate path stays an argv element, never script text.
  (b) It applies to all calls, not only the listing calls: pinned, stdin and bare. One rule is simpler to prove than a per-call list. Planning checks: folders of mode 0000, 0111, 0222 and 0311 make status and ls-files --others (with or without --ignored) print "could not open directory", omit the contents and exit 0. Mode 0444 warns about the folder's .gitignore but still lists the file. Mode 0555 lists normally. An unreadable tracked file is reported as modified with no stderr. Real-candidate check: at e4344ca5 with the pins, read-tree, status and the ignored listing all wrote empty stderr (9185 ignored entries listed), so the change does not block the real candidate. 184-14 re-proves this on a full HEAD copy.
  (c) Rejected alternative: a work-tree pre-walk that fails on any folder that cannot be listed. It duplicates git's traversal (symlinks, nested repositories, ignored _build and deps trees) and can disagree with it. Git's own warning names exactly the folders git skipped. Rejected alternative: source_dirty. Git could not look, so the count is unknown, which D-07 calls unavailable. Residual, disclosed: a git that skips entries without any warning is not covered; none was found on 2.41.
- D-40: git-format text is read the way git reads it (amends D-04, D-24 and D-38's attributes note; closes GAP3-CR-02 and GAP3-IN-01).
  (a) info/attributes: strip only leading ASCII space, tab, CR and LF (git's attr.c blank set). A line is inactive only when nothing is left or its first remaining byte is #. Checked: NBSP, vertical tab and form feed before # make check-attr report ident: set; space, tab and CR before # are comments. A UTF-8 BOM before # on the first line is a comment to git but is refused here. That over-refusal is accepted (fail-closed), like D-38's BOM over-count.
  (b) GAP3-IN-01 is fixed, not deferred: info/exclude and info/attributes are split on LF only. The exclude predicate removes the one trailing CR, as git does. A CR CR LF line is the live pattern CR and now counts 1. For attributes, CR is in the blank set, so an LF-only split changes nothing there.
  (c) Audit of every other place that parses git text. The rev-parse outputs (git-path info/attributes, git-path info/exclude, absolute-git-dir, and the rev-parse values read by git/3) lose only one trailing LF instead of being Unicode-trimmed. No test can show this load-bearing (each output ends in a fixed ASCII name or is hex), so it has no mutation control; it is audit consistency. Config values from config --list -z are compared after ASCII downcasing with no trim, and the refusals fail closed: core.bare and extensions.worktreeConfig are refused unless the value is a git false spelling (false, no, off, 0, or empty); core.symlinks is refused unless the value is a git true spelling (valueless, true, yes, on, 1). Checked: git reads core.symlinks=00 and 0k as false, and extensions.worktreeConfig=2 as true; with the latter, a worktree-scoped filter applies but does not appear in the --local listing. The old truthy?/falsy? lists let both through. An unusual spelling of the safe value is now refused, which is accepted. The index, status, ignored-listing and check-ignore parsers already split on NUL and compare bytes; reviewed, no change.
- D-41: pin core.ignorecase=false (closes GAP3-WR-01; amends D-05).
  (a) The shared builder adds -c core.ignorecase=false to every pinned call. A command-line -c beats every config file (as in D-34).
  (b) Refusing core.ignorecase=true was rejected. Git sets it itself on every case-insensitive filesystem, and the real candidate's .git/config has core.ignorecase=true, so a refusal would refuse every macOS candidate.
  (c) Pinning false only adds findings. Checked on APFS: with a committed deps/ rule, an untracked DEPS/x.ex is hidden under true and reported as ?? under false. A case-only rename of a tracked file shows nothing under true and an untracked entry under false. A clean tree stays clean. The real candidate's ignored listing is byte-identical under both settings and its status is empty.
  (d) core.precomposeUnicode is not pinned. Git honours it only on macOS, whose filesystems treat the composed and decomposed forms as one name, so it cannot stretch a rule to a different file. The round-3 review's NFC/NFD checks found no wrong trust.
