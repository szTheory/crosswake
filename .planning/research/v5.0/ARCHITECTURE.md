# Architecture Patterns

**Domain:** Mobile SDK Architecture & Dependency Management
**Researched:** 2026-06-03

## Recommended Architecture

**Binary Core + Hosted Glue**

The core logic of Crosswake (Manifest Resolution, Route Activation, Bridge Enforcement) is packaged as a pre-compiled binary library (AAR/SPM). The host application provides a thin "Glue" layer (generated by `mix crosswake.gen.shell`) that configures the library and observes its state.

### Component Boundaries

| Component | Responsibility | Communicates With |
|-----------|---------------|-------------------|
| `crosswake-shell-core` (Library) | Route policy enforcement, manifest parsing, bridge command validation, capability checking. | The Host App (via APIs), the bounded WebView (via JS). |
| Host App (Generated Glue) | App lifecycle (AppDelegate/MainActivity), UI rendering (SwiftUI/Compose), custom capability implementations (e.g., custom File Picker). | `crosswake-shell-core` (via Delegate/StateFlow), Elixir Backend (via LiveView). |
| Elixir Backend (Phoenix) | Ultimate source of truth for routing, permissions, and manifest data. | Host App (via Manifest), WebView (via LiveView). |

### Data Flow

1. **Boot:** Host App calls `CrosswakeShell.initialize(manifest)`.
2. **Activation:** Host App passes an intent/URL to the core library: `shell.activate(url)`.
3. **Resolution:** Core library resolves the route against the manifest and checks capabilities.
4. **State Update:** Core library updates its reactive state (e.g., `StateFlow<ShellPresentation>`).
5. **Render:** Host App observes the state change and renders the appropriate UI (e.g., `LiveViewSession`, `Denied`).
6. **Bridge:** WebView sends a bridge command. Core library intercepts, validates, and either handles it internally or delegates to the Host App via the `CrosswakeShellDelegate`.

## Patterns to Follow

### Pattern 1: Reactive State Exposure
**What:** Exposing the internal state of the shell via modern reactive streams.
**When:** For any state that the host UI needs to render (booting, active route, required packs).
**Example (Android):**
```kotlin
// Inside Library
class CrosswakeShell {
    private val _presentation = MutableStateFlow<ShellPresentation>(ShellPresentation.Booting)
    val presentation: StateFlow<ShellPresentation> = _presentation.asStateFlow()
}

// Inside Host App
lifecycleScope.launch {
    shell.presentation.collect { state ->
        when (state) {
            is ShellPresentation.LiveView -> renderWebView(state.session)
            // ...
        }
    }
}
```

### Pattern 2: Inversion of Control via Narrow Delegates
**What:** Defining narrow, specific interfaces for host-provided capabilities.
**When:** When the core library needs to execute a side-effect that is highly platform or app-specific (e.g., triggering a custom haptic pattern or opening a custom file picker).
**Example (Swift):**
```swift
public protocol CrosswakeHapticsDelegate {
    func performHaptic(style: String)
}

// Library configures it
public struct CrosswakeConfig {
    public var hapticsDelegate: CrosswakeHapticsDelegate?
}
```

## Anti-Patterns to Avoid

### Anti-Pattern 1: The Massive Callback Interface
**What:** Creating a single `CrosswakeSDKCallback` interface with 20 methods that the host *must* implement.
**Why bad:** Forces boilerplate. Users must implement methods they don't care about, leading to empty function blocks. Violates Interface Segregation Principle.
**Instead:** Use specific, optional delegates (e.g., `HapticsDelegate`, `FilePickerDelegate`) or allow lambda injection during configuration.

### Anti-Pattern 2: Over-Generation
**What:** Generating the entire `ActivationCoordinator` logic into the host app.
**Why bad:** Creates the "eject trap". Adopters modify the generated code, making future updates to the routing logic impossible without manual merging.
**Instead:** Package the core logic in a binary library. Only generate the thin host glue.
