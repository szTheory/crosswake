# v25 Proof Convergence Challenge

**Scope:** Resolve material evidence, isolation, and acceptance conflicts across `GENERATION.md`, `TWIN-ARCHITECTURE.md`, `DX.md`, and `PROOF-OPERATIONS.md`.

## Decisions

**Keep one narrow twin receipt, but make it a derived record, not a new runtime authority.** Reusing the physical-iPhone evidence schema is incompatible: that closed contract requires `physical_iphone` and a complete passing physical roster, while its report join collapses non-passes. Reusing the navigation advisory also loses per-scenario ownership and provenance. The twin therefore needs a small versioned receipt to retain its fixed scenario outcomes and fidelity limits. It must only summarize evidence emitted by the existing Phoenix host, visible generated app/WebView, browser corpus, and native test adapter. It may not authorize replay, decide route readiness, certify an installed build, or influence physical promotion. Keep `doctor`/`inspect` as guidance and presentation; never infer pass from a report or artifact merely existing. Keep the physical report/schema unchanged. [Physical contract](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/lib/crosswake/proof_lane/physical_iphone_contract.ex) · [physical report join](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/lib/mix/tasks/crosswake.proof_lane.physical_iphone.ex)

**A declared source SHA is only one input to provenance, not proof of the installed/served candidate.** The checked-in iOS host README says its normal proof resolves the published SwiftPM mirror, with `--local` as a separate maintainer mode. Phoenix host dependencies and static media also have their own selected/resolved bytes. Thus a report that copies the repository SHA into every owner row can falsely join a current source tree to an older Swift package, generated manifest, installed app, WebView JavaScript, backend process, or fixture. [iOS host README](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/ios_shell_host/README.md) · [host Mix dependencies](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/mix.exs)

Bind a run to independently observed, sanitized identities: Crosswake and host source/dependency lock inputs; generated manifest/activation/config digest; the installed app build hash plus an in-app run nonce/build marker; the JS/static fixture digest actually loaded or consumed by that WebView; and a backend process/build marker queried from the run-owned server. Compare these with expected values fixed before launch, never values read back solely from the report under test. If a layer cannot expose and match its identity, mark its observation unavailable and the required run blocked. Do not emit bundle/team IDs, origin, cookies, fixture content, account/scope references, answer/media data, or stable device IDs.

**Synthetic fixture authority must remain explicit.** The reference host's test session proves that its real Phoenix admission, replay transaction, and Ecto effect work under a synthetic fixture. It is not real adopter authentication or proof of an external identity provider. Record authority as `synthetic_test_authority`; a successful backend assertion must not be labeled adopter-authorized. Keep fixture creation, database, endpoint, and server owned by one run. The existing whole-table `ReviewEvent` cleanup is safe only against a newly created, exclusively owned database; never run it against a shared/default DB. Do not reuse port 4700 or attach to an existing server. Create a fresh DB and exclusive loopback port, start and identify the exact child process, then terminate that process and delete only the run-owned root. On failure retain diagnostics privately; shared CI/stdout/receipt gets sanitized stage IDs and causes only. [Phoenix replay authority](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/lib/crosswake_example/local_first/physical_iphone_authority.ex) · [Playwright server config](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/playwright.config.ts)

Faults must be deterministic and run-scoped: use the existing host's test controls to prepare server rejection/disablement, missing or corrupt only the owned fixture, and switch only the test session. Browser offline uses that Playwright context's network emulation. Simulator offline must be scoped to the simulator/test target and verified at the actual request boundary; if that cannot be done without changing laptop/network state, bypassing WebKit, or substituting Safari/mock transport, mark it blocked. Do not treat a dispatched `online` event alone as a network cut or proof. Preserve the target app's actual visible `WKWebView`, normal JS replay path, and ordinary backend request. Do not upload traces, screenshots, `.xcresult`, raw stdout, or logs that may contain private payloads; restricted local failure artifacts may be retained for diagnosis. [Playwright offline API](https://playwright.dev/docs/api/class-browsercontext#browser-context-set-offline) · [Apple simulated/physical destinations](https://developer.apple.com/documentation/Xcode/running-your-app-on-simulated-or-physical-devices)

## Roster and acceptance correction

The scope proposal's ten scenarios are authoritative. `TWIN-ARCHITECTURE.md` currently substitutes a different ten: it adds cold-boot/bridge as scenario 1, moves missing/corrupt media to scenario 10, and drops the proposal's scenario 10 (report integrity). Correct the architecture text to use the proposal's exact ten IDs and sequence: pack install; authorized entry/offline; selected/freeform writes; installed offline audio plus missing/corrupt denial; kill/relaunch without reset; reconnect/exactly-once/empty backend outbox; rejection/conflict; logout/switch fencing; entry/replay disablement; redacted source-bound report and fabricated/missing-observation rejection. Treat cold boot, expected origin, same visible WebView/bridge, and owner identity as scenario 1 setup/observations, not an eleventh case. Do not repurpose the existing 19 physical assertions as this roster; they remain a separate physical contract.

The ten are finite and coherent as a bounded run, with isolated controlled negative cases, but not all are presently demonstrated by the described owners. In particular, native pack verification/playback does not prove that the offline study in the actual WebView consumes those installed bytes; browser page reload is not app process death; and synthetic sessions do not prove adopter identity. Keep the ten rows, require all component assertions within a bundled scenario, and block completion if any required virtual join is unavailable. Do not silently narrow “WebView offline audio” to native AV playback or classify an automatable missing seam as a physical/adopter residual. If the existing host cannot prove the byte-to-WebView media path or target-scoped network loss, record the blocker and narrow any completion claim to the observations actually made; do not claim TWIN-02 or full TWIN completion.

**Final acceptance gates:** (1) exact ten-row roster, no duplicates or omissions, with per-row owner and observed pass/fail/unavailable; a required unavailable or unmet precondition blocks completion; (2) source/build identities match the installed candidate, loaded WebView/static bytes, and run-owned backend; (3) one uninterrupted offline lifecycle preserves IndexedDB and installed media across app termination/relaunch; (4) ordinary WebView requests reach the owned Phoenix/Ecto server for accepted and negative replay checks, with exact one effect and empty outbox only on acceptance; (5) synthetic authority, redaction scan, fixture provenance, and absence of fabricated/missing observations are verified; (6) simulator/browser receipts never satisfy physical-iPhone or real-adopter gates. Stop after the fixed virtual roster passes and only those expressly external gates remain. Repeated CI is warranted only for the stable report/anti-overclaim contract, not the one-off simulator reconciliation.
