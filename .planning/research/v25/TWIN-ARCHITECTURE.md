# v25 Twin Architecture Research

**Question:** What is the smallest credible digital twin for demonstrating Crosswake’s bounded offline-study flow with a generated iOS host?
**Recommendation:** Keep fast contract tests and the real Phoenix/browser corpus, then add one simulator composition that launches the generated candidate, observes its own visible `WKWebView` and bridge, uses the same local Phoenix host/database, and performs a process kill/relaunch without resetting app storage. Treat the full physical-adopter harness as separate, non-transferable evidence.
**Evidence baseline:** GitHub `main` resolves to `d0dbdf7bf196cea167ced3c50cf620bf3cb2452b` (confirmed with read-only `git ls-remote` on 2026-10-13). The recovery checkout does not contain that Git object and has extensive uncommitted release-recovery changes. Production facts below come from raw files at the approved GitHub ref; local working-tree changes are not treated as production truth.

## What exists and what remains uncomposed

At the approved ref, `examples/phoenix_host` is already a runnable Phoenix/Ecto reference host with a real IndexedDB offline island and a sequential Playwright corpus. The offline-sync spec switches Chromium network transport offline, drives the real study UI, inspects IndexedDB, reconnects through the app’s online listener, observes `/study/sync`, checks the actual Ecto row count, resends the same mutation ID, and confirms one persisted row. It also tests scope partitions, replay denials, paused lifecycle behavior, and recovery presentation. The host’s Playwright `webServer` owns the test database and server process; its test config explicitly uses a shared SQLite database rather than Ecto SQL Sandbox for browser HTTP requests. Sources: [offline-sync spec](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/e2e/offline_sync.spec.ts), [offline route proof helpers](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/e2e/support/offline_route_proof.ts), [Playwright config](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/playwright.config.ts), [test config](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/config/test.exs).

That corpus does not prove every claim in the proposed twin. The `offline_sync` scenario’s seeded `/_e2e/replay-session` cookie supplies a closed test authority fixture; it exercises real Phoenix admission and Ecto idempotency, not adopter identity-provider or credential authority. Some rejected-work UI tests replace `window.fetch` with a canned rejection response, which proves client presentation/retention only. Server rejection, conflict, logout, switch, and disablement must be separate server-backed cases if TWIN-04 claims end-to-end behavior. Playwright’s built-in isolated contexts are non-persistent; page reload is not process death. Playwright documents its offline emulation as affecting the browser network stack and not every possible transport, so its result belongs to the browser runtime. Sources: [offline-sync spec](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/e2e/offline_sync.spec.ts), [Playwright BrowserContext](https://playwright.dev/docs/api/class-browsercontext), [Playwright `setOffline`](https://playwright.dev/docs/api/class-browsercontext#browser-context-set-offline).

The checked-in iOS shell host has a real SwiftUI shell, `WKWebView`, `WKUserContentController`, low-frequency bridge handlers, route/navigation coordinator, and host-supplied pack provider. The separate Phoenix physical-proof host has real provider/media verification and a native/XCTest flow. However, its physical study contract test explicitly skips in Simulator. Its physical adapter stores its own native `UserDefaults` and host-private file journal and posts through its own URLSession transport; that is useful Phase 162/163 proof infrastructure, but it is not the browser IndexedDB island inside the visible WebView. Do not repurpose or rebuild that lane as a simulator twin. Sources: [iOS WebView host](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/ios_shell_host/CrosswakeShell/LiveViewContainerViewController.swift), [reference host app composition](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/ios_shell_host/CrosswakeShell/CrosswakeShellApp.swift), [physical adapter](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/native/ios/CrosswakeProofLane/ProofLaneDriver.swift), [physical UI tests](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/examples/phoenix_host/native/ios/CrosswakeProofLaneUITests/ProofLaneUITests.swift).

The current `bin/crosswake-ios-rehearsal` starts the reference host, runs the `examples/ios_shell_host` Dev scheme tests, then opens the study URL in **Simulator Safari**. That is a useful developer rehearsal and browser-on-simulator view, but it does not demonstrate that the generated shell’s own `WKWebView` loaded the route or that its bridge participated. The new twin must launch the generated app and observe the same visible WebView instance. Keep the Safari rehearsal’s advisory label. Source: [iOS rehearsal script](https://github.com/szTheory/crosswake/blob/d0dbdf7bf196cea167ced3c50cf620bf3cb2452b/bin/crosswake-ios-rehearsal).

The older [adoption proof strategy](../ADOPTION-PROOF-STRATEGY.md) contains useful app-archetype/offline-island rationale, but its recommendation to ship generic `Crosswake.Offline`/`Crosswake.Sync`, broad content packs, and a reusable sync engine conflicts with the governing first-adopter ADR and current workstream constraints. Do not carry that proposal forward: the study island, opaque scope, host authority, one provider, and physical exit test are deliberately bounded.

## Three twin designs

| Design | What it exercises | Advantages | Blind spots and cost | Recommendation |
|---|---|---|---|---|
| **A. Component/contract twins**: ExUnit/Plug, Ecto tests, shared JSON vectors, Swift/XCTest contract tests, and browser unit tests. | Envelope validation, route/bridge contracts, denial vocabulary, Ecto transaction/idempotency rules, pack digest logic. | Fast, stable, precise failure location; idiomatic for pure Elixir/native logic; shared vectors reduce cross-language drift without copying implementations. | Cannot establish a rendered offline page, real IndexedDB persistence, actual WebKit process restart, installed bytes consumed by that page, or that generated iOS wiring reaches the tested endpoint. A mock transport cannot prove replay. | Keep as the fast inner layer; it is insufficient as “digital twin demonstration.” |
| **B. Real Phoenix + browser twin**: existing Phoenix test server/database plus Chromium/Playwright and actual `offline_sync` corpus. | Real host route, browser JS/IndexedDB, transport toggles, HTTP, host replay admission, Ecto effect and duplicate response. | Already valuable and cheap to reuse; clear diagnostics; good host developer loop; scenario drives the real app instead of a test-only sync client. | Browser context is not the generated iOS process or WKWebView. Current reload coverage is not process kill. Client-faked error responses are UI-only; synthetic replay sessions are not real account authentication. | Preserve as the authoritative web/offline-island gate; add only a persistent-browser lifecycle case if cheap, and label it Chromium. |
| **C. Phoenix + generated iOS simulator composition**: one configured local Phoenix host/database plus XCUITest of the generated candidate app’s visible WKWebView and host bridge, with real study JS and IndexedDB in that WebView. | The cross-boundary composition: generated config → shell activation → visible WebView → offline island → native pack/runtime seam → Phoenix HTTP → Ecto, plus app-process terminate/relaunch. | Tests precisely the mismatch between the pieces that separate tests currently cannot detect. Exercises the candidate host users generate, not a generic wrapper or Safari. | Slow and more brittle; simulator networking, app signing/build modes, app-bound domains, WebKit storage/process behavior and XCUITest accessibility require diagnosis. Simulator does not cover all hardware or replace physical proof. | Add one bounded composition journey and only necessary isolated recovery cases; do not mirror the full browser/native suite. |

An exhaustive three-runtime fan-out of every one of ten scenarios into ExUnit, Playwright, and XCTest would triple setup and fixture policy while creating disagreement about what each layer actually owns. A mock-only twin is cheaper but can pass when the app pieces do not join. The minimum credible composition is A + existing B + a small C that observes only the missing seams.

## Recommended runtime ownership and composition

Keep ownership visible in each scenario: Phoenix owns route policy, configured router/origin, session-to-scope mapping, host flags, replay admission, and domain writes; the offline-island JavaScript owns its card interaction, IndexedDB outbox, status and replay trigger; the generated iOS host owns shell bootstrap/navigation, the one `WKWebView` instance, cookies/data-store configuration, bridge installation, and its host-supplied provider; Ecto/Postgres-or-the-reference-host’s configured test database owns the durable accepted/rejected effect. The WebView does not turn LiveView into an offline engine. High-frequency study interaction stays in the local island; bridge calls stay typed, versioned and low-frequency.

The simulator journey should cold-launch the **Phase 179 generated candidate** from the host-owned input set. Phase 179 should take one Phoenix router/origin authority and host-owned bundle/signing configuration, write only declared managed generator outputs, and preserve those values on regeneration. Build the generated candidate in explicit unsigned-simulator mode; inspect device-target signing/build settings separately without requiring private signing values in artifacts. Confirm bundle/build mode, configured Phoenix origin, route ID/runtime, and manifest origin match the host input. A run marker visible through the app’s own navigation/WebView host should prove (a) the generated app process is running, (b) its visible `WKWebView` loaded the study route at that origin, and (c) a nonce-bound typed bridge handshake/reply traversed that same WebView/controller. This should be a test-only observation seam with no route, auth, or storage authority. Do not infer it from an app launch, Xcode test pass, an unrelated shell test, or Simulator Safari.

Then run one uninterrupted storage journey: install one host-provided pack and independently read back its exact expected size/digest; exercise the route’s offline audio from those installed bytes while browser-network access is denied; activate the opaque scope; submit one selected and one free-form answer in the actual offline-island UI while disconnected; inspect only safe local counts/state; terminate the app with XCTest, relaunch the same installed bundle without reset arguments or a new website-data store, and verify both outbox records remain in that WKWebView’s IndexedDB; reconnect and let application code replay. Await the real HTTP response, assert the actual host database has one scoped effect per mutation ID, explicitly resend one ID through the ordinary endpoint, then verify still one effect and an empty IndexedDB outbox. “Exactly once” means one durable domain effect under retry/duplicate delivery, not exactly-once network delivery. Apple XCTest/XCUIAutomation is intended for interacting with app UI and app process; its result is simulator evidence only. Sources: [XCTest](https://developer.apple.com/documentation/xctest), [Apple Simulator test guidance](https://developer.apple.com/library/archive/documentation/IDEs/Conceptual/iOS_Simulator_Guide/GettingStartedwithiOSSimulator/GettingStartedwithiOSSimulator.html), [WKUserContentController](https://developer.apple.com/documentation/webkit/wkusercontentcontroller).

There is one substantive integration question to resolve in Phase 180 planning: the existing iOS reference pack provider installs verified files in app-owned Application Support and the native proof host can play its AIFF through AVFoundation, while the browser island reads browser-managed IndexedDB and media URLs. Research found no existing assertion that the visible WebView’s audio element consumes the bytes installed by that host provider. The twin must either prove the currently designed host-to-WebView asset path with the existing adapter or report the missing seam as blocked. It must not claim “offline WebView audio” from a separate native AVAudioPlayer assertion, nor add a generic storage/URL-scheme bridge just to make the test pass. Route ownership, host authentication and storage authority stay with the host. This should be the first feasibility check in the phase, before scenario expansion.

For fault cases, use the reference host’s test-only `/_e2e` case-preparation controls where already supported, then drive the **normal visible app path and normal `/study/sync` request**. The test session fixture and fault controls are intentional synthetic inputs, but the endpoint’s `ReplayAdmission` and `Study.apply_one` transaction and the database observation remain real. Record these limits as test authority, not adopter auth. At minimum, verify server-backed rejection and conflict retain work and show recovery state; log out and switch scope before another send and verify no old-scope request/effect; disable entry and replay separately and verify queued work remains; remove and corrupt the pack and prove entry/audio fail closed. Keep client-injected `fetch` responses only as fast presentation tests and label them mocks. Do not place raw answers, media, session cookies, account IDs, scope values or mutation IDs in retained artifacts; emit only closed case IDs, outcome, aggregate row/outbox counts and artifact hashes.

Phoenix/Plug/Ecto ergonomics favor the existing test seams: use `Plug.Test`/`Phoenix.ConnTest` for deterministic router/controller authorization cases; `Phoenix.LiveViewTest` for server-rendered interaction and disconnected/connected mount contracts; ExUnit plus Ecto SQL Sandbox for in-process transactional tests and explicitly managed spawned processes; use the existing Playwright server and an isolated real test database for cross-process HTTP behavior, because an external browser or simulator cannot share an ExUnit transaction. Ecto’s sandbox ownership/allowance model is process-scoped and shared mode trades concurrency for implicit process access. Preserve the existing Playwright runner as owner of its database/server lifecycle unless the Phase 180 coordinator can cleanly compose one run-owned host without a second reset/start path. Sources: [Plug.Test](https://hexdocs.pm/plug/Plug.Test.html), [Phoenix.LiveViewTest](https://hexdocs.pm/phoenix_live_view/Phoenix.LiveViewTest.html), [Ecto SQL Sandbox](https://ecto-sql.hexdocs.pm/Ecto.Adapters.SQL.Sandbox.html).

Cross-language lesson: Hotwire Native validates a useful split—web content can remain in a shared WKWebView while native navigation/chrome and named bridge components stay host-owned. Adopt the seam clarity, not Hotwire’s route framework or a generic plugin catalog. Continue the existing shared contract-vector practice for values that truly must agree across Elixir, Swift and JavaScript; keep state-machine and transaction behavior tested in the implementation that owns it. Do not copy the same scenario implementation three times. Source: [Hotwire Native handbook](https://turbo.hotwired.dev/handbook/native), [Crosswake native test strategy](../NATIVE-TESTING.md).

## Fixed roster, evidence strength and stop rule

Reuse the scope proposal’s ten scenario IDs as the entire roster: (1) cold boot and route/origin/visible-WebView/bridge binding; (2) verified pack install and installed-byte offline audio; (3) authorized entry, offline selected and free-form mutations; (4) process terminate/relaunch with no reset and retained local work; (5) reconnect and real backend acceptance/empty outbox; (6) duplicate replay leaves exactly one Ecto effect; (7) rejection and conflict retain recoverable work; (8) logout and account switch fence old-scope replay; (9) disabled entry and disabled replay both fail closed without deleting queued work; (10) missing/corrupt pack denies the dependent route/audio. Browser coverage may satisfy steps only as browser observations; generated-iOS coverage must satisfy the missing integrated assertions. Contract and unit tests underpin them but are not relabeled runtime passes.

Run precondition: exact candidate source/build identity, generated host input digest, expected origin/route, isolated database and one-time fixture reset are bound before launch. Reuse current browser cases; add no new cases merely to create equal-looking platform counts. The report should have one row per fixed scenario with owner and observation class (`contract`, `Playwright/Chromium`, `generated-app/WKWebView on iOS Simulator`, `reference backend/Ecto`), observed result, and explicit unavailable/blocked status. Missing or synthetic observations cannot pass; unavailable runtime work remains incomplete. Keep simulator and browser results advisory and separate from physical-device records. Apple’s own Simulator guidance says it should not be the sole test platform; physical hardware remains an external gate, as the Crosswake route map already states.

**Diminishing-returns exit:** stop when the ten bounded cases pass with source-bound observations at the Phase 179 candidate and the only remaining uncertainty is hardware behavior, adopter route/identity authority, credentials or an external approval. A blocked automatable assertion is not completion. Reopen twin work only for a reproducible defect in this generated reference composition or new authorized adopter evidence; no new matrix, generic sync/storage, first-party WebView runtime, Android expansion, broad bridge conformance product, or showcase work. This gives a solo maintainer an adoption job: “generate my configured iOS host without hand patches, demonstrate one honest Phoenix offline island end-to-end, and know exactly what remains for physical/adopter proof.”

## Corrections to proposed requirements

- **TWIN-01:** name the generated candidate, host-owned router/origin, visible app process, same `WKWebView`, and nonce-bound typed bridge round-trip as required observations. “Reuses adapters” and “XCUITest passed” are not enough. Report browser-only, contract-only, simulator-WebView and backend observations separately.
- **TWIN-02:** distinguish browser page reload from true app terminate/launch. In Simulator, prove the real study UI writes IndexedDB in the same persistent WebKit data store before and after app-process relaunch. Prove the pack hash and audio consumption path belong to the same installed artifact. If the iOS provider’s files are only proven through native AVFoundation and the WebView cannot consume them, mark the scenario blocked and resolve the host seam before claiming it.
- **TWIN-03:** define exactly-once as actual Ecto effect idempotency under duplicate HTTP delivery, not transport semantics. Keep the test-only replay session fixture explicit; it does not prove the real adopter’s session provider. Query the backend after normal app replay and duplicate replay rather than accepting a canned success callback.
- **TWIN-04:** split UI mocks from server-backed fault cases. For end-to-end rejection/conflict, logout/switch and feature disablement, prepare controlled conditions in the host, then drive the ordinary WebView/JS replay path and inspect retained IndexedDB plus Ecto state. Missing/corrupt pack assertions must occur at the owner that serves the pack to the actual route.
- **TWIN-05/06:** include failed/unavailable cases and provenance in a closed, redacted source-bound report; keep simulator evidence advisory; stop at the fixed roster and residual hardware/adopter gates. A failing XCUITest or a blocker is a blocker, not a successful demonstration.

## Material conflicts to resolve in phase discussion

1. **Installed audio asset handoff:** native pack storage and web-island playback have separate existing demonstrations; the join is unproven. Do not invent a URI scheme or WebView file bridge until the existing host wiring is inspected and a need is demonstrated.
2. **One server lifecycle:** browser Playwright owns a destructive test-db/server setup; simulator XCUITest needs the same host while preserving it across lifecycle. Decide one coordinator that starts/resets once and lets both runners consume it, without duplicate server setup or reset during the scenario.
3. **Authority level and cookie ownership:** current reference host’s E2E session fixture exercises host admission and real Ecto effects, but not external user identity. Establish that fixture in the visible WebView’s own cookie/session store; the physical adapter’s separate URLSession cookie jar is not proof of WKWebView auth continuity. Keep all output described as reference-host test authority and non-transferable to the parked adopter gate.
4. **Simulator network/offline control:** Playwright’s browser-context offline toggle is not an iOS simulator network control. The simulator flow needs an explicit deterministic network cut/restoration under XCTest or a host-owned test transport and must distinguish “WebView requests denied” from merely firing a JavaScript `online` event.
5. **Signing/config and simulator mode:** Phase 179 must supply host-owned identity/team and origin inputs, while preserving a supported unsigned simulator mode and separately inspectable device-target signing settings. Twin should build the actual generated candidate using the declared simulator mode; it must neither require physical signing secrets nor claim signed-device installability.
