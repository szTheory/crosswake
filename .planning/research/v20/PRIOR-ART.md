# Prior Art / Ecosystem Research — v20.0 "Native Controls Pack 1"

Researched: 2026-07-12
Scope: bounded route-local controls (alert/confirm, menu/action-button, haptics,
share sheet, toast/review prompt) + read-only `permissions.status` /
`notification_token` evidence surfaces.

Crosswake's existing vocabulary (from `guides/bridge.md`, `guides/capabilities.md`)
already ships `app.info.get`, `haptics.impact`, `permissions.status`
(`notifications` alias only), `files.pick`, `transfer.*`. `share`,
`notification_token` are declared capability families already (share = `core`,
notification_token = `companion`) but not yet backed by a shipped command. Pack 1
is filling in the remaining bounded-bridge surface, not inventing the taxonomy.

## 1. Comparison Table

| Library | Control model | Declaration site | Degradation when native absent | Versioning / rebuild story | Steal | Avoid |
|---|---|---|---|---|---|---|
| **Hotwire Native (Bridge Components / ex-Strada)** | Named component (`bridge--form`, `bridge--menu`, `bridge--button`) = Stimulus controller pairing with a native class of the same name. Component sends typed `event`+JSON `data`, native replies via callback. | **Web side, inline in HTML** via `data-controller="bridge--X"` + `data-bridge-*` attrs. No separate DSL/manifest — the page itself is the declaration. | **Web is always the fallback.** Component doesn't even connect in a browser or on an app version that lacks native support — `shouldLoad()` sniffs the WebView user-agent string for the component name; if absent, Stimulus never attaches, and the plain HTML/CSS underneath just renders. CSS can additionally hide the web fallback only when native is confirmed present (`[data-bridge-components~="menu"] .web-fallback { display:none }`). | Native app version advertises supported component names in its User-Agent. `this.enabled` on the JS controller tells you if the *installed* native build supports this component version. No IDL/codegen — plain JSON messages, native and web hand-authored per platform per component. | **(a)** Progressive enhancement is structural, not a mode flag: absence of native support degrades to "the web already worked," never to an error. **(b)** UA-string capability advertisement — cheap, works before any handshake round-trip. **(c)** Per-instance platform opt-out (`data-controller-optout-ios`) for "native supports it but we don't want it here." **(d)** Ships pre-built components for the exact same shapes Crosswake wants: button (nav-bar action), menu (native action sheet from a declarative list), form (submit-button relocation). | No typed schema/versioning beyond a component name string + "enabled" boolean — works because Basecamp/37signals ships both web and native themselves. | **Capacitor** (Ionic) | Generic **plugin catalog**: JS plugin shim ↔ native plugin class, matched by string name + arbitrary method surface. No bounded vocabulary — any plugin can expose any method. | `npm install @capacitor/x` + native platform project registration; call `Plugin.method()` from JS anywhere. | **Throws/rejects at call time** if plugin isn't installed/linked on that platform — no structural fallback. Community has to hand-roll `Capacitor.isPluginAvailable('X')` checks everywhere. | Plugin JS version and native plugin version are **independently versioned npm/native packages** — CLI (`cap doctor`) exists specifically because they drift. Native code changes require a full native rebuild; Capacitor gives no compile-time signal that a JS call site and the installed native plugin version agree on shape. | Nothing structural — its value is the negative example. `npx cap doctor` as a *diagnosis-after-the-fact* tool is the thing Crosswake's `mix crosswake.doctor` replaces with **fail-closed at declaration time** instead. | This is the exact trap Crosswake's manifesto explicitly refuses: unbounded method surface, version skew between JS shim and native plugin ([Capacitor 6 plugin-registration breaking change](https://github.com/ionic-team/capacitor/issues/7443), [8.0 upgrade notes](https://capacitorjs.com/docs/updating/8-0)), and reactive "run doctor to find out what broke" instead of proactive declared capability + fail-closed denial. |

This is the ecosystem-scale version of what Crosswake's small, curated, versioned command vocabulary + generate-and-diff manifest is designed to prevent by construction — Pack 1 must NOT grow into "and now also add a plugin for X" acceptance criteria.
| **Expo Modules / Config Plugins** | Native modules authored against a typed Swift/Kotlin "Expo Modules API"; **config plugins** mutate native project config (Info.plist, AndroidManifest, Podfile) at prebuild time. | `app.json`/`app.config.js` plugin list (declarative) + native module source in an isolated `modules/` dir. | Structural split, not degradation: **Expo Go** (fixed native binary, can't add native code) vs. **dev client** (custom binary, rebuild whenever native deps change). Expo is explicit that "you only needed to build the JS bundle" in Expo Go, but "with development builds you also need to compile the native app" ([Expo docs](https://docs.expo.dev/develop/development-builds/introduction/)). | Communicates the rebuild boundary as a **named artifact class** (Expo Go vs dev-client) rather than a vague warning. Rebuild cadence in a healthy team is framed concretely: "once every two or three weeks" ([capgo.app writeup](https://capgo.app/blog/expo-development-client/)). Config-plugin ordering footgun is explicit in their own docs: "[if multiple config plugins modify the same native file, order in app.json determines who wins, and plugins can inadvertently overwrite each other]" ([Expo docs](https://docs.expo.dev/develop/development-builds/introduction/)). | **Steal:** naming the rebuild boundary as a first-class artifact/mode (Crosswake already has a "rebuild class" concept per the brief — validate it against Expo's dev-client/Expo-Go split: Crosswake should give Pack 1 controls an explicit "requires native shell rebuild: yes, because new capability = new shell version" callout in the manifest diff, exactly like Expo's prebuild warns). | Config-plugin *ordering/overwrite* footguns are a caution for Crosswake's generator: multiple declared capabilities touching the same native manifest section (e.g. two controls both wanting nav-bar real estate) must not silently clobber each other. |

Pigeon's own docs warn against exactly the trap full codegen would create here. | Full IDL/protobuf pipeline for 7 commands is disproportionate machinery; MethodChannel's raw string-matching (no compile check at all) is the other extreme to avoid — Crosswake's typed envelope + capability-gated allowlist is already better than bare MethodChannel. |
| **React Native TurboModules / JSI + Codegen** | Codegen turns a TS/Flow spec into typed native glue; `TurboModuleRegistry.getEnforcing()` throws hard if the native module isn't registered in the compiled binary. | TS interface file, consumed at build time. | **No graceful degradation** — `getEnforcing` is documented as intentionally strict: "if it is missing, the application will forcefully crash" ([facebook/react-native#47352](https://github.com/facebook/react-native/issues/47352), [react-native-maps#5425](https://github.com/react-native-maps/react-native-maps/issues/5425)). The common failure mode is a **JS-bundle/native-binary mismatch** — new JS ships expecting a module a stale native binary doesn't have. | Codegen at build time gives compile-time type safety but explicitly does *not* protect against runtime skew between an already-shipped native binary and a newly-shipped JS bundle (OTA-update class of bug). | Confirms the value of Crosswake's `native_runtime_version` + `compatibility_mismatch` denial check in the request envelope — this is precisely the failure class (binary/bundle skew) that TurboModules' compile-time codegen does *not* solve, and Crosswake's runtime fail-closed check does. | Do not adopt "throw/crash if missing" as the *default* behavior for an unsupported capability — Crosswake's own `undeclared_capability`/`unavailable_capability` typed denial is the correct opposite of `getEnforcing()`. Good confirmation Crosswake's existing choice is right; nothing new to copy here. |
| **LiveView Native** | Not a bridge at all — it **replaces the render target**. Single LiveView emits `~SWIFTUI`/`~JETPACK` templates instead of HTML; native views ARE the UI, diffed and pushed like LiveView DOM diffs. | Template format sigil per platform, same component API surface (e.g. `<.form>`) mapped to platform-native equivalents (`Toggle` vs `Switch` vs `ToggleSwitch`) ([DockYard, "Road Toward LiveView Native v0.2"](https://dockyard.com/blog/2023/11/01/the-road-toward-live-view-native-v-0-2-part-2)). | N/A — there is no "native absent" case; the whole screen is native by construction once a route opts in. | Requires the LiveView Native client library shipped in the native binary; new component support = new client library version = rebuild. | Nothing to steal for Pack 1 — it's the "own the whole render loop" strategy Crosswake explicitly is not. Keep each Pack 1 control single-shot, request/reply, no native-side state machine. |
| **Tauri 2.x Capabilities/ACL** | Default-deny; every plugin command must be explicitly granted to a named window/webview via a `capability` JSON declaring commands + scopes ([Tauri capabilities docs](https://v2.tauri.app/security/capabilities/)). | Declarative capability files, not inline in the page. | Command call fails at the IPC layer if the calling window has no matching capability — closest analogue in the wild to Crosswake's own manifest-declared, capability-gated, fail-closed model. | Scopes add resource-level restriction *within* a granted command (e.g., filesystem path scoping) — a finer grain than Crosswake currently needs for Pack 1 but a good future pattern for `files.pick`/`transfer.*`. | **Validates Crosswake's existing architecture almost 1:1**: default-deny, explicit per-surface grant, no ambient authority. Good external validation to cite in the roadmap doc that this is now recognized industry-best-practice (Tauri 1→2 was **itself** a migration away from a flat allowlist toward exactly Crosswake's model). | None specific to Pack 1 — mostly confirms direction. |
| **NativePHP (mobile)** | Plugin-based; plugins compile directly into the app and "can access any native API, sensor, or hardware feature" ([nativephp.com/docs](https://nativephp.com/docs/mobile/3/plugins/permissions-dependencies)) — closer to Capacitor's breadth than Crosswake's boundedness. | PHP facade calls; plugin manifest declares required permissions/dependencies. | Not addressed in docs as a first-class concept — permissions are requested at plugin-install/build time, not gated per-call. | Plugins compiled into the binary — any plugin add = rebuild. | Their documentation requirement that "**every plugin must document every public method, every event, and every permission it requires**" is a good adjacent discipline for Crosswake's own Pack 1 docs (each control's guide page should read like this: methods, events/replies, permissions, fallback). | Breadth-first "any native API" posture is exactly what Crosswake refuses to become — cite as an anti-model in the roadmap intro if useful context is wanted, but no technical pattern to adopt. |

## 2. "Steal This" — ranked, concrete, with source

1. **Structural progressive enhancement, not a mode flag** (Hotwire Native). The web/LiveView version of a control should be the thing that exists by default; native is an enhancement layer that swaps in only when the shell advertises support. Concretely: `alert`/`confirm` and `toast` should have a real Phoenix/LiveView-rendered fallback UI that is what ships when the capability is undeclared or unavailable — not an error state. This is stronger than "graceful degradation as an edge case" — it's "the web thing already works, native is opt-in enhancement," which is the same posture as `route_policy.md`'s "Rough edge" framing. Source: [Hotwire Native Bridge Components reference](https://native.hotwired.dev/reference/bridge-components), [Strada handbook](https://strada.hotwired.dev/handbook/how-it-works).

2. **Per-instance platform opt-out, not just per-capability** (Hotwire Native's `data-controller-optout-ios`/`-android`). Crosswake's route DSL should let a route declare a capability but still say "don't use native menu on Android for this one" — useful because Pack-1 controls (esp. menu, toast) have very different platform-policy risk profiles per OS (see §4). Source: [Hotwire Native reference](https://native.hotwired.dev/reference/bridge-components).

3. **Name the rebuild boundary as a first-class artifact, not a warning string** (Expo Go vs. dev-client split). Every Pack 1 capability that's genuinely new native surface (menu, share, review-prompt evidence) should show up in `mix crosswake.doctor` and the generated manifest diff as "adding this capability requires shipping a new native shell version" exactly the way Expo's tooling names "you're now in dev-client territory." Source: [Expo dev builds intro](https://docs.expo.dev/develop/development-builds/introduction/).

4. **Config-plugin ordering/overwrite footgun → generator collision detection**. Expo's own docs admit that multiple config plugins touching the same native file silently overwrite each other depending on declaration order. Crosswake's generator should explicitly detect and fail-closed (not silently merge/overwrite) if two declared capabilities in Pack 1 want the same native resource (e.g. nav-bar button slot claimed by both `menu` and a future capability). Source: [Expo config plugins guidance](https://docs.expo.dev/develop/development-builds/introduction/).

5. **Default-deny capability grant as industry-validated, not idiosyncratic** (Tauri 2.0's capabilities/ACL migration away from Tauri 1's flat allowlist). Useful citation for the roadmap/PITFALLS narrative: Crosswake's fail-closed, declared-capability model isn't an invented constraint, it's where the rest of the hybrid-native ecosystem is independently converging. Source: [Tauri 2.0 security/capabilities docs](https://v2.tauri.app/security/capabilities/).

6. **Per-plugin documentation discipline: methods + events + permissions, always together** (NativePHP). Apply directly to Pack 1's guide pages — each control's doc page should state the command, the reply shape, the platform permission (if any), and the fallback in one place, matching the existing `guides/bridge.md`/`guides/capabilities.md` style. Source: [NativePHP plugin permissions docs](https://nativephp.com/docs/mobile/3/plugins/permissions-dependencies).

7. **Reject codegen/IDL for this vocabulary size — Pigeon's own maintainers warn against it for public APIs.** Validates the v14.0 decision rather than just leaving it unexamined: Pigeon (Flutter's typed-codegen tool) explicitly discourages shipping generated code in a **public** package API because generator version bumps become an extra breaking-change axis for downstream consumers. A hand-authored canonical Elixir command list + generate-and-diff avoids adding "which Pigeon/codegen version produced this" as a second compatibility dimension on top of the bridge protocol version Crosswake already tracks. Source: [pub.dev/packages/pigeon](https://pub.dev/packages/pigeon).

## 3. Footgun Ledger

| # | Footgun | Real citation | Crosswake guard |
|---|---|---|---|
| 1 | **Review prompt treated as "did it show?" API / used as a button CTA.** Both platforms explicitly warn against a tappable "rate us" button that calls the native review API, because the call may silently no-op once quota is hit, leaving a dead button. | Android: "*you should not have a call-to-action option (such as a button) to trigger the API... redirect the user to the Play Store instead*" — [Android Play In-App Review docs](https://developer.android.com/guide/playcore/in-app-review). iOS: no completion callback exists at all; frequency capped and silently no-ops past quota — [Apple SKStoreReviewController docs](https://developer.apple.com/documentation/storekit/skstorereviewcontroller/requestreview()), community confirmation on [Apple Developer Forums](https://developer.apple.com/forums/thread/115193). | The `review_prompt` (or similarly named) command must reply only with `status: "requested"` / a typed denial — **never** `"shown"` or `"accepted"`. Docs and the route DSL must make it structurally impossible to wire the capability to a visible "Rate us" button; the guide should show only the "ask after a positive moment" pattern (e.g., after N successful completions), never a menu item. |
| 2 | **Review-prompt gating/incentivizing → App Store rejection (Guideline 5.6.3 / general anti-manipulation clauses).** Apps have been rejected for prompting on first launch/onboarding or for tying review-prompt logic to positive-only funnels. | Apple App Review Guidelines anti-manipulation clause — [developer.apple.com/app-store/review/guidelines](https://developer.apple.com/app-store/review/guidelines/); onboarding-timing rejections — [RevenueCat, "Move your rating prompt out of onboarding — or risk rejection"](https://www.revenuecat.com/blog/engineering/dont-prompt-ratings-during-onboarding/). | Capability docs must state the honest fallback + timing guidance as **normative, not optional**: no menu/UI entry point that calls it on-demand; require callers to fire it from a route-local "meaningful completion" event, not a first-run hook. Doctor/support-matrix should flag (advisory) if a route calling the review capability is a route reachable on first navigation. |
| 3 | **Toast has no native OS primitive on iOS — every "toast" implementation is a hand-rolled overlay view, not a system surface.** Treating "toast" as a `bounded_bridge` native capability on iOS is a category error: there is nothing native to bind to. | Confirmed directly by absence of any Apple toast API and universal reliance on custom UIWindow/UIView overlays in third-party libs — [BastiaanJansen/toast-swift](https://github.com/BastiaanJansen/toast-swift), [michael94ellis/ToastWindow](https://github.com/michael94ellis/ToastWindow). | Do not ship `toast` as a native bounded-bridge capability at all. It should be documented as a **LiveView/web-owned UI concern** (a Phoenix-rendered transient banner), consistent with §1's "web is the default" posture. If Android's native `Toast.makeText` is wanted for parity, that asymmetry (native on Android, none on iOS) itself would violate Crosswake's honest-support-truth brand — better to keep it entirely web-side or explicit `defer`. |
| 4 | **`UIActivityViewController` crashes on iPad when no `sourceView`/`sourceRect`/`barButtonItem` is set on its `popoverPresentationController`.** This is one of the most common "works on iPhone simulator, crashes on iPad in production" bugs in iOS. | [UIPopoverPresentationController crash writeup](https://topofstacksoftware.com/2016/04/uiactivityviewcontroller-crashing-on-ios8-ipads/), [agilebits/onepassword-app-extension#147](https://github.com/agilebits/onepassword-app-extension/issues/147). | The `share` command's native-side reference implementation (and any generated shell scaffold) must set `sourceView`/`sourceRect` unconditionally, anchored to the triggering UI element (nav-bar button rect or tapped view frame) — never conditionally. Add this as a **merge-blocking** proof check in the shell-core CI (a device-class matrix run that includes iPad), not just advisory, since it is a guaranteed crash, not a degraded experience. |
| 5 | **No reliable "did the user actually share/complete the action?" callback from the OS share sheet — `completionWithItemsHandler` reports UI dismissal, not delivery success**, and Capacitor's own `Share.canShare()` only reports *capability*, not outcome. | [Capacitor Share plugin issues](https://github.com/ionic-team/capacitor-plugins/issues/747), [Capacitor Share API docs](https://capacitorjs.com/docs/apis/share) (canShare returns capability only). | The `share.invoke` reply payload must be honestly scoped to `"sheet_dismissed"` / `"presented"` + which activity type the user picked if the OS reports it (iOS does report `activityType` on completion) — never a semantic `"shared successfully"` claim Crosswake can't back. Docs must state this limitation explicitly next to the command, same posture as `permissions.status`'s "does not prove X" table. |
| 6 | **Generic plugin-catalog version skew** (JS shim version vs. native plugin version silently diverging, requiring a `doctor`-style reactive diagnosis). | Capacitor 6 plugin-registration breaking change causing "not implemented" regressions — [ionic-team/capacitor#7443](https://github.com/ionic-team/capacitor/issues/7443); Cordova plugin-rot as the #1 cited migration reason — [Cordova 2023 survey](https://cordova.apache.org/announcements/2024/01/12/survey-results.html). | Already structurally prevented by Crosswake's `native_runtime_version` + `compatibility_mismatch` fail-closed check in the bridge envelope — Pack 1 must not weaken this by letting any new command skip the envelope's compatibility check "because it's just a simple one." Explicitly re-verify each new Pack 1 command exercises `compatibility_mismatch` in its test matrix. |
| 7 | **Native-module-missing crash instead of graceful denial** (RN's `TurboModuleRegistry.getEnforcing()` intentionally crashes hard on JS/native binary skew). | [facebook/react-native#47352](https://github.com/facebook/react-native/issues/47352), [react-native-maps#5425](https://github.com/react-native-maps/react-native-maps/issues/5425). | Confirms (does not require new work) that Crosswake's existing `undeclared_capability`/`unavailable_capability` typed-deny path is the correct opposite behavior — call out in PITFALLS.md as "known-good, keep doing this" rather than a new guard. |
| 8 | **Play Core monolithic library deprecation** broke apps that pinned old `com.google.android.play:core` review APIs; the in-app review API moved to a dedicated `com.google.android.play:review` artifact with different import paths. | [Play Core release notes](https://developer.android.com/reference/com/google/android/play/core/release-notes), [migration writeup](https://medium.com/mobile-innovation-network/migration-from-the-play-core-library-3ce3d3bda03d). | Shell-core's Android dependency for the review-evidence capability must pin the modern `com.google.android.play:review`/`review-ktx` artifact from day one (not the deprecated monolithic `play-core`), and the support-matrix should record the artifact + version explicitly so a future Play Core-style split doesn't silently orphan Crosswake's shell. |
| 9 | **Haptics on budget Android hardware silently degrade** — many low-end devices use ERM motors that ignore amplitude/pattern entirely, so a "sharp double-tap" haptic pattern plays as one dull buzz, and system settings (Settings > Sound & vibration off, Do Not Disturb) or iOS Low Power Mode silently no-op the Taptic Engine with **no error returned**. | [Android haptics API reference](https://developer.android.com/develop/ui/views/haptics/haptics-apis), community writeup on ERM vs. LRA hardware differences — [Newly haptics guide](https://newly.app/sensors/haptics-mobile-apps). | `haptics.impact` reply must not promise pattern fidelity — docs should say "the OS decides whether/how this renders; a no-op is indistinguishable from a played-but-unfelt haptic." Do not add new haptic *pattern* variety in Pack 1 beyond what's already shipped (`impact`) — expanding pattern vocabulary increases the overclaim surface without adding provable value. |

## 4. Per-Control Platform-Policy Truth Table

This is the load-bearing artifact. "Guarantees" = what the OS contract actually promises; "Does NOT guarantee" = what an honest API must refuse to claim; "Honest API can promise" = the only truthful reply shape.

| Control | OS guarantees | OS does NOT guarantee | Honest API can promise | Honest API must NOT promise |
|---|---|---|---|---|
| **Review prompt** (`SKStoreReviewController.requestReview` / Play `ReviewManager.launchReviewFlow`) | The OS will *consider* showing a native rating UI when invoked at an appropriate time, subject to an internal, undisclosed, per-app/per-user rolling quota (iOS: capped at "up to 3 times per app per year" per widely corroborated developer reports; Android: an explicitly undocumented, Google-controlled "time-bound quota" — [Android docs](https://developer.android.com/guide/playcore/in-app-review): *"the specific value of the quota is an implementation detail, and it can be changed by Google Play without any notice"*). | Whether the prompt appeared at all. Whether the user rated/reviewed. Whether a rating dialog vs. nothing was shown. Any completion/result callback with semantic meaning ([Apple docs](https://developer.apple.com/documentation/storekit/skstorereviewcontroller/requestreview()); [Android docs](https://developer.android.com/guide/playcore/in-app-review) both confirm no submission-status signal exists). | `"requested"` — i.e., "Crosswake asked the OS to consider showing the native prompt." That is the entire truthful contract. | `"shown"`, `"displayed"`, `"user rated"`, `"success"`, or any callback implying the app knows the outcome. Also must not expose this as a tappable "Rate us" affordance per both platforms' explicit guidance against CTA-triggered calls. |
| **Toast** | Android: `Toast.makeText(...).show()` is a real system-level transient overlay. iOS: **no system toast primitive exists at all.** | Cross-platform parity of any kind. On iOS, "toast" is not an OS concept, so no native guarantee can exist to honestly proxy. | On Android only: "a system toast was requested" (fire-and-forget, no confirmation of on-screen duration/visibility either, since Android toasts can be suppressed by DND/battery optimizations on some OEM skins). On iOS: none — should not exist as a *native* bridge capability. | Cross-platform "shows a toast" claim. Any implied guarantee that a toast is visible/read (neither OS confirms this). |
| **Alert / confirm** | Both platforms provide a real native modal (`UIAlertController` / Android `AlertDialog`) that blocks input to the rest of the screen until dismissed, and *does* return the user's choice synchronously to the caller — this is the one control in Pack 1 with a genuinely strong OS guarantee. | That the user read/understood the content — HIG explicitly frames alerts as a **last resort**, not a general-purpose control: *"do people really need to know this, and do they need to know this now [...] if the answer [...] is not an absolute resounding yes, do not interrupt"* ([Apple HIG: Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)). | The user's explicit choice among presented options (this is a genuine, provable native contract, unlike review/toast). | That using a *native* alert instead of an in-page LiveView modal changes anything about correctness — see the skeptical JTBD discussion below. |
| **Menu / action-button** | iOS `UIMenu`/`UIContextMenuInteraction` and Android `ActionMode`/overflow menu both guarantee: menu renders using system chrome, respects OS-level text size/dark mode/accessibility settings automatically, and returns exactly the item the user tapped. | That the menu placement (nav-bar vs. contextual/long-press vs. overflow) is visually identical across platforms — Hotwire Native's own menu component explicitly renders as a **native bottom sheet** on the platform's chosen idiom rather than a shared cross-platform shape ([SupeRails Hotwire Native UIMenu writeup](https://blog.superails.com/hotwire-native-ui-menu-dropdown)). | "One of these N declared items was selected" (an index/id), with the actual visual affordance left to platform-idiomatic rendering (nav-bar button + UIMenu on iOS, overflow/DropdownMenu on Android) rather than a pixel-identical spec. | A single prescribed visual placement that's identical on both OSes — that would fight platform HIG conventions and is not what Hotwire Native or either platform's own guidance recommends. |
| **Haptics** | Both platforms guarantee the API call itself does not throw and requires no runtime permission dialog (Android's `VIBRATE` is a manifest-only, non-dangerous permission — no user prompt) ([Android haptics API reference](https://developer.android.com/develop/ui/views/haptics/haptics-apis)). | That the device physically vibrates or that the pattern is felt as designed. Silently no-ops under: iOS Low Power Mode, iOS "System Haptics" disabled in Settings, Android "Vibration & haptics" disabled, Do Not Disturb, or on budget Android hardware with ERM (not LRA) motors that flatten all patterns to one buzz. | "Crosswake requested this haptic pattern from the OS." | That the user felt anything, or that pattern fidelity (double-tap vs. single, sharp vs. soft) survived to the hardware — no OS API reports actual actuation. |
| **Share sheet** | `UIActivityViewController` / Android `ACTION_SEND` intent chooser both guarantee: presents the system's registered share targets and returns control to the app when dismissed; iOS additionally reports which `activityType` (app/extension) was used if the user completed a share (`completionWithItemsHandler`). | Whether the recipient action described by the target activity actually completed (e.g., message actually sent, not just "Messages" was tapped) — that's the target app's business, invisible to the caller. Also does NOT guarantee no-crash on iPad unless the caller sets `sourceView`/`sourceRect` (footgun #4 above — this is an app-side obligation, not something the OS provides for free). | "Sheet presented" + optionally "user picked target X" (iOS) / "intent chooser resolved" (Android, no activity-type granularity guaranteed by the OS the same way). | "Content was successfully shared/delivered" — no OS on either platform confirms downstream delivery. |
| **`permissions.status` (notifications alias)** | Reading current OS-reported authorization status (`UNAuthorizationStatus` / Android `NotificationManagerCompat.areNotificationsEnabled()`) is synchronous, side-effect-free, and accurate **at the instant of the call**. | That the status remains valid after the call returns — a user can flip the OS setting in Settings at any time without the app being notified; this is a snapshot, not a subscription. Already correctly scoped in Crosswake's own docs ("prompt-free... snapshot rather than delivery truth" — `guides/capabilities.md`). | "As of this call, the OS reports status X." | Any implication of a live/subscribed value, or that a `granted` snapshot guarantees notifications will actually be delivered (delivery also depends on APNs/FCM reachability, which this call cannot see). |
| **`notification_token` evidence surface** | Reading the current device push token (APNs token / FCM token) the OS has issued to this app install, if any, is a snapshot read with no side effects. | That the token is currently valid/routable (tokens rotate silently on reinstall, OS updates, or backup-restore); that possessing the token means the backend can successfully deliver (requires the backend's own APNs/FCM plumbing, entirely outside Crosswake's evidence surface — hence "companion," not "core," per `guides/capabilities.md`). | "As of this call, the shell holds token value X (or none)" — a provider-explicit evidence snapshot. | Any delivery guarantee, or that the token is durable/reusable indefinitely — must be documented as a point-in-time evidence artifact only, exactly matching the existing `capabilities.md` framing ("prompt-free, provider-explicit evidence snapshot rather than delivery truth"). |

### Is a native alert/confirm actually worth it vs. an in-page LiveView modal? (steelmanned both sides)

**Case for native:** A true native `UIAlertController`/`AlertDialog` blocks the entire screen including system chrome, cannot be dismissed by a background LiveView re-render or a lost WebSocket reconnect, and is the one Pack-1 control with a hard OS-level modal guarantee (see table above) — useful specifically for **destructive confirmation on an offline island or a route mid-transition**, where a LiveView-rendered modal's DOM could be torn down by the very navigation event it's supposed to gate. This is a real, narrow JTBD: confirming irreversible actions across a runtime-ownership boundary (e.g., "discard local draft before this offline island hands the route back to LiveView").

**Case against (cargo-cult risk):** For any route that stays fully LiveView-owned and online, an in-page LiveView `<.modal>` is strictly better UX (matches web app chrome/branding, no native round-trip latency, works identically in browser preview) and this is a big share of actual Crosswake routes (`plain :live_view` and even `:live_view with one bounded bridge affordance` per `route_policy.md`). Hotwire Native's own posture — web is the default, native is an enhancement only where it adds something the web genuinely cannot — argues that native alert should be scoped *narrowly* to the "boundary-crossing confirmation" case, not offered as a general-purpose alternative to a LiveView modal.

**Recommendation:** Ship native `alert`/`confirm` scoped explicitly to destructive/irreversible confirmations at **runtime-ownership boundaries** (offline island → back to LiveView, native screen exit, transfer cancellation) — document the JTBD narrowly in the capability guide so adopters don't reach for it as a default confirm() replacement for ordinary in-page interactions.

---

## 5. Wedge Recommendation

**Ship, in this order: (1) haptics pattern completeness (already shipped, low new risk — skip), (2) menu/action-button, (3) share sheet, (4) alert/confirm scoped to boundary-crossing confirmations.**

Defer or narrow-scope: **toast** (no native OS primitive on iOS — push to LiveView/web-owned UI, not a bridge capability) and **review prompt** (real Pack-1 candidate, but ship last and with the most defensive docs, since it's the single highest brand-risk control — any hint of an overclaiming API is a direct violation of "honest support truth").

### Top 5 footguns for the milestone plan

1. Review prompt exposed as a button/CTA or with a "shown"/"success" reply — both platforms explicitly warn against this ([Android docs](https://developer.android.com/guide/playcore/in-app-review), [Apple docs](https://developer.apple.com/documentation/storekit/skstorereviewcontroller/requestreview())). Must ship as `"requested"`-only, non-CTA-triggerable.
2. `UIActivityViewController` iPad crash from missing `sourceView`/`sourceRect` — a guaranteed crash, not a degraded experience; must be a merge-blocking iPad-class CI check, not advisory ([citation](https://github.com/agilebits/onepassword-app-extension/issues/147)).
3. Treating "toast" as a native capability when iOS has no such OS primitive at all — category error, not a degradation; keep it web/LiveView-owned.
4. Share sheet reply overclaiming delivery/completion when the OS only reports sheet dismissal (+ optionally which target app was picked on iOS) — [Capacitor Share issue thread](https://github.com/ionic-team/capacitor-plugins/issues/747).
5. Review-prompt timing (first-launch/onboarding placement) risking App Store rejection under anti-manipulation/Guideline 5.6.3 — must be documented as a route-reachability advisory in doctor/support-matrix ([RevenueCat writeup](https://www.revenuecat.com/blog/engineering/dont-prompt-ratings-during-onboarding/)).
