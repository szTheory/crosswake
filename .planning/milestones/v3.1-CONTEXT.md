# Project Description

Crosswake is expanding its official native capability support. After locking the packaging and contract rubrics in v3.0, this milestone (v3.1) focuses on shipping the first set of low-frequency, high-DX native capability families (`haptics`, `share`, `app_info`, `deep_link`, `permissions.status`, `notification_token`, and `file_picker`) that strictly fit the established bounded bridge thesis.

# Why This Milestone

Milestone v3.0 successfully established the capability taxonomy, packaging ledgers, and support contracts. With these guardrails in place, v3.1 is the natural next step to reduce bespoke native glue for adopters. By providing these common capabilities out-of-the-box, we deliver immediate value to Phoenix teams without compromising the project's architectural integrity or collapsing it into a universal app framework.

# User-Visible Outcome

Phoenix developers can declare capabilities like `haptics`, `share`, or `file_picker` in their route policies and invoke them directly from LiveView or native screens via the bridge. Operators will see accurate diagnostics from `mix crosswake.doctor` if their native shell lacks the required permissions or versions to support these newly added capabilities.

# Completion Class

Integration and Contract.

# Final Integrated Acceptance

- The 7 target capability families can be successfully invoked from a host Phoenix application connected to the checked-in iOS and Android example shells.
- Attempting to use a capability on an unauthorized route or without the required platform permissions explicitly fails closed and is accurately diagnosed by the doctor tool.

# Architectural Decisions

### Bounded Low-Frequency Affordances Only
We are explicitly restricting this milestone to low-frequency bridge commands (e.g., triggering a share sheet, picking a file, requesting a token) rather than continuous high-frequency streams (like real-time sensor data).
*Rationale:* This maintains the semantic, typed, versioned nature of the bridge without turning Crosswake into a high-overhead event bus.

### Fail-Closed Default
Missing permissions or capability mismatches will immediately deny the capability execution rather than silently failing.
*Rationale:* Keeps the architectural boundaries honest and debugging straightforward.

# Error Handling Strategy

Errors at the native boundary (e.g., user denies file permission) must be passed back through the bridge envelope as structured, typed errors. Route-policy rejections must occur synchronously on the host before the command is even emitted. Operator errors (missing shell permissions) must be clearly flagged by the doctor tool.

# Risks and Unknowns

- **Permissions matrix complexity:** Handling OS-level permission lifecycles (especially `file_picker` and `notification_token` on newer Android/iOS versions) may require nuanced fallback behaviors that stretch the current doctor logic.

# Existing Codebase / Prior Art

- `lib/crosswake/bridge/` — The existing typed bridge envelope that will transport these commands.
- `lib/crosswake/policy.ex` — The route policy engine that will authorize the new capability families.
- `lib/crosswake/doctor/` — The diagnostic tool that must be expanded to cover the new prerequisites.

# Relevant Requirements

- Extend capability ladder with concrete native affordances.
- Platform support matrix must be updated by shell version.
- Doctor output handles missing prerequisites for the new families.

# Scope

**In Scope:**
- Capability implementations for: `haptics`, `share`, `app_info`, `deep_link`, `permissions.status`, `notification_token`, `file_picker`.
- Route-local allowlist enforcement for all new capabilities.
- Platform support matrix updates and doctor diagnostics for these families.

**Out of Scope:**
- Real-time sensor/control bridges (e.g., accelerometer stream).
- Broad scanning or custom camera media workflows (these belong in native-screen ownership).
- First-party push notification delivery integration (we are only generating/passing the token in this milestone).

# Technical Constraints

- Must maintain compatibility with iOS and Android native shell architectures.
- The new capabilities must not violate the single-runtime ownership per-route rule.

# Integration Points

- iOS Native Shell (`CrosswakeShell`) bridge handlers.
- Android Native Shell (`android_shell_host`) bridge handlers.
- Host Phoenix Application capability registry and route policy DSL.

# Testing Requirements

- **Unit:** Route-local allowlist tests for the new capability keys.
- **Integration:** Platform support matrix tests verifying shell version compatibility.
- **Operational:** Doctor output tests ensuring missing permissions correctly flag as errors.
