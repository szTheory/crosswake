# Requirements: Crosswake

**Defined:** 2026-05-27
**Core Value:** Make runtime boundaries explicit so Phoenix teams can ship credible mobile apps without hiding the tradeoffs between LiveView, offline, and native ownership.
**Milestone:** v3.2 Commerce And Entitlement Seams

## Milestone Gates

### Capability Selection Rubric

| Capability family | Route-owner expectation | Bridge frequency | Permission / policy sensitivity | Support-matrix impact | Proof required | Package classification |
|-------------------|-------------------------|------------------|---------------------------------|-----------------------|----------------|------------------------|
| `paywall_entry` | Phoenix-owned route by default; native corridor only for storefront-sensitive presentation | Low-frequency semantic | High policy sensitivity | Requires commerce prerequisite and fallback truth | Merge-blocking route/manifest/denial proof | `core` seam, companion-ready native presentation |
| `purchase_intent` | Native-screen or companion corridor for storefront confirmation; Phoenix owns intent and reconciliation | Low-frequency semantic evidence | High | Requires native rebuild/provider prerequisite truth | Merge-blocking contract proof; advisory StoreKit/Play Billing proof | `core` seam plus `companion` adapters |

### Packaging Ledger

| Surface | Classification | Scope note |
|---------|----------------|------------|
| Commerce route/corridor declarations | `core` | Core owns normalized route vocabulary and fail-closed validation. |
| Commerce contract lifecycle vocabulary | `core` | Core owns normalized purchase/restore/reconciliation/snapshot semantics. |
| Phoenix reconciliation inbox and entitlement projection example | `example/docs-only` with companion-ready boundaries | Proves backend-owned truth without imposing storage or job framework choices. |
| Native storefront command/event contracts | `companion` by default | Native SDK loops, provider callbacks, and platform UI stay outside core. |
| StoreKit, Play Billing, RevenueCat, Accrue, or other provider adapters | `companion` or future milestone | Provider logic follows the seam; it does not define it. |
| Reviewer/storefront sandbox playbooks | `example/docs-only` | Required support truth, not runtime support claims. |

### Commerce Scope Guard

- Crosswake core normalizes route/corridor declarations, purchase/restore intents, reconciliation evidence, and entitlement snapshots.
- Entitlement truth lives in Phoenix/backend systems; device callbacks and storefront SDK events are evidence inputs only.
- StoreKit, Play Billing, provider SDKs, webhook verification clients, acknowledgement/consumption calls, and paywall SDK UIs remain adapter- or provider-specific.
- Storefront-sensitive purchase confirmation, restore choreography, redeem/offer-code flows, and provider session loops require explicit native-screen or companion posture.
- Crosswake must fail closed when commerce prerequisites are missing and must not imply web checkout fallback for digital goods.

## Milestone v3.2 Requirements

### Commerce Route Corridors (`core`)

- [x] **COMM-04**: Phoenix teams can declare commerce-sensitive routes that distinguish Phoenix-owned paywall/account surfaces from native-screen or companion-owned storefront loops.
- [x] **COMM-05**: Crosswake can render commerce route/corridor declarations into manifest and support truth without exposing provider-specific route-policy vocabulary.
- [x] **COMM-06**: Unsupported or undeclared commerce corridors fail closed with explicit denial/fallback reasons instead of silent WebView or bridge fallback.

### Entitlement Lifecycle Semantics (`core`)

- [x] **ENTL-01**: Phoenix teams can model entitlement snapshots with authority state, access state, reconciliation state, freshness, effective dates, and bounded evidence metadata.
- [x] **ENTL-02**: Crosswake distinguishes pending purchase, pending restore, awaiting verification, grace/billing retry, canceled scheduled end, revoked/refunded, expired, and stale snapshot states without leaking raw provider enums.
- [x] **ENTL-03**: Device, storefront, webhook, and support evidence can feed reconciliation but cannot directly grant entitlement authority in core contracts.

### Reconciliation Example (`example/docs-only`, companion-ready)

- [x] **RECN-01**: Host apps can follow a minimal Phoenix-owned reconciliation inbox example for purchase, restore, webhook, and support evidence.
- [x] **RECN-02**: Host apps can follow idempotency guidance that uses provider-aware identity rather than transient device correlation IDs.
- [x] **RECN-03**: Host apps can project one authoritative entitlement snapshot from verified evidence and expose stale, pending, denied, and granted states clearly.

### Commerce Support And Proof (`core` support truth)

- [x] **SUPP-04**: Doctor and support-matrix output identify missing commerce prerequisites, unsupported native corridors, stale entitlement snapshots, and native rebuild requirements.
- [x] **SUPP-05**: Public commerce guidance explains reviewer/storefront sandbox setup, restore expectations, fallback behavior, and rough edges without implying provider adapters have shipped.
- [x] **SUPP-06**: Maintainers can run merge-blocking hermetic commerce proof while treating StoreKit/Play Billing simulator, device, or storefront checks as advisory until adapter milestones ship.

## Future Requirements

### Provider And Companion Adapters

- **ADPT-01**: Crosswake or a first-party companion ships StoreKit adapter support for storefront purchase, restore, server verification, and App Store Server Notifications.
- **ADPT-02**: Crosswake or a first-party companion ships Play Billing adapter support for purchase flow, purchase-token verification, acknowledgement, and Real-time Developer Notifications.
- **ADPT-03**: Crosswake or a first-party companion integrates with `accrue` or a similar Phoenix commerce library after the core seam is validated.

### Commerce Archetype Proof

- **ARCH-02**: Crosswake re-runs an adopter-shaped subscription/paywall proof lane using the v3.2 seam and at least one provider-aware adapter or mocked storefront corridor.

### Companion And Operator Expansion

- **COMP-05**: Crosswake ships commerce-adjacent first-party companion integration only after package boundaries and rebuild truth are proven.
- **OPS-01**: Crosswake provides richer operator inspection for entitlement snapshots, reconciliation attempts, and commerce route support truth.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Universal billing engine in core | Conflicts with backend-owned Phoenix truth and provider-specific lifecycle complexity |
| StoreKit or Play Billing adapter implementation in core | Provider SDKs belong in companion or future adapter milestones |
| Device-local entitlement authority | Device callbacks are evidence, not final access truth |
| Offline purchase replay granting permanent access | Commerce requires online verification before durable entitlement changes |
| Generic provider plugin bus | Crosswake preserves typed, versioned, route-local seams |
| Silent web checkout fallback for unsupported native commerce | Digital goods and storefront policy require explicit native/companion posture |
| Broad companion rollout in v3.2 | This milestone validates the commerce seam before widening companion breadth |
