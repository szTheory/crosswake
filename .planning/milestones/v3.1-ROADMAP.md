# Milestone v3.1: Native Capabilities and Bridge Expansion

**Status:** ◆ ACTIVE
**Phases:** 15-18
**Total Plans:** 11 planned

## Overview

Crosswake is expanding its official native capability support. After locking the packaging and contract rubrics in v3.0, this milestone focuses on shipping the first set of low-frequency, high-DX native capability families (`haptics`, `share`, `app_info`, `deep_link`, `permissions.status`, `notification_token`, and `file_picker`) that strictly fit the established bounded bridge thesis.

## Phases

### Phase 15: Base Capability Bridges (Haptics, Share, App Info)

**Goal**: Implement the simplest low-frequency stateless capabilities to establish the bridge pattern for v3.1.
**Depends on**: Milestone v3.0
**Plans**: 3 plans
**Requirements**: `CAP-HAPTICS`, `CAP-SHARE`, `CAP-APPINFO`

Plans:

- [ ] 15-01: Implement `haptics` across iOS, Android, and Phoenix host registries.
- [ ] 15-02: Implement `share` across iOS, Android, and Phoenix host registries.
- [ ] 15-03: Implement `app_info` across iOS, Android, and Phoenix host registries.

**Success criteria:**
1. The 3 base capabilities can be successfully invoked from a host Phoenix application.
2. The capabilities map perfectly to the established bounded bridge schema.

### Phase 16: System Context Bridges (Deep Link, Permissions Status)

**Goal**: Implement capabilities that query or pass system context without requiring user prompts.
**Depends on**: Phase 15
**Plans**: 2 plans
**Requirements**: `CAP-DEEPLINK`, `CAP-PERMSTATUS`

Plans:

- [ ] 16-01: Implement `deep_link` handling and capability bridge.
- [ ] 16-02: Implement `permissions.status` querying bridge for checking capabilities before use.

**Success criteria:**
1. Deep links correctly traverse the native shell into Phoenix.
2. The Phoenix app can accurately query the permissions status from the native host.

### Phase 17: User-Prompted Capabilities (Notification Token, File Picker)

**Goal**: Implement complex capabilities that involve asynchronous OS-level user permission flows.
**Depends on**: Phase 16
**Plans**: 2 plans
**Requirements**: `CAP-NOTIFTOKEN`, `CAP-FILEPICKER`

Plans:

- [ ] 17-01: Implement `notification_token` bridge to request and return APNs/FCM tokens.
- [ ] 17-02: Implement `file_picker` bridge to handle OS file selection and return typed results.

**Success criteria:**
1. The Phoenix app can trigger file pickers and receive the structured typed results safely.
2. The Phoenix app can trigger token requests and receive the push tokens successfully.

### Phase 18: Operational Diagnostics and Enforcement

**Goal**: Extend route policies, doctor tools, and the support matrix to enforce the new v3.1 capabilities.
**Depends on**: Phase 17
**Plans**: 4 plans
**Requirements**: `OPS-ALLOWLIST`, `OPS-DOCTOR`, `OPS-SUPPORT`

Plans:

- [ ] 18-01: Add route-local allowlist enforcement for all new v3.1 capability keys in the policy engine.
- [ ] 18-02: Extend `mix crosswake.doctor` to handle missing OS permissions and shell capability mismatches.
- [ ] 18-03: Update the platform support matrix documentation and verify error handling behaves as fail-closed.
- [ ] 18-04: Execute final integrated acceptance test across the 7 target capability families.

**Success criteria:**
1. Attempting to use a capability on an unauthorized route or without the required platform permissions explicitly fails closed and is accurately diagnosed by the doctor tool.
2. Final end-to-end integration is proven using the generated Android and iOS shell tests.

## Milestone Summary

**Requirements mapped:** 8/8 complete in roadmap coverage terms
**Coverage:** All active milestone requirements mapped exactly once ✓

**Key sequencing decisions:**

- Group the simplest capabilities first (Phase 15) to warm up the bridge wiring.
- Separate user-prompted capabilities (Phase 17) since they introduce complex OS-level asynchronous lifecycles.
- Consolidate all diagnostics, allowlisting, and documentation into the final phase (18) once all capabilities are functioning, ensuring comprehensive coverage of the final fail-closed mechanisms.
