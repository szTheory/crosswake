# Phase 48.1: Close gap: ADPT-01/ADPT-02 - provider facade paywall swap-target contract - Context

**Gathered:** 2026-06-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the milestone-audit blocker where the example-host provider facade cannot
be configured as the existing paywall storefront adapter.

**Delivers:**
- A real storefront adapter contract for the example-host paywall corridor.
- `ProviderAdapterStorefront` compatibility with the `PaywallEntryLive`
  purchase/restore swap target.
- Explicit StoreKit/Play Billing provider selection that stays outside the
  LiveView UI layer.
- Merge-blocking proof that provider evidence enters the existing
  reconciliation path and remains non-authoritative until backend projection.

**In scope:**
- Example-host adapter contract closure for ADPT-01 and ADPT-02.
- Hermetic proof for configured provider facade purchase/restore flow.
- Minimal docs/support wording if needed to lock the swap-target contract and
  evidence-only authority boundary.

**Out of scope:**
- New provider adapters beyond StoreKit and Play Billing.
- Device-local entitlement grants.
- Hidden platform/provider inference from request params or shell context.
- Provider/device/storefront proof promotion beyond the existing ADPT-03 rules.
- Full diagnostic auto-registration for companion modules; the audit noted it
  as tech debt, not the ADPT-01/ADPT-02 blocker.

</domain>

<decisions>
## Implementation Decisions

### 1. Storefront Adapter Contract - LOCKED
- **D-01:** Define an explicit example-host storefront adapter contract for
  `simulate_purchase/1` and `simulate_restore/1`. The contract should be
  behaviour-backed or equivalently compiler-visible so future facades cannot
  repeat the current mismatch.
- **D-02:** Prefer typed result callbacks:
  `simulate_purchase(Contracts.PurchaseIntent.t()) ::
  {:ok, Contracts.ReconciliationEvidence.t()} | {:error, term()}` and the same
  shape for restore. This is more durable than preserving the current direct
  evidence return because provider normalizers already return tagged results and
  provider failures must fail closed.
- **D-03:** Update `PaywallEntryLive` only enough to consume the typed result
  contract and keep the existing Phoenix-owned reconciliation path. It should
  not branch on StoreKit vs Play Billing and should not interpret provider
  statuses as entitlement authority.
- **D-04:** Keep `MockStorefront` as the default adapter, updated to satisfy the
  same explicit contract. The mock remains pure Elixir and provider-neutral.

### 2. Provider Selection - LOCKED
- **D-05:** Use a closed provider selection contract, not hidden inference. The
  provider vocabulary is `:storekit | :play_billing` and must map to the existing
  closed `Crosswake.Commerce.ProviderEvidence` provider vocabulary.
- **D-06:** Strong default: keep `ProviderAdapterStorefront` as the single
  ergonomic paywall swap target and have it delegate to explicit provider-owned
  wrapper modules or private dispatch branches based on runtime app config, for
  example `config :crosswake_example, :paywall_storefront_provider, :storekit`.
- **D-07:** Do not pass provider choice from `PaywallEntryLive` event handlers.
  The LiveView owns paywall UI and intent creation; provider ownership belongs
  at the adapter boundary.
- **D-08:** Do not auto-select the provider from route/platform context in this
  closure phase. That would add hidden behavior, weaker hermetic tests, and
  ambiguity for web/dev environments. If future mobile shell context becomes
  authoritative, it should be a later explicit phase.
- **D-09:** Invalid or missing provider configuration for the provider facade
  must fail closed with a typed error, not silently fall back to mock and not
  grant access.

### 3. Proof And Documentation - LOCKED
- **D-10:** Add merge-blocking hermetic proof for the exact audit gap:
  configuring `ProviderAdapterStorefront` as the paywall storefront adapter must
  drive both purchase and restore through the existing `PaywallEntryLive`
  callback path into `ReconciliationInbox`.
- **D-11:** The proof must assert authority boundaries, not just function
  existence: provider evidence is accepted as reconciliation evidence, immediate
  state is pending/awaiting verification, and access becomes granted only after
  backend-owned projection refresh.
- **D-12:** Tests should cover both StoreKit and Play Billing provider choices
  against the same public storefront adapter contract. Testing only
  provider-specific helper functions is insufficient because that is the gap the
  audit found.
- **D-13:** Add docs-contract or guide assertions only where they protect public
  support truth: the provider facade is a paywall swap target, the default mock
  remains default, and StoreKit/Play Billing seams emit evidence only.
- **D-14:** Keep provider/device/storefront lanes advisory until existing
  promotion criteria pass. Green sandbox/device runs must not close this
  phase's merge-blocking proof requirement by themselves.

### 4. Ecosystem Lessons Applied - LOCKED
- **D-15:** Follow the Elixir/Phoenix/Plug/Ecto idiom of explicit module
  contracts plus explicit runtime config. Behaviours and callbacks should name
  required functions; runtime app config is appropriate for deploy-time choices;
  per-request UI branching is not the right place for provider ownership.
- **D-16:** Apply the billing ecosystem lesson from Apple and Google: provider
  transaction identifiers and purchase tokens are evidence for backend
  verification/reconciliation, not client-side entitlement authority.
- **D-17:** Apply the Crosswake prompt-corpus lesson: native/provider breadth is
  safe only when route ownership, typed boundaries, support truth, and proof
  class stay explicit.

### the agent's Discretion
- Exact module names are planner discretion. Strong defaults:
  `CrosswakeExample.Commerce.StorefrontAdapter` for the behaviour and either
  explicit wrapper modules such as
  `CrosswakeExample.Commerce.StoreKitStorefront` /
  `CrosswakeExample.Commerce.PlayBillingStorefront`, or private dispatch inside
  `ProviderAdapterStorefront` if that keeps the closure smaller.
- Exact config key names are planner discretion if provider selection remains
  closed, explicit, and runtime-configurable.
- Exact docs anchors are planner discretion. Prefer stable semantic assertions
  over brittle prose snapshots.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `PaywallEntryLive.storefront_adapter/0` already provides the exact config
  swap point: `config :crosswake_example, :paywall_storefront_adapter,
  YourAdapterModule`.
- `MockStorefront` already models the desired public adapter callbacks and the
  provider-neutral downstream path, but currently returns raw evidence instead
  of tagged results.
- `ProviderAdapterStorefront` already builds correct StoreKit and Play Billing
  `ReconciliationEvidence`; the gap is public contract shape and provider
  selection, not normalizer correctness.
- `ReconciliationInbox`, `ReconciliationKeys`, `EntitlementProjection`, and
  `MockBackend` already prove the backend-owned authority path.

### Established Patterns
- Crosswake prefers closed vocabularies, typed structs, and fail-closed optional
  surface behavior.
- Provider/device/storefront proof stays advisory until explicit promotion
  criteria pass; hermetic contract proof stays merge-blocking.
- Public docs/support claims derive from canonical truth and are locked with
  docs-contract tests when a claim could drift.
- Example-host proof should use the adopter-facing path, not only internal
  provider helper functions.

### Integration Points
- `ProviderAdapterStorefront` must become configurable as
  `:paywall_storefront_adapter`.
- `PaywallEntryLive.handle_event("subscribe" | "restore")` must handle the
  adapter result shape and keep the existing pending/error UX.
- Provider selection config must feed `ProviderAdapterStorefront` without
  leaking provider choice into LiveView params/session.
- Phase 48 proof should gain a Phase 48.1 closure assertion or a new Phase 48.1
  proof test that directly targets the audit gap.

</code_context>

<specifics>
## Specific Ideas

- The user explicitly selected all gray areas and requested subagent-backed
  research with one cohesive recommendation set instead of a broad option menu.
- Research converged on: explicit storefront adapter contract, closed
  provider-config facade with wrapper/delegation, and hermetic swap-target proof
  plus selective docs-contract lock.
- Developer ergonomics goal: adopters should be able to read one callback
  contract and one config example and understand how to swap mock, StoreKit, or
  Play Billing without learning provider internals in the LiveView.

</specifics>
