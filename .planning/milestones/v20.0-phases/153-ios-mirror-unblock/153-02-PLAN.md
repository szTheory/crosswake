  <how-to-verify>
    **Step 4 — the tag. ⚠️ THIS IS A ONE-WAY DOOR.**

    SwiftPM caches resolved tags aggressively, and both the release job and the backfill script refuse by design to delete or move a published tag. If this lands wrong, the only remedy is a forward release (`v0.2.1`). Never a retag. All safety is pre-push — the verify run in task 2, the dry-run, and the SHA-equality short-circuit. There is no safety after.

    ```
    gh workflow run ios-mirror-backfill.yml \
      -f version=0.2.0 \
      -f release_ref=refs/tags/ios-core-v0.2.0 \
      -f apply=true \
      -f update_main=false
    ```

    Note `update_main=false`. The tag (irreversible) and the `main` re-baseline (reversible) must not ride the same dispatch.

    Post-check — the tag must equal the split SHA you recorded in task 2:
    ```
    git ls-remote --tags https://github.com/szTheory/crosswake-shell-core-ios
    ```
    Expect `refs/tags/v0.2.0` at exactly your recorded SHA, and `refs/tags/v0.1.2` still present at `6417ae65…`.

    The tag push is unaffected by the lineage problem: creating `refs/tags/v0.2.0` is a brand-new ref with no fast-forward constraint. **MIRROR-01 is done at this point.** Stop and confirm before continuing.

    ---

    **Step 5 — the `main` re-baseline. Separately approved. Reversible.**

    Mirror `main` sits on a lineage no tool in this repo can reproduce: the 0.1.2 mirror was finished out-of-band with `git subtree split` after splitsh-lite v2.0.0 404'd mid-job. `main` == `HEAD` == `v0.1.2` == `6417ae65…`, an object this repo has never seen. Left alone, the NEXT release's non-forced `main` push non-fast-forward-rejects, kills the job before the tag push, and reports it as a credential error — misdiagnosing a lineage problem as a token problem for the SECOND time.

    This is safe because the mirror is a pure derived, read-only artifact: nothing depends on its commit SHAs, only on its tags — SwiftPM resolves tags, never branches — and both `v0.1.2` and `v0.2.0` are preserved through the operation. It also fixes the shopfront: GitHub renders `main`'s README, so an adopter's first impression of the package is currently 0.1.2 content for a package that is really 0.2.0.

    ```
    gh workflow run ios-mirror-backfill.yml \
      -f version=0.2.0 \
      -f release_ref=refs/tags/ios-core-v0.2.0 \
      -f apply=true \
      -f update_main=true
    ```

    The tag path short-circuits with "already points at … no push needed" (idempotent — task 2's script change guarantees this), then the `main` push runs with the explicit lease against the value read fresh via `ls-remote`. A concurrent third-party change to `main` aborts it.

    Expect one advisory log line: mirror main is an object unknown to this repository, so ancestry cannot be proven either way. That is the D-08 case, it is expected exactly once, and plan 01 taught the guard to say so rather than fail-close on it.

    Post-checks — all three must hold:
    ```
    git ls-remote https://github.com/szTheory/crosswake-shell-core-ios
    ```
    - `refs/heads/main` == your recorded split SHA
    - `refs/tags/v0.2.0` == your recorded split SHA (UNCHANGED by step 5)
    - `refs/tags/v0.1.2` still resolves to `6417ae65…` — it becomes an orphaned-but-resolvable commit, which is fine: a tag pins its object regardless of branch reachability, so existing 0.1.2 adopters keep working forever.
  </how-to-verify>

  <acceptance_criteria>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator laptop → GitHub API | The deploy key's private half is generated locally and transits to GitHub's secret store |
| CI runner → mirror repo | The first-ever exercise of the CI push credential |
| This repo's git state → mirror's public tag namespace | An irreversible, adopter-visible mutation |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-153-02 | Information Disclosure | Deploy key private half leaked during the D-05 minting ritual (pasted into a terminal arg, committed, or left on disk) | high | mitigate | `gh secret set` reads from stdin, never an argv value; both key halves are removed with `rm -P` immediately after; the private half is never echoed. Task 1 acceptance criteria assert this. |
| T-153-03 | Tampering | Moving the already-published `v0.1.2` tag, breaking every existing iOS adopter's cached resolution | high | mitigate | Structural: the script never forces a tag refspec, and `refs/tags/*` rejects updates to existing refs absent an explicit force. Task 3 asserts `v0.1.2` still resolves to its original object after both dispatches. |
| T-153-05 | Tampering | Pushing `v0.2.0` at the WRONG object (a tag that looks right but carries wrong content) — irreversible, on the one registry whose tags policy forbids moving | high | mitigate | Pre-push only, by construction: task 2's verify run computes and records the split SHA; task 3's post-check asserts the landed tag equals that exact recorded SHA; the script fail-closes on `points at <X>, expected <Y>`. The go/no-go gate (D-09) is a blocking human decision, never auto-advanced. |
| T-153-04 | Tampering | A concurrent third-party change to mirror `main` silently overwritten by the re-baseline | medium | mitigate | Explicit `--force-with-lease` against the value read fresh via `ls-remote`; a mismatch aborts the push. Blast radius is bounded regardless — the mirror is a pure derived artifact and `main` is not what SwiftPM resolves. |
| T-153-06 | EoP | Deploy key minted without `--allow-write`, or minted with broader scope than one repo | medium | accept/mitigate | `--allow-write` scopes the key to git-push on exactly one repo, with no other GitHub API surface. Blast radius shrinks from "every repo szTheory owns" (classic PAT) to one regenerable artifact repo — the mirror is a pure `splitsh-lite` function of this monorepo and can be rebuilt at any time. A missing `--allow-write` surfaces as a task-2 dry-run failure that mutates nothing. |
</threat_model>
