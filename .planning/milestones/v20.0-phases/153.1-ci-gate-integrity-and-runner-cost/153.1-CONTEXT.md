# Phase 153.1 Context: CI Gate Integrity & Runner Cost

**Type:** INSERTED (decimal phase — urgent insertion between Phase 153 and Phase 154)
**Source:** `.planning/seeds/SEED-007-ci-cd-performance.md` — a deliberately narrow slice, not the whole seed.
**Scoped:** 2026-07-28

## Why this is inserted here, and why now

SEED-007 is a `v21.0-or-later` milestone candidate. This phase pulls **three of its seven
requirement categories forward** and leaves the rest planted. The reason is sequencing, not
enthusiasm:

1. **`GATE-*` is a correctness bug, not an optimization.** Three required check *names* are each
   emitted by two different workflows. GitHub branch protection matches required contexts **by
   string**, so it cannot distinguish them — a red `phase132` run can be masked by a green
   `phase130` run wearing the same name. Separately, 20 test files carrying `:requires_example_host`
   are excluded by every CI lane and excluded by no local default, so they run **only on laptops**.
   That is precisely how a genuinely red gate sat on `main` unnoticed until it was found by hand
   this session (fixed in #89). The safety net has holes; the holes are cheap to close.

2. **Phase 154 is the largest phase in v20 and will land many PRs.** The CI tax is paid per-PR and
   compounds under `strict: true`. Paying it across all of Phase 154 and *then* fixing it is
   strictly worse than fixing it first. This phase is inserted before 154 for that reason alone.

3. **The measured tax is large and mechanical to remove.** ~25,500 runner-seconds (~7 h) per push
   to run an 88-second test suite. The cost is macOS **queue** time, and most macOS jobs never
   invoke an Apple toolchain.

## Scope — deliberately narrow

**In:**
- `GATE-*` — de-duplicate colliding required-check names; make the registration script assert
  uniqueness; give `:requires_example_host` a real CI lane; correct the stale audit header.
- `RUNNER-*` — move non-Apple macOS jobs to ubuntu; delete the dead `DEVELOPER_DIR`; add
  `timeout-minutes` everywhere it is missing.
- `CACHE-*` — cache `deps/` and `_build` with correct key dimensions; replace the retired
  `actions/cache@v3`; fix the Gradle cache path.
- A **lightweight before/after measurement** (the seed's `OBS-*`, minimized): capture
  runner-seconds-per-push before Task 1 and after Task 3, so the phase's claim is evidence, not
  assertion. Full `OBS-*` instrumentation stays in the seed.

**Explicitly out — stays planted in SEED-007:**
- `CONSOL-*` (39 workflow files → ~4, composite actions, change detection, required-context
  topology). This is the large, judgment-heavy piece, it interacts with the auto-discovery
  machinery, and it is where the risk lives. It needs its own milestone.
- The merge-queue (`on: merge_group:`) decision — the biggest semantic change to "every proof runs
  on every change." A milestone-activation decision, not a phase decision.
- `FLAKE-*` and `DX-*`.
- **Test sharding is a non-goal and must not be proposed.** 1,093 tests / ~88 s ≈ 12 ms each;
  per-shard setup exceeds execution saved. Ecto measured a 31% regression doing this.

## Sequencing constraint (hard)

**No plan in this phase may begin until the current PR queue has drained.** Seven PRs
(#87, #88, #89, #90, #52, #51, #50) are validating against the workflow files this phase rewrites.
Editing them mid-flight invalidates in-flight runs and, under `strict: true`, re-serializes the
whole queue. Plans run **serially** (Wave 1 → 2 → 3) for the same reason: all three touch
`.github/workflows/`, and parallel execution would conflict and re-invalidate each other.

## The trap that governs every change here

Two mechanisms, **opposite** behavior:

| Mechanism | Status reported | Blocks a required check? |
|---|---|---|
| Workflow-level `paths:` → workflow never runs | **nothing** → "Expected — Waiting for status" | **YES — PR hangs forever** |
| Job-level `if:` → job evaluates, resolves false | `skipped` | **NO — merge allowed** |

**Never add a workflow-level `paths:` filter to any of the 22 required contexts.** This phase does
not add change-detection at all (that is `CONSOL-*`), but the constraint is recorded because every
plan here edits required-context workflows.

## Non-negotiable constraints carried from the seed

- Preserve per-phase proof **job names, logs, and artifacts** — evidence is a product feature in
  this repo. What changes is where a job *runs* and what it *caches*, never what it proves.
- Renaming a required check is a **two-step ritual**: the new name must go green on `main` before
  it can be registered, and the old name must be de-registered. Branch protection cannot be updated
  in the same PR that renames the job. See `script/register_required_checks.sh`.
- `release-please.yml` is security-sensitive (REL-05 SHA pinning, two previously-armed fuses). Its
  concurrency settings (`cancel-in-progress: false`, `queue: max`) are **correct** — do not
  "optimize" them. It is the one workflow that legitimately needs macOS.
- No auto-retry as a flake fix, and never auto-retry a macOS lane.

**Runner classification caveat — read before Plan 02.** A file-level `grep` for
`xcodebuild|simctl|swift build` is **not** a valid classifier. The Apple-toolchain dependency is
often inside a shell script the workflow calls. Confirmed examples: `phase18-proof.yml` and
`phase79-proof.yml` both look pure-Elixir at the workflow level but call
`script/verify_generated_ios_shell.sh`, which hard-requires `xcodebuild` (line 14). Classification
must be **per job, by following every `run:` into the scripts it invokes.**
