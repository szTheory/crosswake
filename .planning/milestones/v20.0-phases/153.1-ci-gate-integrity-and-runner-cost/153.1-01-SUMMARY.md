## What shipped

### GATE-01 — three colliding check names de-duplicated

Three merge-blocking check names were each emitted by **two different jobs**. Branch
protection matches required contexts by *string*, so GitHub could not tell the emitters
apart and a red run could be masked by a green one. The gate failed open while reporting
as fully registered — presence was being checked, uniqueness was not.

Renamed the **later-phase** emitter in each pair, never the already-registered one:

| was | now | file |
|---|---|---|
| `merge-blocking commerce support proof (hermetic)` | `merge-blocking phase34 commerce support proof (hermetic)` | `phase34-proof.yml` |
| `advisory commerce proof (...)` | `advisory phase34 commerce proof (...)` | `phase34-proof.yml` |
| `core hermetic proof (merge-blocking)` | `phase132 core hermetic proof (merge-blocking)` | `phase132-proof.yml` |
| `companion engine-absent proof (merge-blocking)` | `phase132 companion engine-absent proof (merge-blocking)` | `phase132-proof.yml` |
| `companion engine-present proof (advisory)` | `phase132 companion engine-present proof (advisory)` | `phase132-proof.yml` |

Direction chosen so branch protection stayed **continuously valid**: contexts were added,
none de-registered, no window in which `main` was less protected than before.

### GATE-02 — uniqueness asserted, not just presence

- `script/list_merge_blocking_checks.py` gained `--emitters`, printing
  `<context>\t<workflow path>\t<job id>` per emitter, **not de-duplicated**. The default
  output is byte-identical, so no caller changed behaviour.
- `script/check_required_checks_registered.sh` consumes it and fails closed on any name
  emitted more than once, naming both source files.

The assertion runs **before** the `gh api` branch-protection read on purpose: it is a pure
local check on workflow files, so it stays meaningful in CI where no repo-admin token
exists and the registration half exits `3 UNVERIFIED`.

### GATE-03 — `:requires_example_host` got a real CI lane

These tests were excluded by every CI lane (`--exclude requires_example_host`) but

## The bug this plan's own test caught on its first CI run

Both gate scripts used `mapfile`, which is **bash 4.0+**. macOS ships bash 3.2.57 (frozen
at the last GPLv2 release). On all four macOS lanes the scripts died with
`mapfile: command not found` and **exit 127 — before checking anything**.

A gate script that cannot run is indistinguishable from a gate that passes.

It survived because the audit workflow runs on ubuntu, and a maintainer's PATH resolves
`bash` to Homebrew 5.x — only `/bin/bash` is 3.2. Fixed with portable `while IFS= read -r`
loops in both scripts, verified under real `/bin/bash` 3.2.57, and guarded by a regression
test that greps both scripts for `mapfile|readarray`, `declare -A`, and case-conversion
expansion.
