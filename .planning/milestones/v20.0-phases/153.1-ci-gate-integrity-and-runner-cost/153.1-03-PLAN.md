## Task 1 — Fix the existing broken and unsafe caches first

Before adding anything new, repair what is already there and lying:

- **`phase69-proof.yml:59`** uses `actions/cache@v3`, whose backing service was retired in February
  2025. It has been a no-op. Move to the current major version.
- **`contract-drift-gate.yml:64,90` and `offline-sync-e2e-gate.yml:108,145`** cache `_build` with
  **no OTP or Elixir dimension** in the key. The toolchain comes from `.tool-versions`, so bumping
  OTP silently restores incompatible BEAM files. This is a correctness bug, not an efficiency one —
  fix it here even though the cache "works".
- **Gradle cache** points at a project-local `.gradle` rather than `~/.gradle/caches`, so it caches
  approximately nothing useful. Prefer `gradle/actions/setup-gradle`, which handles this correctly,
  over a hand-rolled `actions/cache`.

## Task 2 — Build one composite action for the Elixir setup + cache

Create `.github/actions/setup-elixir-cache/action.yml` wrapping the block that is currently
copy-pasted roughly 40 times (`erlef/setup-beam` appears 62 times): checkout-adjacent setup,
`deps` + `_build` restore, `deps.get`, compile.

Cache key:
```
${{ runner.os }}-${{ runner.arch }}-otp${{ steps.beam.outputs.otp-version }}-elixir${{ steps.beam.outputs.elixir-version }}-${{ env.MIX_ENV }}-${{ hashFiles('**/mix.lock') }}
```
`restore-keys` must be the identical prefix with **only** the `mix.lock` hash removed. Any looser
prefix reintroduces the cross-toolchain corruption Task 1 just fixed.

Read OTP/Elixir from the `setup-beam` step outputs, not from hardcoded strings — hardcoding
reintroduces drift against `.tool-versions` the moment either is bumped.

Cache `deps/` and `_build` as **separate** entries. `deps/` is stable across compiler changes;
`_build` is not, and conflating them means one invalidation throws away both.

## Task 3 — Adopt the composite action across the Elixir lanes

Convert lanes to the composite action in reviewable batches, verifying each batch is green before
continuing.

Preserve exactly:
- job `name:` values (required contexts match by string — a rename un-protects the branch),
- every `--exclude` / `--only` flag,
- `MIX_ENV` per lane. `MIX_ENV` is a **key dimension**; a lane that silently changes it will
  thrash the cache rather than use it.

Skip `release-please.yml`. It is security-sensitive (REL-05 SHA pinning, two previously armed
fuses) and gains little here.

**A composite action must be SHA-pinned where the repo's REL-05 policy requires it.** Match the
surrounding file's existing pinning discipline rather than introducing a new convention; the seed
notes the repo is already split 94 SHA pins vs 94 tag pins along the infra/phase-proof line.

## Task 4 — Measure the hit rate honestly, then guard it

Cache correctness is invisible until measured, and a wrong key produces a permanent 0% hit rate
that looks exactly like "caching didn't help much."

- After the first merge to `main` (caches are branch-scoped — only `main` writes readable entries),
  record the hit rate per lane and the compile-time delta.
- Watch the **10 GB repo cap with LRU eviction**. If total cache size approaches it, entries evict
  each other and lanes get slower. If that happens, report it and reduce what is cached rather than
  quietly leaving it thrashing.

Add `test/crosswake/proof/phase153_1_cache_integrity_test.exs` asserting every `actions/cache` key
in the repo carries all of the `os`/`arch`/`otp`/`elixir`/`MIX_ENV`/`mix.lock` dimensions, and that
each `restore-keys` prefix differs from its primary key by exactly the lock hash. Include a negative
control with a key missing the OTP dimension and assert the test fails on it.

## Task 5 — Close the phase with the after-measurement

Re-measure the `153.1-BASELINE.md` metrics and write
`.planning/phases/153.1-ci-gate-integrity-and-runner-cost/153.1-RESULTS.md`: before, after, delta,
per lever (GATE / RUNNER / CACHE), using the same commands as the baseline.

**Lead with wall-clock time-to-green, not runner-seconds.** Baseline is 34.9 min across 41 runs for
one commit; the phase target is under 15 min. Runner-seconds is a billing metric and moves
independently — queue time costs wall-clock while billing nothing, and parallelism cuts wall-clock
without cutting spend. Report both, but the headline is the number a human waits through. If
wall-clock improved much less than runner-seconds (or vice versa), say so and explain which lever
moved which.

**Report the real numbers.** The seed's aspiration is ~25,500 → ~2,000-3,000 runner-seconds per
push, but that target assumes `CONSOL-*`, which is explicitly out of scope here. If this phase lands
well short of it, say so plainly and record what remains attributable to consolidation — an honest
partial result is what tells the next milestone whether the rest is worth doing.
