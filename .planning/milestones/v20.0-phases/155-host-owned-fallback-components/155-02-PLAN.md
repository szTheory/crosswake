<objective>
Fix the two shipped-code defects Phase 155 must land before generated adopter code can safely
call into the seam, each as its own bisectable commit.

D-50: `Crosswake.Bridge.resolve/2`'s docstring promises "it never raises", but its
implementation calls the strict `fetch_state!/1`. Starting with this phase, `resolve/2` ships
INSIDE generated adopter code (D-03), and in 155 there is no `menu` capability to motivate
calling `attach/1` — so an early adopter's first fallback click 500s. The fallback must never
be the thing that crashes.

D-51: the "family is not in the bridge vocabulary at all" moment routes into
`raise_undeclared_capability!/3`, whose remediation tells the adopter to add
`capabilities: ["…"]` — which per `validator.ex:116-131` escalates a click-time crash into a
mount-time crash. Ship a distinct, correctly-worded error instead.

Purpose: `resolve/2` becomes safe to call from generated code before any generated code calls
it, and the two undeclared moments stop collapsing into one misleading remediation.
Output: a tolerant `resolve/2`, a new `Crosswake.Bridge.UnknownCapabilityFamilyError`, and
ExUnit coverage for both — each with a positive and a negative control.
</objective>
