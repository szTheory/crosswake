<objective>
Ship the catalog line as a merge-blocking structural guard, and close the one latent contract
violation that goes from dormant to provable the moment Plan 03's reply parsing lands.

The guard extends the attestation file that already exists — `Manifest.Builder.capability_catalog/0`
is a committed compile-time literal carrying owner, package class, proof class, rebuild, denial,
fallback, guide, and prerequisites for all 15 capabilities. A second catalog file would recreate
exactly the two-lists-drift problem the milestone's API design rejects; here it would be five-way
drift (new file plus catalog plus the command list plus the capability-command map plus two native
enums). So: no new catalog (D-42), one new guard module in `lib/` (D-43).

Purpose: CTRL-04 says host-registrable or dynamic command registration must be structurally
impossible. This plan makes that mechanically true for the plugin-catalog road, and is honest in
writing about what it does NOT do (D-45): it does not stop a maintainer adding forty controls one
string at a time. The inoculation against gradual sprawl is the attestation criteria plus CTRL-05
making each control's rebuild cost publicly named — both of which shipped in Plan 02.

Output: `Crosswake.Bridge.CatalogGuard`, its predicate-level unit tests, and the merge-blocking
proof test with four kinds of negative control, riding existing hermetic lanes with no new workflow
file.
</objective>
