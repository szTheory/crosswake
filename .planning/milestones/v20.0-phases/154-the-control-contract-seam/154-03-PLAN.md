<objective>
**This plan carries the phase's tracer.** Task 1 wires one path through every layer of the seam
end-to-end — adopter LiveView → `Bridge.push/3` → `Registry.lookup/4` authorization → correlated
`Contract.Request` → `push_event` → (transport present or absent) → typed reply or synthesized
denial → `attach_hook` interception → `send/2` → adopter `handle_info/2` — and proves it with a
real `Phoenix.LiveViewTest` round trip, with zero JavaScript and zero native code.

That is deliberate. The one architectural question in this phase (can a typed struct cross the
reserved-event boundary?) is settled in Elixir, so if the shape is wrong it is wrong after one
commit rather than after the JS hook, the iOS return leg, and the showcase migration have all
been built on top of it. RESEARCH.md §1 verified against the installed `phoenix_live_view 1.1.30`
that halt-plus-`send` is the ONLY mechanism this version supports — `attach_hook(:handle_event)`
cannot rewrite the params an adopter's own `handle_event/3` sees on `{:cont, socket}`. D-17 is
locked with confidence; no execution-time spike is needed.

Tasks 2 and 3 expand outward from the proven slice: the loud-failure preflight (CTRL-03) and the
full denial collapse across all four failing moments (CTRL-02).

This is D-76's **PR #2a**: the seam, unit-tested only, no showcase changes. The example host is
not touched here.

Purpose: every future native-controls pack rides on this seam. Getting the reply shape and the
denial collapse right once is what makes Menu (Phase 156) a data change rather than a redesign.

Output: `Crosswake.Bridge` with `push/3`, `attach/1`, and `on_mount/4`; the adopter-facing
`Crosswake.Bridge.Reply` struct; `:shell_unreachable` as the 14th closed denial reason; and a
LiveViewTest suite that proves the round trip and both failure directions.
</objective>

   there is exactly one place the flattening happens. Plan 05 owns the structural guard that makes
